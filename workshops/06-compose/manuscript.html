Two services and a queue

0:00 → 1:00 · 1 min · 128 words

Hands up if you have ever run a program that was really three programs. A web app, a database, and something in the middle: a cache, a queue, a second service. Three terminals, started in the right order, or the first one crashes and you start again. Every morning, and the README said which order.

Today we write that order down. By the end you will have an API in Go, a worker in TypeScript and a Redis queue between them, and one file that starts all three with one command. Then we scale the worker to three, kill one while it is working, and go looking for the job it was holding. Fifteen minutes of talking, then ninety of typing, with two terminals open the whole time.

2

A service is a process with an address

1:00 → 3:00 · 2 min · 223 words

Here is the whole afternoon in one picture. Three boxes on one network. Each box is an ordinary process, exactly the kind of process workshop one put in a container. And the only thing any of them knows about the others is a name and a port.

Look at what they do not share. Not memory: the API cannot see the worker's variables. Not files: they have separate filesystems. Not even a language: the API is Go, the worker is TypeScript, and Redis is a C program none of us wrote. The only way any of them can affect another is to open a connection and send bytes. A socket is one program's open connection to another over the network. They meet on a socket, or they do not meet.

That sounds like a limitation, and it is also the point. Because they only touch over the network, you can write each one in whatever language fits, run them on one laptop or on three machines, restart one without the others noticing, and run three copies of one of them. Every word people use for this, microservices, distributed systems, service-oriented, means this picture with more boxes.

And it means the network is the first thing to get right, which is why one slide later in this talk is entirely about one word: localhost.

3

Why a queue

3:00 → 5:00 · 2 min · 225 words

Why is there a list in the middle at all? Why does the API not just do the work?

Because the API answers in about a millisecond, and the work takes a second. In our lab the work is fake, a one-second sleep and reversing a string, but stand in for it anything real: making a thumbnail, sending an email, running a report. If the API did that itself, every request would take a second, and a hundred requests at once would take a hundred seconds or crash it.

So the API does the smallest thing it can. It gives the job a number, writes it on the list, and says: accepted, here is your number. That is all. Somewhere else, a worker is waiting on that list, takes the job, spends its second, and writes the answer down under that number. Whoever asked comes back later and reads the answer.

Three things fall out of this. The API is fast no matter how slow the work is. A burst of a thousand jobs does not break anything; the list just gets long, and it drains. And if the list is draining too slowly, you add workers, without touching the API. The cost is that the answer arrives later, so there are two requests: post the job, then fetch the result. You will type both.

4

A queue is a list

5:00 → 6:00 · 1 min · 135 words

Redis is a server that keeps data structures in memory and lets you talk to them over the network. One of them is a list, and a list is all a queue is. Two commands. L push jobs hello: put hello on the left end of the list called jobs. B R pop jobs zero: take one element from the right end. Push left, pop right: oldest out first.

The letter that matters is the B, for blocking. If the list is empty, B R pop does not return empty-handed. It waits. Redis holds the connection open, and the moment somebody pushes, the waiting client gets it. The zero means wait forever. So a worker never polls; it asks once and Redis wakes it. Step one is this by hand: one terminal wakes the other.

5

What is on the wire

6:00 → 7:00 · 1 min · 133 words

Since these programs only meet as bytes on a socket, look at the bytes. This is what the API sends to push hello. A star and a three: three words follow. Each word as a dollar, its length, a line break, the word, a line break. Redis does the push and answers with a colon and a number: the length of the list.

That is the whole protocol we need, and it is so small that the Go API speaks it itself, in one function, no library: open a TCP connection, write those bytes, read one line back. You will paste that function and read it aloud. The Deno worker uses the official client instead, as you would in real life. A protocol is not magic; it is bytes two programs agreed on.

6

compose.yaml

7:00 → 8:00 · 1 min · 124 words

Here is the file. Read it as three docker run commands from workshop one, with the flags turned into keys. Image, or build a folder. Ports, which was dash p. Environment, which was dash e. Depends on, which says start Redis first. Three services, and docker compose up starts all three on a private network of their own. You will type it in two instalments this afternoon.

See it as a description of the system, not as configuration. Which processes exist. Which one is reachable from outside, and on which port: only the API. What each one is told: where Redis is. Hand someone a compose file for a system they have never seen and they know the architecture before they read any code.

7

Names, not localhost

8:00 → 10:00 · 2 min · 230 words

This is the slide that saves you an hour, because everybody gets bitten by it exactly once, and I would rather it was today.

In steps two and three you run the API and the worker natively on your laptop, and Redis is at localhost port 6379, because Compose published that port onto your laptop. It works, and your fingers learn it.

Then in step four the API moves into a container, and localhost means something different. Inside a container, localhost is that container. The API's localhost is the API. Nothing there listens on 6379. So the same address that worked a minute ago now says connection refused, and the log line looks like Redis is down. It is not down; you are knocking on your own door.

The address of another service, from inside the network, is its service name and its container port. Redis, colon, 6379. Compose runs a small DNS server on that network and answers for every service name, so the word redis in the compose file is literally the hostname. It does not matter whether the port is published; publishing is only for the laptop, and the containers would still find each other with the ports line deleted. Service name, container port, every time. Write it on your hand, because in step four the log line that says connection refused is not Redis being down.

8

Scaling is a number

10:00 → 12:00 · 2 min · 204 words

Here is the system from slide six, live. I post eight jobs: they land on the list, and one worker takes them off one a second. Watch the queue length. Now I switch to three workers: same list, same jobs, and it drains three times as fast.

That is what scaling is here. One flag: scale worker equals three. Compose starts three containers from the same image, and all three block on the same list. When a job arrives, Redis wakes the one that has been waiting longest, so the jobs go round-robin: one, two, three, then whoever finished first. In the lab, ten jobs took about four seconds with three workers instead of ten with one.

Notice what did not change: the code, the compose file, the API. A worker that takes one job at a time from a shared list is scalable by construction. You cannot do the same to the API, because three containers cannot all publish port 8080; that needs a load balancer, and that is workshop seven. And one more button, the red one. I press it once, a job turns orange and falls off the picture, and the counter says lost. Hold that thought for the next slide.

9

What gets lost

12:00 → 14:00 · 2 min · 256 words

Now the red button. A worker is holding a job, halfway through its second of work, and I kill it. Not politely: the way a crash, an out-of-memory or a rebooted machine kills it. Where is the job? It is not on the list; B R pop removed it. It is not in a result; the worker died first. It is gone, and nobody will ever notice unless they ask for that number and get "not done yet" forever.

That is called at-most-once delivery, and it is what a plain B R pop gives you. Sometimes it is fine: a lost thumbnail gets regenerated when someone looks. Sometimes it is not: a lost payment is a lost payment.

The alternative is at-least-once. Instead of popping, you move the job to a second list called working, do the work, and only then remove it. If the worker dies, the job is still in working, and a restarted worker puts it back on the queue. That is one Redis command, B L move, and a stretch goal with the code written for you.

But at-least-once has its own price: a job can run twice, if the worker died after doing the work and before removing it. So the work must be safe to repeat: run it twice, same result. The word is idempotent. Setting a result under an id is idempotent; charging a card is not. Every queue makes you choose one of these two, and in step six you will watch the loss with your own eyes.
