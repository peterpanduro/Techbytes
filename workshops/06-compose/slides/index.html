Two Services and a Queue

Three terminals, started in the right order, every morning.

A service is a process with an address

No shared memory, no shared files, no shared language. They meet on a socket or not at all.

Why a queue

api

writes it down: “accepted”

about a millisecond

→ list →

worker

does the work

one second each

A fast thing and a slow thing, cooperating without waiting for each other.

A queue is a list. Two commands.

LPUSH jobs hello

BRPOP jobs 0

Push on the left. Pop from the right. The B means: if it is empty, wait.

What is on the wire

*3\r\n $5\r\nLPUSH\r\n

$4\r\njobs\r\n $5\r\nhello\r\n

Redis answers :1\r\n

A protocol is bytes both sides agree on. The API speaks this one in a single function.

compose.yaml: the architecture, written down

services:
  redis:
    image: redis:7
    ports: ["6379:6379"]
  api:
    build: ./api
    ports: ["8080:8080"]
    environment:
      REDIS_ADDR: redis:6379
    depends_on: [redis]
  worker:
    build: ./worker
    environment:
      REDIS_URL: redis://redis:6379
    depends_on: [redis]

Workshop 1's docker run flags, per service, in one file. One command.

Names, not localhost

from your laptop

localhost:6379

the published port

from another container

redis:6379

service name · container port

Inside the network, localhost is yourself.

Scaling is a number

Interactive · three services, one network, one list

The API pushes jobs on the left end of a Redis list; each worker blocks on the right end. Post jobs, add workers, then kill one while it is busy and see what a plain queue does with the job it was holding.

queue 0 · working 0 · done 0 · lost 0

--scale worker=3: three copies, one list, and the code does not know.

What gets lost

at most once

BRPOP

popped, then the worker dies: gone

at least once

BLMOVE + a working list

put back if the worker dies: may run twice

Choose which mistake you can live with. Then make the work idempotent.
