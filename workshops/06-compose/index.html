Two Services and a Queue

An API in Go that accepts jobs, a worker in TypeScript that does them, and a Redis list between them. First each piece runs by itself on your laptop; then one compose.yaml starts all three as containers on a private network, scales the worker to three, and shows what a plain queue loses when a worker dies.

  • 15 min talk
  • 90 min guided lab
  • ~25 min student prep, one week before
  • Needs workshop 1 (Docker)
  • Deno + Go, deliberately both
  • Any OS
Interactive · three services, one network, one list

The API pushes jobs on the left end of a Redis list; each worker blocks on the right end. Post jobs, add workers, then kill one while it is busy and see what a plain queue does with the job it was holding.

Workshop 6

At a glance

OutcomeEvery student leaves with a three-service application they can start with one command, a compose file they wrote themselves and understand line by line, and two things in their fingers that no amount of reading gives: that services reach each other by service name and not localhost, and that a queue built from a Redis list drops the job a worker was holding when it dies.
Why this topicAlmost every system students will work on is several processes that only meet over the network. Docker Compose is where most people first see that written down, and most people first see it as a file somebody else wrote. Writing one from an empty file, with a real queue in the middle, makes the architecture visible. Workshops 7 and 8 deploy and instrument exactly these containers.
ConceptsServices as separate processes; a queue as a Redis list with LPUSH and BRPOP; a wire protocol (RESP) small enough to speak by hand; compose.yaml: services, build, image, ports, environment, depends_on; the project network and service-name DNS; published ports versus container ports; up --build, ps, logs -f, exec, --scale, kill, down; blocking pops and who gets woken; at-most-once versus at-least-once delivery and why idempotency matters.
Assumed knowledgeWorkshop 1: image versus container, -p, -e, docker ps/logs. Enough TypeScript to type 15 lines (workshop 2) and enough Go to read 90 lines aloud (workshops 3 and 4). No Redis, no Compose, no queues.
LanguageBoth, on purpose. The API is Go (pasted, read aloud, never edited) because its standard library speaks TCP and HTTP and workshop 1's Dockerfile builds it unchanged. The worker is TypeScript on Deno (typed) because a 15-line blocking loop is the whole idea and the Deno image needs no build stage. The two never share a line of code; they share a list in Redis. That is what "microservices" means at the smallest useful size.
Students needLaptop with Docker Desktop or Docker Engine (workshop 1), Deno 2 (workshop 2), Go 1.27 (workshops 3–4), curl, a text editor, and the three images from the prep pack already pulled: redis:7, denoland/deno:2.9.7, golang:1.27.
Room needsProjector. Wi-Fi only for step 3's one-time npm:redis download (a few hundred kilobytes) and for anyone who skipped the prep; the instructor carries the images on a USB stick.
Timing15 min talk · 5 min break · 90 min lab (seven steps, each with a checkpoint that must pass before moving on). The heaviest afternoon of the year: two terminals open from step 1 and nothing optional before step 7.

The talk: the compose file is the architecture, written down

The single idea to land: services are separate processes that only ever meet over the network, so the file that says which processes exist, how they find each other and what they are told is the whole architecture. Everything in the lab, including the lost job, follows from it.

  1. 1Two services and a queue1 min Title slide. Ask who has run a program that was really three programs: a web app plus a database plus something else, started in the right order in three terminals. Today we write that order down.
  2. 2A service is a process with an address2 min Three boxes on one network. Each is an ordinary process, exactly as in workshop 1, and the only thing any of them knows about the others is a name and a port. No shared memory, no shared files, no shared language: the API is Go, the worker is TypeScript, Redis is C. They meet on a socket or not at all. This is what "microservices" means at its smallest, and it is why the network is the first thing to get right.
  3. 3Why a queue2 min The API answers in a millisecond because it does not do the work: it writes the job down and says "accepted". The worker takes a second per job. The list in between lets a fast thing and a slow thing cooperate without waiting for each other, absorbs bursts, and lets us add workers without touching the API. It also means the answer arrives later, so there is a second request to fetch it. Two cards: "API: 2 ms, accepted" and "worker: 1 s each".
  4. 4A queue is a list: LPUSH and BRPOP1 min Redis is a server that holds data structures in memory. One of them is a list. LPUSH jobs x puts x on the left end; BRPOP jobs 0 takes from the right end, and if the list is empty it waits, holding the connection open, until something arrives. That B is the whole trick: the worker does not poll, it sleeps inside Redis. Step 1 does this by hand in two terminals.
  5. 5What is on the wire1 min The bytes the API sends: *3\r\n $5\r\nLPUSH\r\n $4\r\njobs\r\n $5\r\nhello\r\n. A star, the number of words, then each word as a dollar, its length, the word. Redis answers :1\r\n, the length of the list. That is the entire protocol we need, and the Go API speaks it in one function with no library, so that nobody has to trust a client they cannot read. The Deno worker uses the official client instead; both are fine, and the point is that a protocol is just bytes both sides agree on.
  6. 6compose.yaml: the architecture, written down1 min The file, alone. Three services. Each one is a docker run from workshop 1 with the flags turned into keys: build or image, ports, environment, depends_on. One command starts all three on a private network. Read it as a description of the system: which processes exist, which one is reachable from outside, what each is told.
  7. 7Names, not localhost2 min The thing that bites everyone once. On your laptop Redis is localhost:6379, because Compose published that port. Inside the network, the API's localhost is the API's own container, where nothing listens on 6379. The address of Redis from another container is the service name, redis, and the container port, 6379, whether or not anything is published. Compose runs a DNS server that answers for service names. Two cards: from the laptop, from a container.
  8. 8Scaling is a number2 min The widget from the top of this page. Post eight jobs with one worker: they queue and drain one a second. Switch to three workers: same list, three times faster. --scale worker=3 is three containers from the same image, all blocked on the same list; Redis wakes the one that has been waiting longest, so the jobs go round-robin: in the lab ten jobs took about four seconds instead of ten. Nothing in the code knows it was scaled. Press the red button once and say "hold that thought".
  9. 9What gets lost2 min Kill a worker while it is holding a job. The job was popped, so it is not in the list; the worker is dead, so it is not in the result either. It is gone. That is at-most-once delivery, and it is what a plain BRPOP gives you. The alternative, at-least-once, moves the job to a "working" list instead of popping it (BLMOVE) and puts it back if the worker dies; the price is that a job can then run twice, so the work has to be safe to repeat: idempotent. Every queue system you will ever use is one of these two, and the lab shows you the loss with your own eyes so you never forget which one you chose.
  10. 10What we build in the next 90 minutes1 min Seven steps: Redis alone, the queue by hand; the API natively; the worker natively; all three in Compose; scale; kill; wrap-up. Two terminals from step 1. Five-minute break, then step 0.

Step 1

Redis alone: the queue is two commands

15 min

Before any code, the queue itself. Create compose.yaml in compose-lab with one service in it:

services:
  redis:
    image: redis:7
    ports: ["6379:6379"]

Four lines: a services map, a service called redis, the image it runs, and a published port so that programs on your laptop can reach it at localhost:6379. Start it and open a Redis prompt inside the container:

docker compose up -d redis
docker compose exec redis redis-cli
BRPOP jobs 0

The prompt hangs. BRPOP jobs 0 means "take one element from the right end of the list called jobs, and if there is none, wait forever". Nothing is there, so it waits. In your second terminal, put something on the left end:

docker compose exec redis redis-cli LPUSH jobs hello

The first terminal wakes up immediately and prints the list name and the element. That is the entire mechanism of the afternoon: one side pushes, the other side blocks until there is something to pop. Now, still in the first terminal's prompt, push three at once and pop them one by one (press the up arrow to repeat BRPOP):

LPUSH jobs a b c
BRPOP jobs 0

They come out a, b, c: LPUSH adds to the left, so a was pushed first and ended up rightmost, and BRPOP takes from the right. Oldest first, a queue. A fourth BRPOP hangs again; Ctrl-C it (the image's redis-cli returns to its prompt) and type exit.

Checkpoint 1

The blocked BRPOP in terminal one printed 1) "jobs" 2) "hello" the moment terminal two ran LPUSH; LPUSH jobs a b c printed (integer) 3; three pops gave a, b, c in that order; docker compose ps would show one container, compose-lab-redis-1.

Talk about it: where was the blocked client while it waited: in your terminal, or inside Redis? (Its connection was open and Redis was holding it; no polling.) What is the difference between docker compose exec redis and workshop 1's docker exec compose-lab-redis-1? (None; Compose only fills in the container name.) Why is the container called compose-lab-redis-1? (Project name from the folder, service name, replica number. The -1 matters in step 5.)

Step 2

The API, natively, against the Compose Redis

15 min

The API is 95 lines of Go, and it is pasted: Go is not today's topic. Create these two files in the api folder, then read main.go top to bottom as a room. It does three things. POST /jobs makes an id and pushes "<id> <body>" on the list, exactly your LPUSH from step 1. GET /jobs/<id> reads the key result:<id>, which nothing writes yet. And the function redis() at the bottom speaks the Redis protocol itself: it opens a TCP connection, writes the command as a counted list of words, and reads one reply. Match the bytes in its comment against what you typed in step 1.

api/go.mod

module api

go 1.24

api/main.go

// The API: takes jobs in over HTTP and puts them on a Redis list.
// It never does the work itself; a worker somewhere else does.
package main

import (
	"bufio"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"log"
	"net"
	"net/http"
	"os"
	"strconv"
	"strings"
)

func main() {
	addr := os.Getenv("REDIS_ADDR") // "redis:6379" inside Compose
	if addr == "" {
		addr = "localhost:6379"
	}

	// POST /jobs with any text body: give it an id, push "<id> <text>" on the list.
	http.HandleFunc("POST /jobs", func(w http.ResponseWriter, r *http.Request) {
		body, _ := io.ReadAll(r.Body)
		id := newID()
		n, err := redis(addr, "LPUSH", "jobs", id+" "+string(body))
		if err != nil {
			http.Error(w, err.Error(), 502)
			return
		}
		log.Printf("queued %s (%s waiting)", id, n)
		fmt.Fprintf(w, "{\"id\":%q}\n", id)
	})

	// GET /jobs/<id>: the worker leaves the answer in the key result:<id>.
	http.HandleFunc("GET /jobs/{id}", func(w http.ResponseWriter, r *http.Request) {
		result, err := redis(addr, "GET", "result:"+r.PathValue("id"))
		if err != nil {
			http.Error(w, err.Error(), 502)
			return
		}
		if result == "" {
			http.Error(w, "not done yet", 404)
			return
		}
		fmt.Fprintln(w, result)
	})

	log.Println("api listening on :8080, redis at", addr)
	log.Fatal(http.ListenAndServe(":8080", nil))
}

// redis sends one command in RESP, the Redis wire protocol, and returns the reply.
// A command is an array of bulk strings: "*2\r\n$3\r\nGET\r\n$5\r\nhello\r\n".
func redis(addr string, args ...string) (string, error) {
	c, err := net.Dial("tcp", addr)
	if err != nil {
		return "", err
	}
	defer c.Close()
	fmt.Fprintf(c, "*%d\r\n", len(args))
	for _, a := range args {
		fmt.Fprintf(c, "$%d\r\n%s\r\n", len(a), a)
	}
	rd := bufio.NewReader(c)
	line, err := rd.ReadString('\n')
	if err != nil {
		return "", err
	}
	line = strings.TrimRight(line, "\r\n")
	switch line[0] {
	case '+', ':': // simple string or integer: "+OK", ":3"
		return line[1:], nil
	case '-': // error: "-ERR unknown command"
		return "", fmt.Errorf("redis: %s", line[1:])
	case '$': // bulk string: "$5\r\nhello\r\n"; "$-1" means no such key
		n, _ := strconv.Atoi(line[1:])
		if n < 0 {
			return "", nil
		}
		buf := make([]byte, n+2)
		_, err = io.ReadFull(rd, buf)
		return string(buf[:n]), err
	}
	return "", fmt.Errorf("redis: unexpected reply %q", line)
}

func newID() string {
	b := make([]byte, 4)
	rand.Read(b)
	return hex.EncodeToString(b)
}

Run it natively in terminal one, from inside the api folder. With no REDIS_ADDR set it talks to localhost:6379, which is the port you published in step 1:

go run .

In terminal two, post a job and then ask for its result, using the id you got back:

curl -d "hello world" localhost:8080/jobs
curl localhost:8080/jobs/1c8a66fe
docker compose exec redis redis-cli LRANGE jobs 0 -1

Checkpoint 2

The POST prints {"id":"1c8a66fe"} (your eight hex characters differ). The GET prints not done yet, and that is correct: nobody has done it. LRANGE shows the job sitting in the list as one string, 1) "1c8a66fe hello world". Terminal one logged queued 1c8a66fe (1 waiting).

Common mistakes: go run from compose-lab instead of api ("no Go files"); bind: address already in use because workshop 1's container is still running on 8080 (docker ps, then docker rm -f it); on Windows, curl without .exe gives a PowerShell error about -d. Talk about it: the API answered in a millisecond and did no work. Where is the job now, and who owns it?

Step 3

The worker

15 min

Now the other half, typed. Create worker/worker.ts. It is step 1's BRPOP loop in TypeScript: block on the list, split the job into its id and its text, pretend the work is hard for one second, write the answer under result:<id>, repeat. The "work" is reversing the text, so you can check it by eye. The npm:redis client is the official one; brPop returns the same two things redis-cli printed, the list name and the element. The ! after job is not a typo: it tells TypeScript the pop cannot be empty, because we asked it to wait forever.

import { createClient } from "npm:redis@4";

const redis = createClient({ url: Deno.env.get("REDIS_URL") });
await redis.connect();
const me = Deno.hostname();
console.log(me, "waiting for jobs");

while (true) {
  const job = await redis.brPop("jobs", 0);
  const [id, ...words] = job!.element.split(" ");
  const text = words.join(" ");
  console.log(me, "got", id, text);
  await new Promise((r) => setTimeout(r, 1000));
  const result = [...text].reverse().join("");
  await redis.set(`result:${id}`, result);
  console.log(me, "done", id, result);
}

Leave the API running in terminal one and start the worker in terminal two, after cd worker (terminal two has been in compose-lab since step 1). Deno asks for each thing the program touches: the network, the REDIS_URL variable (unset for now, so the client uses localhost:6379), and the hostname it prints so you can tell workers apart later.

deno run --allow-net --allow-env --allow-sys worker.ts

The first run downloads npm:redis@4. Watch the worker's output: the job you posted in step 2 was still in the list, so it is taken at once. Then, in a third terminal (this is the only step that needs one), post another and fetch the result:

curl -d "hello world" localhost:8080/jobs
curl localhost:8080/jobs/1d33a31b

Checkpoint 3

The worker printed vm waiting for jobs (your hostname instead of vm), then got 1c8a66fe hello world and one second later done 1c8a66fe dlrow olleh. A GET for the new id within the first second says not done yet; after that it prints dlrow olleh. The list is empty again.

Common mistakes: error: Module not found "file:///…/compose-lab/worker.ts" means terminal two is still in compose-lab: cd worker; a missing --allow- flag stops the program with NotCapable: Requires env access (or sys access) and names the flag to add; job.element underlined red in the editor because the ! was left out (brPop can return null on a timeout, and the type system does not know we passed 0). Talk about it: the worker got a job it never saw posted. What does that say about where the queue lives? What if two people in the room pointed their worker at the same Redis?

Step 4

All three in Compose

15 min

Everything works, and it works because two programs are running natively in two terminals with the right folders and the right addresses in your head. Now write that down. First the two Dockerfiles, pasted: the API's is workshop 1's multi-stage file unchanged; the worker's is one stage because the Deno runtime has to stay in the image.

api/Dockerfile

# Same recipe as workshop 1: build in the Go image, ship one file in an empty image.
FROM golang:1.27 AS build
WORKDIR /app
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

FROM scratch
COPY --from=build /app/server /server
EXPOSE 8080
CMD ["/server"]

worker/Dockerfile

# Deno ships its own image; the runtime stays in, so this is one stage.
FROM denoland/deno:2.9.7
WORKDIR /app
COPY worker.ts .
RUN deno cache worker.ts
CMD ["deno", "run", "--allow-net", "--allow-env", "--allow-sys", "worker.ts"]

Now stop both native programs with Ctrl-C and add two services to compose.yaml, under the redis service from step 1, at the same indentation:

  api:
    build: ./api
    ports: ["8080:8080"]
    environment:
      REDIS_ADDR: redis:6379
    depends_on: [redis]
  worker:
    build: ./worker
    environment:
      REDIS_URL: redis://redis:6379
    depends_on: [redis]

Read it as three docker run commands. build: ./api is docker build ./api; ports is -p; environment is -e; depends_on says "start Redis first". The one new idea is in the two environment values: the address of Redis is redis, the service name, not localhost. Build and start all three in terminal one, in the foreground so you see every log line:

docker compose up --build
curl -d "hello world" localhost:8080/jobs
curl localhost:8080/jobs/9f0c3a11

The two curls go in terminal two once the logs settle. The API's build pulls nothing (you have golang:1.27) but compiles for a few seconds; the worker's build runs deno cache inside the image, which downloads npm:redis again, because the image has its own filesystem.

Checkpoint 4

Three services start, compose-lab-redis-1, compose-lab-api-1 and compose-lab-worker-1 (docker compose ps in terminal two lists them, all Up). The same two curls as before work with nothing running natively, and the answer comes back dlrow olleh. In terminal one the three logs are interleaved with a coloured prefix per service, and the worker's line says waiting for jobs with a twelve-character hostname: the container id, as in workshop 1.

The one that always bites

If the worker log says ECONNREFUSED 127.0.0.1:6379 or the API answers with a 502, an address still says localhost. Inside a container, localhost is that container, and nothing there listens on 6379. Service name, container port: redis:6379. Fix the compose file and docker compose up -d again; Compose restarts only what changed. The other silent one: worker-1 Exited (1) right after up with ECONNREFUSED in its log means the worker lost the start race with Redis (depends_on only orders the starts, and the worker has no retry); docker compose up -d worker again, and stretch goal 2 fixes it properly.

Talk about it: the worker's REDIS_URL says redis:6379, the container port, although Redis is also published on your laptop's 6379. Would it still work if you deleted the ports line under redis? (Yes for the containers, no for your laptop's redis-cli.) What resolves the name redis? What would happen if two students ran this in folders with the same name on one machine?

Step 5

Scale the worker

7 min

Ctrl-C the foreground up (it stops the containers; that is fine) and start again detached, with three workers, then follow only the workers' logs:

docker compose up -d --scale worker=3
docker compose logs -f worker

In terminal two, post ten jobs in one go. Paste the loop for your shell:

for i in $(seq 1 10); do curl -sd "job $i" localhost:8080/jobs; done
1..10 | ForEach-Object { curl.exe -sd "job $_" localhost:8080/jobs }

Checkpoint 5

The log shows three prefixes, worker-1, worker-2, worker-3, each with its own hostname, and the jobs are dealt round-robin: job 1 to the worker that had been waiting longest, job 2 to the next, job 3 to the third, then job 4 to whichever finished first. All ten are done about four seconds after the loop, instead of ten. Nothing in worker.ts or the compose file changed.

Talk about it: what decided which worker got job 1? (Redis wakes blocked clients in the order they blocked.) What would happen if you scaled the API to 3? (It would fail: three containers cannot all publish port 8080. Workshop 7 solves that with a load balancer.) Could you scale Redis the same way? (No: then there would be three queues.)

Step 6

Kill a worker mid-job

10 min

Keep logs -f running in terminal one and do all of this step in terminal two. Back to one worker, so that the queue drains slowly enough to catch. Then post thirty jobs (thirty seconds of work), count to three, and kill the worker the hard way, which is what a crash, an out-of-memory or a machine reboot looks like:

docker compose up -d --scale worker=1
for i in $(seq 1 30); do curl -sd "job $i" localhost:8080/jobs; done
1..30 | ForEach-Object { curl.exe -sd "job $_" localhost:8080/jobs }
docker compose kill worker
docker compose up -d worker

Look at terminal one's logs -f just before the restart: the worker had printed got for one job, say job 4, and no done. Copy the id from that last got line (not from the loop's output: a mistyped id also says not done yet, which would prove nothing) and fetch that job's result:

curl localhost:8080/jobs/9b4c2ae7

Checkpoint 6

docker compose kill worker prints Killed and docker compose ps -a would show Exited (137), which is 128 plus signal 9. After up -d worker the worker continues with the next job (job 5 onwards) and finishes all of them. The job it was holding says not done yet, forever. It is not in the list (BRPOP removed it) and not in a result (the worker died first). Every other job survived, because they were still in Redis.

Talk about it: this is at-most-once delivery, and it is what a plain BRPOP gives you. For a thumbnail or an email it may be acceptable; for a payment it is not. The alternative is at-least-once: move the job to a second list instead of popping it, and put it back if the worker dies (stretch goal 1). The price is that a job can then run twice, so the work must be idempotent: doing it again gives the same result, like SET result:<id> does and "charge the card" does not. Ask the room which of their own projects' jobs are idempotent.

Step 7

Wrap-up and stretch goals

8 min

Bring the room back together for five minutes, then let the fast students pick a stretch goal. Everyone finishes with:

docker compose down

Wrap-up points

  • Three processes, three languages, one list. They never shared anything but a network; that is why they could be started separately in steps 1–3 and together in step 4 without changing a line.
  • The compose file is the architecture: which services exist, what they run, which ports leave the network, what each is told. Read someone else's compose file this way and you understand their system.
  • Names, not localhost. Service name plus container port, always, from inside the network.
  • A queue is a list; blocking pop is why workers can sleep; scaling is a number. And BRPOP loses the job in flight: choose at-most-once or at-least-once on purpose, and make work idempotent if you choose the second.

Stretch goals (pick one)

  • A queue that does not lose jobs. Replace the worker with worker-reliable.ts from the solution: BLMOVE jobs working RIGHT LEFT moves the job to a working list instead of popping it, LREM removes it when done, and a starting worker puts anything left in working back on the queue. Repeat step 6: the killed job now completes after the restart. Then argue about what happens with three workers when one dies (the restarted one re-queues the other two's in-flight jobs too, so they run twice: idempotency again).
  • Wait for healthy, not just started. depends_on: [redis] only orders the starts. Use compose-healthy.yaml from the solution: a healthcheck on Redis (redis-cli ping every 2 s), condition: service_healthy on the other two, and a named volume so the queue survives docker compose down. Watch docker compose up print Waiting then Healthy before starting the API.
  • Settings out of the file. Put REDIS_URL and the published port in a .env file next to compose.yaml and reference them as ${REDIS_URL}; run docker compose config to see the file with values filled in. That is how the same file runs on a laptop and a server.
  • Real work. Replace the reversal with a SHA-256 of the text using crypto.subtle.digest (WebCrypto, the same API whose sign you used in workshop 2), and bump the sleep to three seconds so the scaling in step 5 is more dramatic.
  • Where does the worker's hostname come from? Compare Deno.hostname() in the log with docker compose ps and docker inspect. Then set hostname: in the compose file and see it change.
  • The CI demo (instructor, projector, 10 min). Show a GitHub Actions workflow that runs docker compose up --build -d, posts a job with curl, polls for the result and fails the build if it never appears. Workshop 10 builds the full pipeline; the compose file is what makes an integration test a shell script.

// The API: takes jobs in over HTTP and puts them on a Redis list.
// It never does the work itself; a worker somewhere else does.
package main

import (
	"bufio"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"log"
	"net"
	"net/http"
	"os"
	"strconv"
	"strings"
)

func main() {
	addr := os.Getenv("REDIS_ADDR") // "redis:6379" inside Compose
	if addr == "" {
		addr = "localhost:6379"
	}

	// POST /jobs with any text body: give it an id, push "<id> <text>" on the list.
	http.HandleFunc("POST /jobs", func(w http.ResponseWriter, r *http.Request) {
		body, _ := io.ReadAll(r.Body)
		id := newID()
		n, err := redis(addr, "LPUSH", "jobs", id+" "+string(body))
		if err != nil {
			http.Error(w, err.Error(), 502)
			return
		}
		log.Printf("queued %s (%s waiting)", id, n)
		fmt.Fprintf(w, "{\"id\":%q}\n", id)
	})

	// GET /jobs/<id>: the worker leaves the answer in the key result:<id>.
	http.HandleFunc("GET /jobs/{id}", func(w http.ResponseWriter, r *http.Request) {
		result, err := redis(addr, "GET", "result:"+r.PathValue("id"))
		if err != nil {
			http.Error(w, err.Error(), 502)
			return
		}
		if result == "" {
			http.Error(w, "not done yet", 404)
			return
		}
		fmt.Fprintln(w, result)
	})

	log.Println("api listening on :8080, redis at", addr)
	log.Fatal(http.ListenAndServe(":8080", nil))
}

// redis sends one command in RESP, the Redis wire protocol, and returns the reply.
// A command is an array of bulk strings: "*2\r\n$3\r\nGET\r\n$5\r\nhello\r\n".
func redis(addr string, args ...string) (string, error) {
	c, err := net.Dial("tcp", addr)
	if err != nil {
		return "", err
	}
	defer c.Close()
	fmt.Fprintf(c, "*%d\r\n", len(args))
	for _, a := range args {
		fmt.Fprintf(c, "$%d\r\n%s\r\n", len(a), a)
	}
	rd := bufio.NewReader(c)
	line, err := rd.ReadString('\n')
	if err != nil {
		return "", err
	}
	line = strings.TrimRight(line, "\r\n")
	switch line[0] {
	case '+', ':': // simple string or integer: "+OK", ":3"
		return line[1:], nil
	case '-': // error: "-ERR unknown command"
		return "", fmt.Errorf("redis: %s", line[1:])
	case '$': // bulk string: "$5\r\nhello\r\n"; "$-1" means no such key
		n, _ := strconv.Atoi(line[1:])
		if n < 0 {
			return "", nil
		}
		buf := make([]byte, n+2)
		_, err = io.ReadFull(rd, buf)
		return string(buf[:n]), err
	}
	return "", fmt.Errorf("redis: unexpected reply %q", line)
}

func newID() string {
	b := make([]byte, 4)
	rand.Read(b)
	return hex.EncodeToString(b)
}

// Stretch goal: the reliable-queue pattern from the Redis LMOVE docs.
// A job is MOVED to a "working" list instead of popped, and removed from
// there only when finished. A job a dead worker was holding is still in
// "working", so a restarted worker puts it back on the queue first.
import { createClient } from "npm:redis@4";

const redis = createClient({ url: Deno.env.get("REDIS_URL") });
await redis.connect();
const me = Deno.hostname();

while (await redis.lMove("working", "jobs", "RIGHT", "RIGHT")) {
  console.log(me, "re-queued a job somebody was holding when they died");
}
console.log(me, "waiting for jobs");

while (true) {
  const job = await redis.blMove("jobs", "working", "RIGHT", "LEFT", 0);
  const [id, ...words] = job!.split(" ");
  const text = words.join(" ");
  console.log(me, "got", id, text);
  await new Promise((r) => setTimeout(r, 1000));
  const result = [...text].reverse().join("");
  await redis.set(`result:${id}`, result);
  await redis.lRem("working", 1, job!);
  console.log(me, "done", id, result);
}

Timing reality

Step 4 is the slow moment: the first docker compose up --build compiles the Go program inside golang:1.27 and downloads npm:redis inside the Deno image, a minute or two per laptop, and it is where any laptop that skipped the prep discovers it. Step 1 runs long if the two-terminal BRPOP demo is done carelessly; do it once on the projector first. Steps 5 and 6 are short and must not be cut: they are the payoff. If you are behind after step 3, skip the LRANGE in step 2 and the "talk about it" in step 4. Step 7's stretch goals absorb any time left over. Nothing about this afternoon was run in a containerised form in the authoring environment beyond stand-in images; the first time you run step 4 on your own laptop, write down how long the build takes and say that number in the room.

Things students ask

  • "Why does the API open a new TCP connection per request?" Because it keeps the protocol code to one readable function. A real service keeps a connection (or a pool) open; the Deno worker does, via the client library. Offer it as a small refactor for anyone bored.
  • "Why is the worker's error a crash and not a retry?" If Redis is unreachable when the worker starts it exits with ECONNREFUSED, and if Redis restarts under it the client throws Socket closed unexpectedly. That is deliberate for the lab: a container that exits is visible in docker compose ps. In production you add restart: unless-stopped to the service and the healthcheck from stretch goal 2, and Compose restarts it.
  • "Is Redis a database?" It can be, but here it is a shared data structure on the network. The same list would work as a queue with any Redis client in any language, which is the point of the two languages.
  • "Why not RabbitMQ / Kafka / SQS?" Same concepts, more machinery: acknowledgements, consumer groups, retention. Redis Streams (XADD/XREADGROUP) are the next step up and give at-least-once with acknowledgements built in. Everything in step 6 applies to all of them.
  • "Can two people share one Redis?" Yes, and it is a good demo: one student's worker consuming another's jobs over the room Wi-Fi shows that the queue is the shared thing, not the code.
  • "npm:redis@4 or the newest?" The current release of node-redis is 6.2.1 and worker.ts runs unchanged against it (tested). The page pins 4 so that every laptop in the room resolves the same code; change it when you re-run the lab.
