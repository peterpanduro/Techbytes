    Workshop 4

    At a glance

    OutcomeEvery student leaves with a folder containing their own certificate authority, a server certificate it signed, a Go HTTPS server the browser shows a padlock for, a Go client that trusts exactly one CA, and a working answer to "what does the padlock mean?": a key I trust vouched for this name, for these dates, and nothing more.
    Why this topicEveryone has clicked through a certificate warning, and almost nobody has made one on purpose. Certificates are copied from Stack Overflow with flags nobody can explain, and "just disable verification" ends up in production code. An afternoon of being the CA yourself replaces the superstition with a mental model that transfers to Let's Encrypt, corporate proxies, mutual TLS and every "unable to get local issuer certificate" for the rest of a career.
    ConceptsPublic and private keys as sign/verify, what a certificate is (a signed statement about a public key and a name), certificate authorities and the chain of vouching, the browser and OS trust stores, subject alternative names, validity dates, the TLS 1.3 handshake as seen through openssl s_client, verification in code with crypto/x509, and the three failure modes: unknown issuer, wrong name, expired.
    Assumed knowledgeCan open a terminal and run a command. Wrote a little Go in workshop 3; no cryptography. Every openssl flag is explained on first use, and every flag is one the student will see again.
    LanguageGo, standard library only: net/http does HTTPS in one call, crypto/x509 and crypto/tls make trust explicit in five lines. openssl is the other tool, because it is what every server, tutorial and colleague uses; on macOS it is LibreSSL, which accepts every command on this page but words some of its output differently (each checkpoint says how).
    Students needLaptop with Go 1.27, openssl on the PATH, curl, Firefox, a text editor. The readiness check in the prep confirms all of it in one command.
    Room needsProjector. No Wi-Fi needed after the prep: nothing in the lab leaves the laptop.
    Timing15 min talk · 5 min break · 90 min lab (seven steps, each with a checkpoint that must pass before moving on).

    Preparation

    For students (about 20 minutes)

    This is written to be pasted into an email or course page as-is.

    1. Install Go 1.27

    If you did workshop 3 you already have it; check with go version, which should print go1.27 followed by a patch number. Otherwise download the installer for your machine from go.dev/dl (the featured downloads are go1.27.1.darwin-arm64.pkg for Apple silicon Macs, go1.27.1.windows-amd64.msi for Windows, and go1.27.1.linux-amd64.tar.gz for Linux) and follow go.dev/doc/install. On Linux that is:

    rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go1.27.1.linux-amd64.tar.gz
export PATH=$PATH:/usr/local/go/bin   # also add this line to ~/.profile

    Open a new terminal afterwards so the PATH change is picked up.

    2. Make sure you have openssl and curl

    macOS and Linux: both are already installed. openssl version prints LibreSSL 3.x on a Mac and OpenSSL 3.x on Linux; either is fine.

    Windows: curl is part of Windows 10 and 11. openssl is not, so install it with winget in PowerShell:

    winget install -e --id ShiningLight.OpenSSL.Light

    The installer puts it in C:\Program Files\OpenSSL-Win64\bin but does not add that folder to your PATH. Open Start, type "environment variables", choose "Edit environment variables for your account", select Path, Edit, New, and paste C:\Program Files\OpenSSL-Win64\bin. Open a new PowerShell window. (If you already have Git for Windows, it ships an openssl at C:\Program Files\Git\usr\bin\openssl.exe; adding that folder to the PATH instead works too.) Use PowerShell, not Git Bash, for this workshop: Git Bash rewrites arguments that start with a slash, and the certificate commands are full of those.

    3. Firefox

    Install Firefox from mozilla.org/firefox if you do not have it. We use it because its certificate manager works the same way on every operating system and needs no administrator password. Chrome and Safari use the operating system's store, which is a different afternoon.

    4. The readiness check

    Make a folder called https-lab, open a terminal in it (Terminal on macOS, PowerShell on Windows), and turn it into a Go module:

    go mod init httpslab

    Then make a subfolder ready inside it and save this as ready/main.go:

    package main

import (
	"crypto/tls"
	"fmt"
	"os/exec"
)

func main() {
	for _, tool := range []string{"openssl", "curl"} {
		if _, err := exec.LookPath(tool); err != nil {
			fmt.Println("not found on PATH:", tool)
			return
		}
	}
	fmt.Println("ready:", tls.VersionName(tls.VersionTLS13), "in Go, openssl and curl on PATH")
}

    Run it from the https-lab folder:

    go run ./ready

    Expected output

    ready: TLS 1.3 in Go, openssl and curl on PATH. That one line proves Go compiles and runs, and that both tools are reachable from your terminal. If it prints not found on PATH: openssl, step 2 is not finished. If go itself is not found, step 1 is not finished. Bring any other error to the workshop and arrive ten minutes early.

    The talk: whom is this encrypted to?

    The single idea to land: the padlock means "a key I already trust vouched for this name", nothing more and nothing less. Encryption is the easy half; the whole apparatus of certificates exists to answer the question "encrypted to whom?", and every failure students will ever see is one of three checks failing.

    1. 1What does the padlock promise?1 min Title slide. Everyone has clicked "Accept the risk" on a certificate warning; almost nobody has made a certificate on purpose. Today everyone in the room becomes a certificate authority and finds out exactly what the padlock is and is not saying.
    2. 2Two problems, not one2 min HTTP is a postcard: anyone on the path can read it and change it. Encryption fixes reading. But encrypting to a stranger is worthless: an attacker in the middle can offer you their key and read everything. So the second problem is identity: am I talking to the server I typed into the address bar? TLS solves both; certificates are the identity half.
    3. 3Keys that sign and keys that verify1 min A key pair: the private key signs, the public key verifies, and the public key can be shown to everyone. A signature proves "whoever holds the private key approved these bytes". That is the only cryptography today; the rest is bookkeeping about names and dates.
    4. 4A certificate is a signed statement2 min Show the real openssl x509 -text output. Subject: who this is about. Public key: theirs. Subject Alternative Name: the DNS names it is valid for. Validity: two dates. Issuer: who signed it. Signature: the issuer's private key over everything above. A certificate is a public key with a name, dates, and a signature. It contains no secrets.
    5. 5The chain of vouching2 min Who signed the CA's certificate? The CA itself; a root is self-signed. So why believe it? Because your browser or OS ships with a list of about 150 root certificates and treats them as axioms. The chain: trust store vouches for the CA, the CA vouches for the server. In the lab we add ourselves to the list, and the browser stops complaining, because that is all "trusted" means.
    6. 6The handshake in five lines2 min Client: I speak TLS 1.3, here is my half of a key. Server: here is mine, here is my certificate, and here is a signature made with the certificate's private key to prove I hold it. Client checks chain, name, dates. From then on everything is encrypted; HTTP/2 rides inside. openssl s_client shows every line of this in step 5.
    7. 7What the padlock checks2 min Use the widget. Three checks: chain (signed by someone in my store), name (the certificate is for the host in the address bar), dates (valid today). Press the four buttons: unknown CA fails check one, importing the CA fixes it without touching the server, 127.0.0.1 fails the name check with the same certificate, and an expired certificate fails the dates. Each failure has its own error code, and the lab produces all three.
    8. 8What it does not promise1 min A valid certificate says nothing about whether the site is honest, competent, or the one you meant. Phishing sites have padlocks; Let's Encrypt is free and automated. The padlock is about the pipe, not the person at the other end. This is the sentence to take home.
    9. 9How real sites get certificates1 min Nobody emails a CSR any more. ACME: the CA says "put this token at this URL or in DNS", the server does, the CA checks from several places on the internet, and issues a 90-day certificate. Free, automated, renewed by a cron job or by autocert in Go. Same chain, same checks; only the vouching is automated.
    10. 10What we build in the next 90 minutes1 min Seven steps: a plain HTTP server, then a CA in two commands, a server certificate signed with a six-line extension file, HTTPS that nobody trusts, trust in curl and in Firefox, a Go client with its own root pool plus the handshake in plain text, and finally the three failures on purpose. Five-minute break, then step 0.

    Step 0

    Hello over HTTP

    10 min

    The server for the afternoon is ten lines of Go and stays that way; only one line changes in step 3. Create a second file also called main.go, in the top https-lab folder next to go.mod, not inside ready/:

    package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Hello over %s, encrypted: %v\n", r.Proto, r.TLS != nil)
	})
	log.Fatal(http.ListenAndServe(":8080", nil))
}

    It answers every request with the protocol it arrived on and whether the connection was encrypted (r.TLS is nil for plain HTTP). Run it in your first terminal, then ask for the page from the second:

    go run .
curl http://localhost:8080

    Checkpoint 0

    curl prints Hello over HTTP/1.1, encrypted: false, and Firefox shows the same text at http://localhost:8080, with no padlock in the address bar. Leave the server running.

    Step 1

    Be a certificate authority

    10 min

    A certificate authority is a private key and a certificate that says "this public key belongs to me", signed with that same key. Two commands. First the key:

    openssl genrsa -out ca-key.pem 2048

    genrsa makes an RSA private key, 2048 bits long, and writes it to ca-key.pem. .pem is just the text format: base64 between BEGIN and END lines; open it in your editor. This file is the whole authority; anyone who has it can sign anything. Now the certificate:

    openssl req -x509 -new -key ca-key.pem -days 3650 -subj "/CN=My Lab CA" -addext "basicConstraints=critical,CA:TRUE" -out ca.pem

    Flag by flag. req is the subcommand for certificate requests; -x509 says "do not make a request, make a certificate directly", which is only possible when you sign it yourself. -new -key ca-key.pem: a fresh certificate for this key. -days 3650: valid ten years. -subj "/CN=My Lab CA": the name inside it, a Common Name and nothing else. -addext adds one extension: this certificate may sign other certificates. Read the result back:

    openssl x509 -in ca.pem -text -noout

    x509 is the subcommand for certificates, -text prints it as a human would want to read it, -noout suppresses the base64 blob at the end. Find these lines: Issuer: CN = My Lab CA and Subject: CN = My Lab CA are the same, which is what self-signed means. Not After is ten years from now. Public-Key: (2048 bit). And under X509v3 extensions, X509v3 Basic Constraints: critical followed by CA:TRUE.

    Checkpoint 1

    ca-key.pem and ca.pem exist. The printout shows Issuer equal to Subject, a Not After in 2036, and CA:TRUE. (macOS prints the names without spaces, Issuer: CN=My Lab CA; same thing.)

    Talk about it: which of the two files would you put on a web page? (ca.pem: it contains only the public key and the name.) Which one goes in a safe? Who signed the CA's certificate, and why should anyone believe it? (Nobody yet. That is step 4.)

    Common mistakes: in Git Bash the -subj argument becomes a Windows path and openssl complains about the subject; use PowerShell. On macOS the key file starts with BEGIN RSA PRIVATE KEY instead of BEGIN PRIVATE KEY; both are fine.

    Step 2

    A certificate for localhost

    15 min

    The server needs its own key, and a certificate for the name localhost signed by the CA. A server never signs its own certificate; it makes a request, and the CA signs that. Key and request in one command:

    openssl req -new -newkey rsa:2048 -nodes -keyout server-key.pem -subj "/CN=localhost" -out server.csr

    -newkey rsa:2048 makes a new key and -keyout says where to put it; -nodes ("no DES") means do not encrypt the key file with a passphrase, because a server has to start without a human typing one. -subj "/CN=localhost" is the name, and -out server.csr is the certificate signing request: the public key plus the name, signed with the server's own key to prove it holds it. It is not a certificate yet; nobody the browser trusts has signed anything. The dots and pluses it prints are the key generation.

    Before the CA signs it, write down what kind of certificate this should be. Browsers ignore the Common Name and look only at the Subject Alternative Name, so the name has to appear there; the rest says "not a CA, for a TLS server". Save this as server.ext:

    basicConstraints = CA:FALSE
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer
keyUsage = digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:localhost

    Now sign. This is the one moment the CA's private key is used:

    openssl x509 -req -in server.csr -CA ca.pem -CAkey ca-key.pem -CAcreateserial -days 365 -extfile server.ext -out server.pem

    x509 -req: the input is a request, not a certificate. -CA and -CAkey: sign with this authority. -CAcreateserial: every certificate a CA issues needs a unique serial number, and this makes the file ca.srl that keeps track. -days 365: one year, which is more than public CAs give now: since March 2026 the CA/Browser Forum caps public certificates at 200 days, dropping to 100 in 2027 and 47 in 2029. -extfile server.ext: add those six extensions. Then ask openssl to check the chain, exactly as a browser would except for the name:

    openssl verify -CAfile ca.pem server.pem

    Checkpoint 2

    The sign command printed Certificate request self-signature ok and subject=CN = localhost (macOS: just Signature ok and subject=/CN=localhost); openssl verify prints server.pem: OK. The folder now has server-key.pem, server.csr, server.ext, server.pem and ca.srl.

    Talk about it: run openssl x509 -in server.pem -text -noout and compare with the CA's: Issuer is now My Lab CA, Subject is localhost, and the extensions block is your six lines, with DNS:localhost under Subject Alternative Name. Which file did the CA never see? (server-key.pem. A CA signs public keys; it never needs the private one.)

    Common mistakes: server.ext saved as server.ext.txt (Windows hides extensions); -extfile forgotten, which produces a certificate with no SAN that every browser rejects; running the sign command in a different folder from ca.pem.

    Step 3

    HTTPS, and nobody trusts you

    10 min

    Stop the server with Ctrl-C and change the last line of main.go so it reads:

    	log.Fatal(http.ListenAndServeTLS(":8443", "server.pem", "server-key.pem", nil))

    One word and two file names: ListenAndServeTLS takes the certificate and the private key and does everything else. Port 8443 is the usual "HTTPS while developing" port. Start it and ask curl for the page, this time with an https:// address:

    go run .
curl https://localhost:8443

    curl refuses, with exit code 60 and a message that, on Linux, reads curl: (60) SSL certificate problem: unable to get local issuer certificate. (macOS says the same; Windows says schannel: SEC_E_UNTRUSTED_ROOT (0x80090325) - The certificate chain was issued by an authority that is not trusted.) curl received a certificate for localhost, signed by My Lab CA, and has never heard of My Lab CA. Now Firefox: open https://localhost:8443.

    Checkpoint 3

    curl fails with exit code 60 and a message naming an untrusted authority. Firefox shows "Warning: Potential Security Risk Ahead" and, under Advanced, the error code SEC_ERROR_UNKNOWN_ISSUER. In the server's terminal, a line like http: TLS handshake error from 127.0.0.1:… appeared for each attempt. Do not click "Accept the Risk"; the next step does it properly.

    Talk about it: try curl http://localhost:8443 (plain http, TLS port). The server answers Client sent an HTTP request to an HTTPS server.: it noticed the first bytes were not a TLS handshake. Is anything wrong with the certificate? (No. Every check would pass except the first: the signer is unknown.)

    Do not

    Do not "fix" this with curl -k or by clicking through the warning. Both mean "encrypt to whoever answers", which is the man-in-the-middle's favourite setting. The whole point of the next step is that trust is a decision you make once, about a CA, not per site.

    Step 4

    Trust: curl, then Firefox

    10 min

    Nothing about the server changes in this step. What changes is the client's list of authorities. For curl that list is a file, and --cacert replaces it with your own:

    curl --cacert ca.pem https://localhost:8443

    It prints Hello over HTTP/2.0, encrypted: true. Two things changed at once: encrypted is true because r.TLS is set, and the protocol became HTTP/2, which Go turns on automatically for TLS servers and curl asks for during the handshake.

    Now the browser. Firefox keeps its own list, and you can add to it without an administrator password on every operating system. Open Firefox's Settings, choose Privacy & Security, scroll to Certificates and press View Certificates…. In the Certificate Manager pick the Authorities tab, press Import…, choose ca.pem from your https-lab folder, tick Trust this CA to identify websites, and OK. "My Lab CA" now appears in the list, under its own heading. Reload https://localhost:8443.

    Checkpoint 4

    curl with --cacert prints the page with encrypted: true. Firefox shows the page with a padlock; clicking the padlock says "Connection secure", and "More information" shows the certificate for localhost verified by My Lab CA.

    Talk about it: the server did not restart and the certificate did not change, yet the warning is gone. Where does the difference live? (In Firefox's profile, in a list of roots.) Firefox on Windows and macOS also trusts whatever is in the operating system's store, so importing into Keychain or certmgr would have worked too, for Chrome and Safari as well; it needs a password and is different on each OS, which is why the lab uses Firefox's own list.

    Common mistakes: importing into the Your Certificates or Servers tab instead of Authorities; forgetting the "identify websites" tick, in which case the CA is listed but the warning stays; a private window, where exceptions are temporary.

    Step 5

    Trust as code, and the handshake in plain text

    15 min

    A program that talks to a server has the same decision to make, and in Go it is explicit: a CertPool is the list of roots, and you can build one containing exactly one certificate. Make a folder client inside https-lab and create client/main.go:

    package main

import (
	"crypto/tls"
	"crypto/x509"
	"log"
	"net/http"
	"os"
)

func main() {
	ca, _ := os.ReadFile("ca.pem")
	pool := x509.NewCertPool()
	pool.AppendCertsFromPEM(ca)
	tr := &http.Transport{TLSClientConfig: &tls.Config{RootCAs: pool}}
	resp, err := (&http.Client{Transport: tr}).Get("https://localhost:8443/")
	if err != nil {
		log.Fatal(err)
	}
	resp.Write(os.Stdout)
}

    Read it as four sentences. Read ca.pem. Make an empty pool and put the CA in it. Make an HTTP transport whose TLS configuration uses that pool as its only roots. Get the page and print the whole response, headers included. Run it from https-lab, so that ca.pem is in the current folder:

    go run ./client

    Now watch the handshake itself. s_client is openssl's "be a TLS client and narrate" tool:

    openssl s_client -connect localhost:8443 -CAfile ca.pem

    It stops with the connection open, waiting for you to type a request; press Ctrl-C. Read upwards from the bottom. Verify return code: 0 (ok) is the verdict (OpenSSL 3 prints it twice, once more inside a Post-Handshake New Session Ticket block that arrives after the handshake). New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256 is what was negotiated. Near the top, Certificate chain lists what the server sent: 0 s:CN = localhost with i:CN = My Lab CA (macOS: 0 s:/CN=localhost), the subject and the issuer of the one certificate in the chain, and above it two depth= lines showing the verifier walking from the CA down to the server. (OpenSSL 3.0 prints a harmless Can't use SSL_get_servername first; ignore it.)

    Checkpoint 5

    The Go client prints HTTP/1.1 200 OK, a few headers, and Hello over HTTP/1.1, encrypted: true. s_client shows Verify return code: 0 (ok) and TLSv1.3 (macOS names the cipher AEAD-AES128-GCM-SHA256 instead of TLS_AES_128_GCM_SHA256; the verdict line is the same).

    Talk about it: change RootCAs: pool to RootCAs: nil, which means "use the operating system's roots", and run again: tls: failed to verify certificate: x509: certificate signed by unknown authority. That is the Go spelling of step 3. Change it back. Why did the Go client get HTTP/1.1 when curl got HTTP/2? (A transport with its own TLS configuration does not enable HTTP/2 unless you set ForceAttemptHTTP2: true; Go's default transport does.) Run s_client without -CAfile and find Verify return code: 21 (unable to verify the first certificate).

    Common mistakes: running the client from inside the client folder, where ca.pem does not exist, which shows up as the "unknown authority" error because the pool is empty; the old server from step 0 still running on 8080 (harmless) or a second copy on 8443 (bind: address already in use).

    Step 6

    What the padlock promises

    10 min

    Three experiments, each making one of the three checks fail on purpose. The first needs no new files at all: the same server, the same CA, a different name in the address bar.

    curl --cacert ca.pem https://127.0.0.1:8443

    curl: (60) SSL: no alternative certificate subject name matches target host name '127.0.0.1'. In Firefox, https://127.0.0.1:8443 gives SSL_ERROR_BAD_CERT_DOMAIN. The chain is perfect; the certificate simply is not about that name. Trust is per name, and the name comes from the address bar, not from the server.

    The second experiment needs a certificate that has already expired. openssl on macOS will not sign one with zero days, so the CA does this one in Go, which also shows that a CA is nothing more than a program with a private key. Make a folder sign and paste this as sign/main.go; read the tmpl block, which is server.ext as a Go struct with the dates moved into the past:

    // The same signing step as "openssl x509 -req -CA ca.pem ...", written in Go,
// except that the certificate it issues expired yesterday. Writes expired.pem.
// Run from the https-lab folder:  go run ./sign
package main

import (
	"crypto"
	"crypto/rand"
	"crypto/x509"
	"crypto/x509/pkix"
	"encoding/pem"
	"log"
	"math/big"
	"os"
	"time"
)

// readPEM returns the bytes inside the first PEM block of a file.
func readPEM(name string) []byte {
	raw, err := os.ReadFile(name)
	if err != nil {
		log.Fatal(err)
	}
	block, _ := pem.Decode(raw)
	if block == nil {
		log.Fatalf("%s: no PEM block found", name)
	}
	return block.Bytes
}

// readKey accepts both key formats openssl produces:
// "BEGIN PRIVATE KEY" (OpenSSL 3, PKCS#8) and "BEGIN RSA PRIVATE KEY" (LibreSSL on macOS, PKCS#1).
func readKey(name string) crypto.Signer {
	der := readPEM(name)
	if key, err := x509.ParsePKCS8PrivateKey(der); err == nil {
		return key.(crypto.Signer)
	}
	key, err := x509.ParsePKCS1PrivateKey(der)
	if err != nil {
		log.Fatal(err)
	}
	return key
}

func main() {
	ca, err := x509.ParseCertificate(readPEM("ca.pem"))
	if err != nil {
		log.Fatal(err)
	}
	caKey := readKey("ca-key.pem")
	serverKey := readKey("server-key.pem")

	// This struct is server.ext, as Go sees it, plus dates in the past.
	tmpl := &x509.Certificate{
		SerialNumber: big.NewInt(time.Now().Unix()),
		Subject:      pkix.Name{CommonName: "localhost"},
		DNSNames:     []string{"localhost"},
		NotBefore:    time.Now().Add(-48 * time.Hour),
		NotAfter:     time.Now().Add(-24 * time.Hour),
		KeyUsage:     x509.KeyUsageDigitalSignature | x509.KeyUsageKeyEncipherment,
		ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
	}
	der, err := x509.CreateCertificate(rand.Reader, tmpl, ca, serverKey.Public(), caKey)
	if err != nil {
		log.Fatal(err)
	}
	out, err := os.Create("expired.pem")
	if err != nil {
		log.Fatal(err)
	}
	pem.Encode(out, &pem.Block{Type: "CERTIFICATE", Bytes: der})
	out.Close()
	log.Println("wrote expired.pem, expired on", tmpl.NotAfter.Format(time.RFC1123))
}

    go run .

    The third experiment is a conversation, not a command. Everything the CA promised held: right key, right name, right dates, padlock. Did the CA check that the server is honest? That its code has no bugs? That it is the site you meant to visit rather than one with a similar name? No. A public CA checks that whoever asked for the certificate controls the name, and nothing else.

    Checkpoint 6

    Three distinct failures seen and named: name mismatch for 127.0.0.1, expiry for expired.pem, and (from step 3) unknown issuer. The server is back on server.pem and curl with --cacert prints the page again.

    Talk about it: openssl verify -CAfile ca.pem -attime 2000000000 server.pem pretends it is the year 2033 and reports certificate has expired for your good certificate: expiry is a property of the moment, not the file. Why are public CAs cutting lifetimes from 200 days today to 47 by 2029? (A stolen key or a sold domain stops mattering on its own, sooner.) What would you have to steal from this folder to impersonate localhost to someone who trusts My Lab CA? (server-key.pem, or ca-key.pem, which is worse.)

    Common mistakes: forgetting to restart the server after editing main.go, so the "expired" test still succeeds; running go run ./sign from the wrong folder, so it cannot find ca.pem.

    Step 7

    Wrap-up and stretch goals

    10 min

    Bring the room back together for five minutes, then let the fast students pick a stretch goal.

    Wrap-up points

    • A certificate is a public key, a name, two dates and a signature. It contains no secrets; the private key never leaves the machine it was made on.
    • Trust is a list. curl has a file, Firefox has a profile, Go has a CertPool, the OS has a store. "Untrusted" means "not on my list", never "broken".
    • Three checks, three errors: unknown issuer, wrong name, expired. When you see a TLS error in the wild, ask which of the three it is before doing anything else.
    • The padlock is about the pipe. It says nothing about the person at the other end. Say it twice.

    Stretch goals (pick one)

    • Mutual TLS. Issue a certificate for /CN=alice the same way as the server's, with an ext file that says extendedKeyUsage = clientAuth. Make the server demand it: build an http.Server with TLSConfig: &tls.Config{ClientAuth: tls.RequireAndVerifyClientCert, ClientCAs: pool} (the same pool as the client) and greet the client by the Subject.CommonName of r.TLS.PeerCertificates[0]. curl without a certificate now fails with "certificate required"; curl --cacert ca.pem --cert alice.pem --key alice-key.pem https://localhost:8443 prints Hello alice. This is how services authenticate to each other inside a cluster.
    • Strict transport. Add w.Header().Set("Strict-Transport-Security", "max-age=31536000") to the handler. Firefox will silently upgrade http://localhost:8443 to HTTPS for a year afterwards (clear it in the site's page info when you are done). Real sites send this on every response.
    • No openssl at all. Turn sign/main.go into a program that makes the CA key, the CA certificate and the server certificate itself, using rsa.GenerateKey and two calls to x509.CreateCertificate. Nothing on this page needed openssl except habit.
    • The real thing. Read golang.org/x/crypto/acme/autocert: autocert.NewListener("example.com") handed to http.Serve gets a Let's Encrypt certificate for a name you own and renews it. It cannot work for localhost, and it needs port 443 reachable from the internet; read the ACME challenge it performs and match it to slide 9.
    • Chrome and Safari. Import ca.pem into the operating system's store (Keychain Access on macOS, certmgr.msc Trusted Root Certification Authorities on Windows, certutil into ~/.pki/nssdb on Linux) and see the padlock there too. Then remove it, and explain to a neighbour why a corporate laptop with an extra root in that store can read all its owner's HTTPS traffic.
    • Read a real chain. openssl s_client -connect go.dev:443 -showcerts, then read the two or three certificates it prints with openssl x509 -text. Find the intermediate, the validity period, the SAN list, and which root in your system's store the chain ends at.

package main

import (
	"crypto"
	"crypto/rand"
	"crypto/x509"
	"crypto/x509/pkix"
	"encoding/pem"
	"log"
	"math/big"
	"os"
	"time"
)

// readPEM returns the bytes inside the first PEM block of a file.
func readPEM(name string) []byte {
	raw, err := os.ReadFile(name)
	if err != nil {
		log.Fatal(err)
	}
	block, _ := pem.Decode(raw)
	if block == nil {
		log.Fatalf("%s: no PEM block found", name)
	}
	return block.Bytes
}

// readKey accepts both key formats openssl produces:
// "BEGIN PRIVATE KEY" (OpenSSL 3, PKCS#8) and "BEGIN RSA PRIVATE KEY" (LibreSSL on macOS, PKCS#1).
func readKey(name string) crypto.Signer {
	der := readPEM(name)
	if key, err := x509.ParsePKCS8PrivateKey(der); err == nil {
		return key.(crypto.Signer)
	}
	key, err := x509.ParsePKCS1PrivateKey(der)
	if err != nil {
		log.Fatal(err)
	}
	return key
}

func main() {
	ca, err := x509.ParseCertificate(readPEM("ca.pem"))
	if err != nil {
		log.Fatal(err)
	}
	caKey := readKey("ca-key.pem")
	serverKey := readKey("server-key.pem")

	// This struct is server.ext, as Go sees it, plus dates in the past.
	tmpl := &x509.Certificate{
		SerialNumber: big.NewInt(time.Now().Unix()),
		Subject:      pkix.Name{CommonName: "localhost"},
		DNSNames:     []string{"localhost"},
		NotBefore:    time.Now().Add(-48 * time.Hour),
		NotAfter:     time.Now().Add(-24 * time.Hour),
		KeyUsage:     x509.KeyUsageDigitalSignature | x509.KeyUsageKeyEncipherment,
		ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
	}
	der, err := x509.CreateCertificate(rand.Reader, tmpl, ca, serverKey.Public(), caKey)
	if err != nil {
		log.Fatal(err)
	}
	out, err := os.Create("expired.pem")
	if err != nil {
		log.Fatal(err)
	}
	pem.Encode(out, &pem.Block{Type: "CERTIFICATE", Bytes: der})
	out.Close()
	log.Println("wrote expired.pem, expired on", tmpl.NotAfter.Format(time.RFC1123))
}

    Instructor notes

    Timing reality

    Step 0 gets ten minutes because its twelve lines of Go are typed cold; do not let it become a Go lesson. Step 2 is the slow one: two long commands typed flag by flag, plus the ext file, and it is where typos live (a missing quote, -extfile forgotten). Budget the full fifteen minutes and do not explain -CAcreateserial twice. Step 4's Firefox import takes two minutes for people who have seen it and eight for people who have not; do it on the projector once, slowly, before anyone starts. Step 6 has the least typing and the most talking, which is why it has ten minutes; if you are behind after step 5, drop the -attime aside and the third experiment becomes the wrap-up.

    Things students ask

    • "Why does curl's error differ from my neighbour's?" Different TLS libraries. Linux and macOS curl (OpenSSL / LibreSSL) say unable to get local issuer certificate; Windows curl uses Schannel and says SEC_E_UNTRUSTED_ROOT (0x80090325) - The certificate chain was issued by an authority that is not trusted (with --cacert it switches to its own validation and a failure there reads CertGetCertificateChain trust error …). Same check, same exit code 60. --cacert works with all of them; on Windows it has since curl 7.60.
    • "Why is HTTP/2 there for curl but not for my Go client?" Go's server enables HTTP/2 automatically over TLS; curl asks for it via ALPN. A Go Transport with a custom TLSClientConfig does not attempt HTTP/2 unless ForceAttemptHTTP2 is set. Nothing to do with certificates.
    • "Can I use this CA for my real project?" For local development, yes: that is exactly what the popular mkcert tool does, with the OS-store import automated. For anything reachable from the internet, use Let's Encrypt; nobody else's browser has your CA.
    • "What does the server log mean?" Each refused connection leaves a http: TLS handshake error line: remote error: tls: bad certificate from the Go client, local error: tls: bad record MAC from curl (the way Go reports the client's encrypted "unknown CA" alert), and client sent an HTTP request to an HTTPS server for plain HTTP. All three are the client hanging up, not the server failing.
    • "My Mac prints something slightly different." LibreSSL (macOS) writes names in slash form and has older strings: step 1 shows Issuer: CN=My Lab CA, step 2's sign command says only Signature ok with subject=/CN=localhost, and step 5's s_client lists 0 s:/CN=localhost and the cipher as AEAD-AES128-GCM-SHA256. The verdicts (server.pem: OK, Verify return code: 0 (ok)) are identical. From LibreSSL source, not run in the authoring environment.
    • "Why RSA and not elliptic curves?" Habit and readability of the -text output. openssl ecparam -name prime256v1 -genkey -noout -out ca-key.pem works everywhere on this page; the server key would use the same, and sign.go already accepts either.
    • "Why does macOS need -addext?" It does not hurt anywhere. LibreSSL's default config has no v3_ca section, so without it the CA certificate would lack CA:TRUE and every verifier would reject the chain with "certificate is not a CA". OpenSSL on Linux and Windows adds it from the stock config, so on those the flag is redundant but harmless.
