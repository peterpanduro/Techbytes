TechBytes · Workshop 8

Logs and Metrics You Can Actually Use

“Checkout is slow.” Twelve servers. Which part?

Two questions, two tools

a log answers

“What happened to this request?”

one record per event · wide · costs per event

a metric answers

“How is the system doing?”

a few numbers · always current · almost free

You cannot grep a thousand pods. You need both.

A log line is data, not prose

// prose: a human reads it
2026/09/22 12:38 GET /checkout 504 2.301s

// data: a program filters it
{"time":"2026-09-22T12:38:29Z",
 "level":"INFO","msg":"request",
 "method":"GET","path":"/checkout",
 "status":504,"duration_ms":2301,
 "request_id":"c11e5f84"}
log/slogin the standard library
select(.status >= 500)no regular expression

Name every field. Stamp an id on it.

A metric is a number with labels

http_requests_total{path="/checkout",status="504"} 17

counter

only goes up

ask for its rate later

labels

how you slice

path, status · never a user id

Every distinct label value is a new time series.

PromQL in three lines

rate(http_requests_total[1m])

sum by (path) (rate(http_requests_total[1m]))

histogram_quantile(0.95,
  sum by (path, le) (rate(http_request_duration_seconds_bucket[1m])))

How fast is it climbing · add up, keep one label · read off the 95th percentile.
