Workshop 8

At a glance

OutcomeEvery student leaves with a Go API that writes one JSON log line per request (method, path, status, duration, request id) and serves a Prometheus /metrics page they wrote themselves, a Compose file that runs it next to Prometheus and Grafana, a two-panel dashboard that shows which endpoint is slow, one alert rule, and the habit of asking a metric "where?" and a log "why?".
Why this topicThe first week on any real system is spent staring at a dashboard someone else built and a log nobody can search. Students have never seen where those numbers come from. Writing the /metrics page by hand, thirty lines, removes the magic for good: a metric is a number with labels that something fetches every few seconds, and a histogram is six counters. After that, every monitoring tool is the same tool.
ConceptsStructured logs and why a log line is a record, not a sentence; request ids; counters and histograms; labels and cardinality; the Prometheus text exposition format; pull-based scraping and the scrape interval; rate(), sum by, and histogram_quantile(); why p95 is not the average and why a bucketed p95 is an estimate; dashboards as questions; alert rules; the difference between "where" (metrics) and "why" (logs), and what traces would add.
Assumed knowledgeWorkshop 1 (containers, ports) and workshop 6 (Compose, a service finds another by name). Can read a short Go program; workshops 3, 4 and 6 provided that. No Prometheus, Grafana or statistics knowledge.

The talk: where, then why

The single idea to land: a log line answers "what happened to this request", a metric answers "how is the system doing", and you need both, because you cannot grep a thousand pods. Metrics find the where; logs find the why; a request id connects them.

  1. 1"It's slow." Which part?1 min Title slide. A customer says checkout is slow. You have twelve servers, a log file on each, and a hunch. Ask what the room would do: ssh in and tail a log? That works for one server. The afternoon is about what works for a thousand.
  2. 2Two questions, two tools2 min "What happened to this request?" is a log question: one record per event, with everything you knew at the time. "How is the system doing?" is a metric question: a few numbers, updated constantly, cheap enough to keep forever. Logs are wide and expensive per event; metrics are narrow and free. A system that has only one of them has a blind spot. Today the API gets both.
  3. 3A log line is data, not prose2 min Show log.Printf("%s %s %d %v", …) next to the JSON line the lab produces: method, path, status, duration in milliseconds, request id. The first is a sentence a human parses with their eyes; the second is a record a program filters with status >= 500. Go's log/slog writes the second form with one line of setup. The request id is a random tag stamped on the request at the door so that every line about it can be found again.
  4. 4A metric is a number with labels1 min http_requests_total{path="/checkout",status="504"} 17. A name, some labels, a value. A counter only goes up; you ask for its rate later. Labels are how you slice: by path, by status. Never a user id or a request id as a label: every distinct value is a new time series, and you would make millions.
  5. 5Histograms, and why p95 is not the average2 min The widget. A histogram is a row of counters with an upper bound each: how many requests took at most 0.1 s, at most 0.25, 0.5, 1, 2.5, anything. Checkout takes 300 ms, except one call in ten that takes two seconds longer. The average settles at half a second and looks fine; the p95 sits above two seconds because one customer in ten is waiting. Averages hide tails; percentiles show them. And a percentile computed from buckets is an estimate: Prometheus will say about 1.9 s where the truth is 2.3, because it interpolates inside the 1-to-2.5 bucket.
  6. 6Pull, not push1 min The API does not send anything anywhere. It serves a plain text page at /metrics with the current counters, and Prometheus fetches that page every five seconds and stores each number with a timestamp. Grafana asks Prometheus questions and draws the answers. Three boxes, two arrows, and the API knows nothing about either of the others. That is why the lab can write the /metrics page by hand in thirty lines.
  7. 7PromQL in three lines2 min rate(http_requests_total[1m]): how fast is the counter climbing, per second, over the last minute. Wrap it in sum by (path) to collapse the status label and get requests per second per endpoint. And histogram_quantile(0.95, sum by (le) (rate(…_bucket[1m]))): take the bucket counters, turn each into a rate, add them up keeping only the bucket label, and read off the 95th percentile. Three shapes cover most dashboards you will ever build.
  8. 8The graph finds the where1 min Two panels: requests per second by path, p95 latency by path. Two lines sit on the floor; one sits at two seconds. You have found the slow endpoint without reading a single log line and without knowing what the code does. That is the point of a metric: it is cheap enough to look at all the time, so you notice before the customer does.
  9. 9The log finds the why1 min The graph cannot tell you why checkout is slow. Take one slow log line, copy its request id, filter the log for it, and there is a second line from inside the handler: "payment provider timed out". Metrics tell you where to look; logs tell you what you find there; the id is the join key. In step 6 you also write the alert rule so that next time nobody has to be watching the graph.
  10. 10What we are not doing1 min Traces: the third pillar, one record per request that crosses several services; OpenTelemetry plus a collector is a workshop of its own. The Prometheus client library, which does what our thirty lines do and much more; we write it by hand once so the library is never magic. Log levels and sampling, and SLOs. All four are stretch goals on the page.
  11. 11The next 90 minutes1 min Seven steps: run the API and a load generator, switch the log to JSON and filter it, write the metrics page, bring up Prometheus and Grafana with Compose, ask three PromQL questions, build the two-panel dashboard and find the slow endpoint, then correlate with a request id and add the alert. Five-minute break, then step 0.

Step 0

Run the API and the load generator

8 min

The app for the afternoon is a 47-line Go web server with three endpoints. Create these two files in obs-lab and read main.go once, top to bottom. wrap runs around every handler, times it and prints one line; the recorder exists only to remember the status code. /checkout is the interesting one: it always sleeps 300 ms, and one call in ten hangs for two more seconds and answers 504. That is the "payment provider" we will find later without being told.

go.mod

module obs

go 1.24

main.go

package main

import (
	"fmt"
	"log"
	"math/rand/v2"
	"net/http"
	"time"
)

// recorder remembers the status code a handler wrote, so we can log it.
type recorder struct {
	http.ResponseWriter
	status int
}

func (r *recorder) WriteHeader(code int) { r.status = code; r.ResponseWriter.WriteHeader(code) }

// wrap runs around every handler: time it, then log one line.
func wrap(h http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &recorder{w, 200}
		h(rec, r)
		log.Printf("%s %s %d %v", r.Method, r.URL.Path, rec.status, time.Since(start))
	}
}

func main() {
	http.HandleFunc("/", wrap(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello")
	}))
	http.HandleFunc("/products", wrap(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, `["socks","hat","mug"]`)
	}))
	http.HandleFunc("/checkout", wrap(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(300 * time.Millisecond) // the payment provider is never fast
		if rand.IntN(10) == 0 {            // and one call in ten hangs
			time.Sleep(2 * time.Second)
			http.Error(w, "payment provider timed out", http.StatusGatewayTimeout)
			return
		}
		fmt.Fprintln(w, "paid")
	}))
	log.Println("listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}

Now the load generator, a Deno script that hits the three endpoints at random from three loops, forever. Paste it as load.ts:

// Load generator: three loops hitting the API at random, forever. Ctrl-C stops it.
const base = "http://localhost:8080";
const paths = ["/", "/products", "/products", "/checkout"];
async function loop(n: number) {
  while (true) {
    const path = paths[Math.floor(Math.random() * paths.length)];
    const t = performance.now();
    const res = await fetch(base + path);
    await res.text();
    console.log(`loop ${n}  ${res.status}  ${path}  ${Math.round(performance.now() - t)} ms`);
    await new Promise((r) => setTimeout(r, 100));
  }
}
await Promise.all([1, 2, 3].map(loop));

Terminal 1 runs the API, terminal 2 the load, terminal 3 is yours:

go run .
deno run --allow-net load.ts
curl -i localhost:8080/checkout

Step 1

Logs are data: log/slog and a filter

12 min

The line terminal 1 prints is a sentence. Try to answer "how many 504s in the last minute?" from it and you are writing a regular expression. Go's log/slog package writes the same information as JSON: one record per line, every field named. Three edits to main.go. First, two imports:

	"log/slog"
	"os"

Second, in wrap, replace the rec :=, h(rec, r) and log.Printf lines with these six. The request id is eight random hex digits, stamped onto the request as a header so that anything deeper in the program can find it:

		id := fmt.Sprintf("%08x", rand.Uint32())
		r.Header.Set("X-Request-Id", id)
		rec := &recorder{w, 200}
		h(rec, r)
		slog.Info("request", "method", r.Method, "path", r.URL.Path, "status", rec.status,
			"duration_ms", time.Since(start).Milliseconds(), "request_id", id)

Third, the first line of main makes the JSON handler the default logger. It also captures the old log package, so the "listening" line turns into JSON too without being touched:

	slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stdout, nil)))

Restart the API (Ctrl-C in terminal 1, go run . again). Every line is now a JSON object. Now filter it. Paste this as filter.ts; it reads lines from standard input, parses each one, and prints the ones with status >= 500:

// Reads JSON log lines on stdin. Prints the ones with status >= 500,
// or, given an argument, the ones containing that text (a request id).
import { createInterface } from "node:readline";
import process from "node:process";
const want = Deno.args[0];
for await (const line of createInterface({ input: process.stdin })) {
  try {
    const rec = JSON.parse(line);
    if (want ? line.includes(want) : rec.status >= 500) console.log(line);
  } catch {
    // not JSON (a startup line, a panic): ignore
  }
}
go run . | deno run filter.ts

If you installed jq, go run . | jq -c 'select(.status >= 500)' does the same thing. Either way the point is the same: nobody wrote a regular expression, because a log line is a record.

Checkpoint 1

Terminal 1 shows only the failures, roughly one every few seconds, each a full JSON line. Nothing with status 200 gets through.

{"time":"2026-09-22T12:38:29.730449449+02:00","level":"INFO","msg":"request","method":"GET","path":"/checkout","status":504,"duration_ms":2301,"request_id":"c11e5f84"}

Common mistakes: log.Printf left in place next to slog.Info (two lines per request, one of them prose); slog.SetDefault placed after the handlers are registered (harmless, it still works, but say why it is at the top: everything after it logs JSON); running the filter on terminal 2's output instead of terminal 1's.

Talk about it: why duration_ms as an integer rather than 300.5ms as a string? (You can compare and sum a number.) What would you put in the line that is not there yet? (User id, upstream latency, the error.) What should never go in a log line? (Passwords, tokens, card numbers; logs are copied everywhere.)

Step 2

Metrics by hand: a counter, a histogram, /metrics

20 min

A log line per request is the right thing for "what happened", and the wrong thing for "how are we doing": to answer "requests per second by endpoint" you would re-read the whole log. A metric keeps the answer up to date instead. Two metrics today: a counter of requests by path and status, and a histogram of request durations by path. We write them with maps and fmt, no library, so that the format is never magic. Create metrics.go and paste its top: the imports and the four variables. buckets is the histogram's upper bounds in seconds, ending in +Inf.

package main

import (
	"fmt"
	"math"
	"net/http"
	"strings"
	"sync"
)

// One counter (requests by path and status) and one histogram (seconds by path),
// kept in plain maps and printed in the Prometheus text format on /metrics.
var (
	mu       sync.Mutex
	buckets  = []float64{0.1, 0.25, 0.5, 1, 2.5, math.Inf(1)}
	requests = map[string]int{}   // "path status" -> count
	observed = map[string][]int{} // path -> cumulative count per bucket
	sums     = map[string]float64{}
)

Now type the two functions under it. observe is called once per request: it bumps the counter for this path and status, then bumps every bucket whose bound the duration fits under (so the buckets are cumulative, which is what Prometheus expects), and adds to the sum. metrics prints everything in the Prometheus text format: a TYPE line, then one line per label combination, name{labels} value.

func observe(path string, status int, seconds float64) {
	mu.Lock()
	defer mu.Unlock()
	requests[fmt.Sprintf("%s %d", path, status)]++
	if observed[path] == nil {
		observed[path] = make([]int, len(buckets))
	}
	for i, le := range buckets {
		if seconds <= le {
			observed[path][i]++
		}
	}
	sums[path] += seconds
}

func metrics(w http.ResponseWriter, r *http.Request) {
	mu.Lock()
	defer mu.Unlock()
	w.Header().Set("Content-Type", "text/plain; version=0.0.4")
	fmt.Fprintln(w, "# TYPE http_requests_total counter")
	for key, n := range requests {
		path, status, _ := strings.Cut(key, " ")
		fmt.Fprintf(w, "http_requests_total{path=%q,status=%q} %d\n", path, status, n)
	}
	fmt.Fprintln(w, "# TYPE http_request_duration_seconds histogram")
	for path, counts := range observed {
		for i, le := range buckets {
			fmt.Fprintf(w, "http_request_duration_seconds_bucket{path=%q,le=%q} %d\n", path, fmt.Sprint(le), counts[i])
		}
		fmt.Fprintf(w, "http_request_duration_seconds_sum{path=%q} %g\n", path, sums[path])
		fmt.Fprintf(w, "http_request_duration_seconds_count{path=%q} %d\n", path, counts[len(buckets)-1])
	}
}

Two lines in main.go connect it: the observation at the end of wrap, after slog.Info, and the route in main before the "listening" line. /metrics is deliberately not wrapped, so scraping it does not count as traffic:

		observe(r.URL.Path, rec.status, time.Since(start).Seconds())
	http.HandleFunc("/metrics", metrics)

Restart the API, let the load run for half a minute, then look at the page:

curl localhost:8080/metrics

Something close to this, with your own numbers. Four counter lines, then for each path six _bucket lines whose values never decrease from top to bottom, a _sum and a _count. Talk about it: read the checkout histogram out loud: 128 requests, 111 under half a second, 17 between one and 2.5 seconds. What is the average? (72.5 s / 128 = 0.57 s.) What is the p95? (The 95th percent mark is request 122 of 128, which is in the 1-to-2.5 bucket; the truth is 2.3 s.) The map order changes between scrapes; why does that not matter? (Each line is self-describing.) Why is the duration in seconds and not milliseconds? (Prometheus convention: base units, always.) What happens to this program if someone requests /a, /b, /c … a million times? (A million time series: the catch-all / handler logs the real path. The fix is r.Pattern, the matched route, instead of r.URL.Path. Not today, but never put an unbounded value in a label.)

Common mistakes: < instead of <= in observe (buckets are "less than or equal", that is what le means); forgetting the +Inf bucket by editing the list (Prometheus rejects the histogram without it); a _count that is not equal to the +Inf bucket.

Step 3

Prometheus scrapes it: prometheus.yml and Compose

12 min

The API serves numbers; Prometheus collects them. It needs to be told what to fetch and how often. Type prometheus.yml; six lines, and every one of them is a real decision:

global:
  scrape_interval: 5s
scrape_configs:
  - job_name: api
    static_configs:
      - targets: ["api:8080"]

scrape_interval: 5s is aggressive (the default is a minute; 15 s is common) so that the graphs move while you watch. The target is api:8080, not localhost: inside Compose, services find each other by name, exactly as in workshop 6, so the API needs to be a service too. Paste the Dockerfile from workshop 1 with one change (COPY *.go, since there are now two files) and a Compose file with three services:

Dockerfile

FROM golang:1.27 AS build
WORKDIR /app
COPY go.mod ./
COPY *.go ./
RUN CGO_ENABLED=0 go build -o server .

FROM scratch
COPY --from=build /app/server /server
CMD ["/server"]

compose.yaml

services:
  api:
    build: .
    ports: ["8080:8080"]

  prometheus:
    image: prom/prometheus:v3.14.0
    ports: ["9090:9090"]
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml

  grafana:
    image: grafana/grafana:13.2.2
    ports: ["3000:3000"]

Stop the go run in terminal 1 (Ctrl-C) so that port 8080 is free; the load generator in terminal 2 can keep running, it will fail for a few seconds and recover. Then bring everything up:

docker compose up -d --build
docker compose ps

Open localhost:9090/targets. Prometheus lists its one target, api:8080, and after a few seconds says UP. Then localhost:9090/query, type http_requests_total in the box and press Execute: the four counter lines from step 2, now as time series that Prometheus has been storing every five seconds.

Checkpoint 3

docker compose ps shows api, prometheus and grafana running. The targets page shows api:8080 as UP with a "last scrape" a few seconds ago. The query http_requests_total returns four series, and running it again returns bigger numbers.

Common mistakes: localhost:8080 as the target (that is Prometheus's own container; the target shows DOWN with "connection refused"); YAML indented with a tab (Prometheus refuses to start; docker compose logs prometheus says so); the old go run still holding port 8080 so api fails to start.

Instructor

Step 4

Three PromQL questions

10 min

Prometheus's query page is where you learn the language, one expression at a time. Switch to the Graph tab for each one. Nothing here is typed into a file; the three expressions are the whole step, and the dashboard in step 5 reuses them unchanged.

rate(http_requests_total[1m])
sum by (path) (rate(http_requests_total[1m]))
histogram_quantile(0.95, sum by (path, le) (rate(http_request_duration_seconds_bucket[1m])))

The first asks: over the last minute, how fast did each counter climb, per second? Four lines, one per path-and-status pair. The second adds them up but keeps path, so the 200s and 504s of /checkout merge into one line: requests per second per endpoint. The third is the one people copy for years: take the six bucket counters per path, turn each into a rate, add them up keeping path and le, and ask for the 95th percentile. Read it inside out and it is three ideas you already have.

Checkpoint 4

Query 1 shows four series: three between about 3 and 6 requests per second and the /checkout 504 series down near 0.3; query 2 shows three lines, /products highest at about 6 per second, the other two about 3 (with our load generator, half the requests go to /products). Query 3 shows / and /products flat at the smallest bucket bound, 0.1, and /checkout at about 1.9 s. Not 2.3: the truth is between the 1 and 2.5 bounds and Prometheus interpolates linearly inside the bucket. Coarser buckets, rougher estimate.

Talk about it: why [1m] and not [5s]? (A rate needs at least two samples in the window; with a 5 s scrape, [1m] holds twelve.) Why does the p95 for the fast endpoints read 0.1 when they take a millisecond? (Everything is in the first bucket, so the best Prometheus can say is "at most 0.1". If you cared about the fast endpoints, you would add smaller buckets.) What does sum by (le) without path give you? (One p95 over all endpoints, which hides checkout inside the fast ones.)

Step 6

Logs find the why, and an alert rule

10 min

The graph says checkout. It cannot say why. That is a log question, and the request id is the join. The API now runs in a container, so its log comes from Compose; the filter from step 1 still applies, and with an argument it prints the lines containing a request id instead:

docker compose logs --no-log-prefix api | deno run filter.ts

Copy the request_id from any 504 line, then ask for everything about it:

docker compose logs --no-log-prefix api | deno run filter.ts c11e5f84

One line comes back: the request record. The why is not in the log yet, because nothing inside the handler logs. Add one line to the slow branch of /checkout, just before http.Error. It reads the id back from the header that wrap set, so the two lines can be joined:

			slog.Warn("payment provider timed out", "request_id", r.Header.Get("X-Request-Id"))

Now the alert, so that next time nobody needs to be watching. Paste alerts.yml: one rule, the step 4 p95 expression, fire when it has been above one second for a minute. The annotation uses Prometheus's template syntax to name the path and the value:

groups:
  - name: api
    rules:
      - alert: CheckoutSlow
        expr: histogram_quantile(0.95, sum by (path, le) (rate(http_request_duration_seconds_bucket[1m]))) > 1
        for: 1m
        labels:
          severity: page
        annotations:
          summary: "p95 latency on {{ $labels.path }} is {{ $value }} s"

Two typed lines tell Prometheus to load it, at the end of prometheus.yml, and one line in compose.yaml, under the Prometheus volumes, mounts the file:

rule_files:
  - alerts.yml
      - ./alerts.yml:/etc/prometheus/alerts.yml
docker compose up -d --build
docker compose logs --no-log-prefix api | deno run filter.ts

The rebuild picks up the warning line; the restart of Prometheus picks up the rule. Take a new 504's request id and filter for it again: two lines this time. Then open localhost:9090/alerts.

Step 7

Wrap-up and stretch goals

6 min

Bring the room back together for three minutes, then let the fast students pick a stretch goal. docker compose down when you leave.

Wrap-up points

  • A log line is a record: name every field, stamp a request id on it, and the log becomes something you query, not something you read.
  • A metric is a number with labels that something fetches every few seconds. A histogram is a row of cumulative counters. You wrote both in thirty lines; every library does the same thing.
  • Averages hide tails. Ask for the p95, and remember that a p95 from buckets is an estimate whose precision is the bucket width.
  • Metrics find the where, logs find the why, the request id is the join. Alerts are the same expression with a threshold and a for.

Stretch goals (pick one)

  • The library. Replace metrics.go with github.com/prometheus/client_golang: promauto.NewCounterVec, promauto.NewHistogramVec, and promhttp.Handler() on /metrics. Compare its output with yours: same names, same lines, plus forty Go-runtime metrics for free. (Needs go get and a network; run it at home if the venue has none.)
  • Traces. The third pillar. Read the OpenTelemetry Go getting-started page, add the SDK and a console exporter, and wrap the checkout handler in a span. Look at what a span carries that a log line does not: a parent, a start and an end. A collector and a UI (Jaeger, Tempo) are the next afternoon.
  • Levels and sampling. Give the handler a slog.Debug line per request and turn it on with slog.HandlerOptions{Level: slog.LevelDebug} only when an environment variable is set. Then log only every tenth 200 but every 5xx: that is sampling, and it is how a busy service keeps its log bill sane.
  • An SLO. "99% of checkouts under one second over 30 days." Write the PromQL for the fraction that met it (_bucket{le="1"} over _count) and compute how many slow requests the month can afford before the objective is broken. That number is an error budget.
  • Alertmanager. Add prom/alertmanager to Compose, point Prometheus at it with an alerting: block, and route the alert to a webhook receiver (a ten-line Deno.serve that prints the JSON). Watch the page arrive.
  • Provision the dashboard. Export the dashboard as JSON from Grafana, mount it under /etc/grafana/provisioning/dashboards with a provider file, docker compose down -v, up, and the dashboard is there before anyone logs in. Dashboards are code too.

package main

import (
	"fmt"
	"log"
	"log/slog"
	"math/rand/v2"
	"net/http"
	"os"
	"time"
)

// recorder remembers the status code a handler wrote, so we can log it.
type recorder struct {
	http.ResponseWriter
	status int
}

func (r *recorder) WriteHeader(code int) { r.status = code; r.ResponseWriter.WriteHeader(code) }

// wrap runs around every handler: time it, log one line, record one observation.
func wrap(h http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		id := fmt.Sprintf("%08x", rand.Uint32())
		r.Header.Set("X-Request-Id", id)
		rec := &recorder{w, 200}
		h(rec, r)
		slog.Info("request", "method", r.Method, "path", r.URL.Path, "status", rec.status,
			"duration_ms", time.Since(start).Milliseconds(), "request_id", id)
		observe(r.URL.Path, rec.status, time.Since(start).Seconds())
	}
}

func main() {
	slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stdout, nil)))
	http.HandleFunc("/", wrap(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello")
	}))
	http.HandleFunc("/products", wrap(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, `["socks","hat","mug"]`)
	}))
	http.HandleFunc("/checkout", wrap(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(300 * time.Millisecond) // the payment provider is never fast
		if rand.IntN(10) == 0 {            // and one call in ten hangs
			time.Sleep(2 * time.Second)
			slog.Warn("payment provider timed out", "request_id", r.Header.Get("X-Request-Id"))
			http.Error(w, "payment provider timed out", http.StatusGatewayTimeout)
			return
		}
		fmt.Fprintln(w, "paid")
	}))
	http.HandleFunc("/metrics", metrics)
	log.Println("listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}
metrics.godownload
package main

import (
	"fmt"
	"math"
	"net/http"
	"strings"
	"sync"
)

// One counter (requests by path and status) and one histogram (seconds by path),
// kept in plain maps and printed in the Prometheus text format on /metrics.
var (
	mu       sync.Mutex
	buckets  = []float64{0.1, 0.25, 0.5, 1, 2.5, math.Inf(1)}
	requests = map[string]int{}   // "path status" -> count
	observed = map[string][]int{} // path -> cumulative count per bucket
	sums     = map[string]float64{}
)

func observe(path string, status int, seconds float64) {
	mu.Lock()
	defer mu.Unlock()
	requests[fmt.Sprintf("%s %d", path, status)]++
	if observed[path] == nil {
		observed[path] = make([]int, len(buckets))
	}
	for i, le := range buckets {
		if seconds <= le {
			observed[path][i]++
		}
	}
	sums[path] += seconds
}

func metrics(w http.ResponseWriter, r *http.Request) {
	mu.Lock()
	defer mu.Unlock()
	w.Header().Set("Content-Type", "text/plain; version=0.0.4")
	fmt.Fprintln(w, "# TYPE http_requests_total counter")
	for key, n := range requests {
		path, status, _ := strings.Cut(key, " ")
		fmt.Fprintf(w, "http_requests_total{path=%q,status=%q} %d\n", path, status, n)
	}
	fmt.Fprintln(w, "# TYPE http_request_duration_seconds histogram")
	for path, counts := range observed {
		for i, le := range buckets {
			fmt.Fprintf(w, "http_request_duration_seconds_bucket{path=%q,le=%q} %d\n", path, fmt.Sprint(le), counts[i])
		}
		fmt.Fprintf(w, "http_request_duration_seconds_sum{path=%q} %g\n", path, sums[path])
		fmt.Fprintf(w, "http_request_duration_seconds_count{path=%q} %d\n", path, counts[len(buckets)-1])
	}
}

// Load generator: three loops hitting the API at random, forever. Ctrl-C stops it.
const base = "http://localhost:8080";
const paths = ["/", "/products", "/products", "/checkout"];
async function loop(n: number) {
  while (true) {
    const path = paths[Math.floor(Math.random() * paths.length)];
    const t = performance.now();
    const res = await fetch(base + path);
    await res.text();
    console.log(`loop ${n}  ${res.status}  ${path}  ${Math.round(performance.now() - t)} ms`);
    await new Promise((r) => setTimeout(r, 100));
  }
}
await Promise.all([1, 2, 3].map(loop));

// Reads JSON log lines on stdin. Prints the ones with status >= 500,
// or, given an argument, the ones containing that text (a request id).
import { createInterface } from "node:readline";
import process from "node:process";
const want = Deno.args[0];
for await (const line of createInterface({ input: process.stdin })) {
  try {
    const rec = JSON.parse(line);
    if (want ? line.includes(want) : rec.status >= 500) console.log(line);
  } catch {
    // not JSON (a startup line, a panic): ignore
  }
}

Things students ask

  • "Why not just use the library?" You will, next week, and it will be four lines. Today you know what those four lines produce, why +Inf is mandatory, and what a histogram costs (six series per path). People who skip this step spend their first incident staring at histogram_quantile as if it were magic.
  • "The p95 says 1.9 but the log says 2.3." Correct, and worth two minutes. Prometheus knows only that 17 requests fell between 1 and 2.5 s and assumes they are spread evenly. Buckets are chosen by you; put a bound where you need precision (at your SLO threshold, say) and the estimate is exact there.
  • "Can Prometheus scrape my app on the laptop instead of in Compose?" Yes: target host.docker.internal:8080, and on Linux add extra_hosts: ["host.docker.internal:host-gateway"] to the Prometheus service. Not in the lab because the room has Compose in its fingers from workshops 6 and 7, and it means one fewer thing that differs by OS.
  • "Is JSON logging slower?" Slightly more bytes per line, and slog is designed not to allocate for the common case. The cost that matters is elsewhere: log volume. A busy service logs every request into a system that indexes it, and that is the bill; sampling (stretch goal) is the answer, not going back to prose.
  • "Where do logs go in production?" Standard output, exactly as here, and the platform collects them: Docker's log driver, Kubernetes, then something like Loki or Elasticsearch that indexes the JSON fields. Step 1's filter is a one-file version of that pipeline.
