Storing Passwords Properly

Store a password so that a leaked database is useless. Start in plaintext, write the dictionary attack that breaks it, then salt, slow and self-describe the hash until the same attack would take centuries — in about fifty lines of Go, standard library only.

Workshop 3

At a glance

OutcomeEvery student leaves having broken a password store with their own dictionary attack and then rebuilt it correctly: a per-user salt, PBKDF2-HMAC-SHA256 at the OWASP-recommended work factor, a constant-time comparison, and a self-describing hash string with a Verify that transparently upgrades old accounts on login. They can say, from having measured it, why a fast hash is a liability and how slow is slow enough.
Why this topicPassword storage is done wrong constantly, and the wrong versions look like they work: a plaintext or plain-SHA-256 store passes every test and every login. The failure only shows up in a breach, when it is everyone's problem at once. The one way to make the lesson stick is to be the attacker for twenty minutes, which is exactly what step 2 is.
ConceptsOne-way hashing vs encryption, dictionary and rainbow-table attacks, per-user salts, the meaning of a "work factor", key-derivation functions (PBKDF2, and Argon2id / bcrypt by name), constant-time comparison and timing side-channels, self-describing hash encodings and upgrade-on-login. On the side: crypto/sha256, crypto/rand, crypto/pbkdf2 (Go 1.24+), crypto/subtle, encoding/base64, and reading a wall-clock time in Go.
Assumed knowledgeCan open a terminal and run a command. Can read a short program in any language. No Go and no cryptography assumed: the topic code is short and typed a line at a time, and the one hashing call comes straight from the standard library.
LanguageGo, standard library only. Go because password hashing is where its crypto packages are the natural home, because a single static binary needs nothing installed but Go, and because crypto/pbkdf2 landing in the standard library in Go 1.24 means the whole lab runs with no dependencies and no network. Argon2id, the production choice, lives in golang.org/x/crypto and appears as a stretch goal.
Students needLaptop with Go 1.24 or newer (the prep installs 1.27), a terminal, a text editor. No phone, no Docker, no network during the lab.
Room needsProjector. Wi-Fi only for students who skipped the prep and still need to download Go; nothing in the lab itself touches the network.

Preparation

For students (about 15 minutes)

This is written to be pasted into an email or course page as-is.

1. Install Go

Go is a single toolchain that compiles and runs programs with one command. Install Go 1.24 or newer — the lab uses a package (crypto/pbkdf2) that was added to the standard library in Go 1.24. The current release is 1.27.1.

On macOS and Windows, download the installer from go.dev/dl (the .pkg for macOS, the .msi for Windows) and accept the defaults. On Linux, follow go.dev/doc/install:

# Linux (amd64): remove any old Go, then unpack the new one
rm -rf /usr/local/go && tar -C /usr/local -xzf go1.27.1.linux-amd64.tar.gz
export PATH=$PATH:/usr/local/go/bin      # add this line to ~/.profile too

Open a new terminal so the tool is on your path, then check the version. Anything 1.24 or higher is fine:

go version

2. The readiness check

Make a folder called passwords-lab and open a terminal in it (Terminal on macOS, PowerShell on Windows). Create a file ready.go with exactly this content:

package main

import (
	"crypto/pbkdf2"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func main() {
	key, _ := pbkdf2.Key(sha256.New, "techbytes", []byte("salt"), 1000, 16)
	fmt.Println("ready", hex.EncodeToString(key))
}

Then initialise the folder as a Go module and run the file:

go mod init passwords
go run ready.go

Expected output

ready 0ac710aaeba8701f0d15781032369385

If you see exactly that, your Go is new enough and the standard-library crypto the lab needs is present. If instead you see package crypto/pbkdf2 is not in std, your Go is older than 1.24 — install a newer one. Any other error: bring it to the workshop and arrive ten minutes early.

Why this exact check

crypto/pbkdf2 only exists in Go 1.24+, so a student on an old Go fails this line during prep instead of in the room at step 4. The printed value is a fixed PBKDF2 output, so a wrong number means a broken install, not a wrong guess.

For the instructor

  • Run the whole lab yourself on each OS you expect in the room, with the exact commands on this page. Note your own timing for step 4 (one PBKDF2 hash at 600,000 iterations) so you can say it out loud; it depends on the laptop and ranges from about a tenth of a second to half a second.
  • The data files — users.txt, hashes.txt and the 300-word words.txt — are pasted from this page (or downloaded from the full solution). Have them on a USB stick too; the lab needs no network, so a student who skipped the prep only needs Go and these files.
  • The attack-cost widget at the top of this page is your slide for step 4. With the hardware slider on "gaming GPU" and the password at 8 lowercase letters, drag the storage slider from "SHA-256 once" to "600,000 · OWASP" while talking and let "10 seconds → 130 days" land. Then — this order matters — first set the password to 20 characters and "all 95 keys", and only then drag the hardware slider all the way up to every Bitcoin miner on Earth: watch that long random password still hold for longer than the universe has existed. Drag the password back down to 6 characters and watch it fall in an instant. Three sliders, three lessons: slow hashing, then hardware, then the password itself.
  • The tenth target hash never cracks: it is judy's long random password, not in the wordlist. Point this out — it is the one honest defence a user can mount, and the reason your side still has to do the work.
  • Step 2's attack.go prints its own hashing time, so the same go run attack.go shows both the cracked passwords and the elapsed time on every OS — no time or PowerShell Measure-Command needed (and Measure-Command would in any case swallow the cracked lines the checkpoint asks students to see).

The talk: make the leak worthless

The single idea to land: a stored password must be useless to whoever steals the database; everything we do is raising the cost of turning a stolen hash back into a password from microseconds to centuries. The lab is the mechanics of that sentence, attacked from both sides.

  1. 1Assume the database will leak1 min Title slide. State the assumption we never drop: your database will leak one day. The job of password storage is to make that leak worthless, not less likely. We build the failure and the fix, and attack both.
  2. 2A leak is the whole file1 min Show a plaintext user:password file. If it leaks, the attacker just reads it and logs in as anyone, then reuses those passwords elsewhere. First rule: never store the password; store something you can check against but cannot reverse — a hash.
  3. 3Don't store it, hash it2 min A hash is one-way and deterministic. Store the hash, check a login by re-hashing and comparing fingerprints. But deterministic means the attacker can guess: same password, same hash, every time. And they guess fast.
  4. 4The dictionary attack2 min The ~15-line attack from step 2: hash each word in a list, check against the stolen hashes. Nine of ten cracked in well under a millisecond on a laptop; one gaming GPU does 22 billion SHA-256/s (hashcat, RTX 4090). SHA-256 is fast, and fast is wrong for passwords. The uncracked tenth is a random password not in any list.
  5. 5Salt1 min Two users, same password, identical hash — that leaks reuse and lets one precomputed (rainbow) table crack everyone. A random per-user salt mixed in before hashing makes them differ, killing precomputation. But the salt leaks with the file, so a targeted per-user guess still works (step 3 does it). Salt beats bulk, not one guess.
  6. 6Slow it down2 min Use a deliberately slow hash: PBKDF2 repeats HMAC-SHA256 a chosen number of times. OWASP recommends 600,000 for SHA-256 (verified for this workshop). One line of stdlib Go. Play the widget: the same GPU that tried every 8-letter lowercase password in ~10 s now needs ~130 days. Invisible to one login, ruinous to billions.
  7. 7Compare in constant time2 min == stops at the first differing byte, so a failed compare's time leaks how many leading bytes were right — 3 ns vs 1.3 µs in step 5's measurement. Fix with crypto/subtle.ConstantTimeCompare, which always reads every byte. Same rule as the TOTP workshop: secrets compare in constant time, always.
  8. 8A hash that describes itself2 min Store $pbkdf2-sha256$iterations$salt$hash (salt and hash Base64): the recipe travels with the hash. To verify, parse it and read the parameters out. Upgrade-on-login: if the stored iteration count is below today's policy and the password was correct, re-hash at the new cost and save — storage heals itself one login at a time. Step 6 writes this.
  9. 9The production answer1 min PBKDF2 is real and FIPS-approved; the modern default is Argon2id, which costs the attacker memory as well as time and so blunts GPUs. bcrypt is the older, solid middle ground (72-byte limit). Argon2id is in golang.org/x/crypto, not stdlib, so it is a stretch goal here — but the shape (salt, cost, self-describing string, constant-time compare) is what you built.
  10. 10The next 90 minutes1 min Walk the eight steps: plaintext and logging in as anyone, the dictionary attack, salt, PBKDF2, constant-time compare, verify-and-upgrade, wrap-up. Go and the standard library only. Five-minute break, then step 0.

Step 0

Ready: the project and a readiness check

5 min

In the passwords-lab folder, confirm the toolchain and make the module. If you did the prep, ready.go and the module already exist; run the loader below either way.

go mod init passwords    # skip if go.mod already exists from the prep

Save the ten-line users file as users.txt — this is the "database" the whole lab attacks — and a small loader as load.go. Both are pasted; a file-reading loop is not the topic.

users.txt

load.go

package main

import (
	"fmt"
	"os"
	"strings"
)

func loadUsers(path string) (map[string]string, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, err
	}
	users := map[string]string{}
	for _, line := range strings.Split(strings.TrimSpace(string(data)), "\n") {
		name, secret, _ := strings.Cut(line, ":")
		users[name] = secret
	}
	return users, nil
}

func main() {
	users, err := loadUsers("users.txt")
	if err != nil {
		fmt.Println("error:", err)
		os.Exit(1)
	}
	fmt.Printf("ready: %d users loaded\n", len(users))
}
go run load.go

Step 1

Plaintext, and logging in as anyone

10 min

Here is the naive password store: the file is the passwords, and a login is a string comparison. Save it as login1.go (pasted — the point is a concept, not the code) and log in as yourself:

login1.go

package main

import (
	"fmt"
	"os"
	"strings"
)

func main() {
	data, _ := os.ReadFile("users.txt")
	users := map[string]string{}
	for _, line := range strings.Split(strings.TrimSpace(string(data)), "\n") {
		name, stored, _ := strings.Cut(line, ":")
		users[name] = stored
	}
	name, password := os.Args[1], os.Args[2]
	if users[name] == password {
		fmt.Printf("welcome, %s\n", name)
	} else {
		fmt.Println("no")
	}
}
go run login1.go alice password    # correct -> welcome; a wrong password -> no

Now play the attacker. The database has leaked — which means you are holding users.txt. Read it, pick any account, and log in as them:

cat users.txt                       # PowerShell: type users.txt
go run login1.go grace sunshine     # someone else's account

Checkpoint 1

You logged in as grace without ever being grace, using only what a leaked file handed you. That is the failure mode the rest of the lab removes.

Talk about it: nothing was "hacked" here — the login code is correct. The bug is entirely in what was stored. Where else has grace probably used sunshine? That is why a leak of your site becomes a problem for sites you have never heard of.

Step 2

Crack it: the dictionary attack

20 min

The obvious fix is to store a hash instead of the password: one-way, so the file no longer is the passwords. But a hash is deterministic — the same password always hashes the same — so an attacker can guess. This is the step where you are the attacker, and you write the guesser yourself.

You have stolen the whole leaked table — one SHA-256 hash per user, all ten of them — and you have a wordlist of common passwords. Save the ten target hashes as hashes.txt:

Now the attack. Create attack.go. Paste the imports, then type the loop — it is the whole idea, about fifteen lines: hash each word, and if its fingerprint is one you stole, you have cracked that account.

attack.go

package main

import (
	"bufio"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"os"
	"strings"
	"time"
)
func main() {
	data, _ := os.ReadFile("hashes.txt")
	want := map[string]bool{}
	for _, h := range strings.Fields(string(data)) {
		want[h] = true
	}
	f, _ := os.Open("words.txt")
	sc := bufio.NewScanner(f)
	start := time.Now()
	for sc.Scan() {
		sum := sha256.Sum256([]byte(sc.Text()))
		if want[hex.EncodeToString(sum[:])] {
			fmt.Printf("cracked  %q\n", sc.Text())
		}
	}
	fmt.Printf("hashed the whole list in %v\n", time.Since(start))
}

Run it — the program prints each cracked password and how long the whole list took to hash, so you feel how cheap guessing is:

go run attack.go

Checkpoint 2

Nine of the ten hashes are cracked and printed as their plaintext passwords — password, 123456, qwerty, letmein, dragon, monkey, sunshine, football, trustno1 — followed by a line like hashed the whole list in 250µs. Hashing all 300 words took well under a millisecond; there was no salt, so one pass over the list cracked every reused password at once. One hash (judy's) is not cracked.

Talk about it: which hash survived, and why? (A long random password that is in no wordlist — the one defence a user can mount.) SHA-256 did its job perfectly and it did not help at all: the problem is that it is fast. A real wordlist is hundreds of millions of entries, and one gaming GPU does 22 billion SHA-256 a second, about five thousand times your laptop core. Try the widget at the top of the page: hardware on "gaming GPU", storage on "SHA-256 once".

Step 3

A per-user salt

15 min

Two problems remain with a plain hash. Identical passwords produce identical hashes, which leaks who shares a password; and an attacker can precompute one giant word-to-hash table (a "rainbow table") once and look everyone up. A per-user salt — a few random bytes, stored with the hash and mixed in before hashing — fixes both. Create salt.go; type the saltedHash function, which is the whole new idea, then paste the demo below it.

salt.go

package main

import (
	"bufio"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"os"
)
func saltedHash(salt []byte, password string) string {
	sum := sha256.Sum256(append(salt, []byte(password)...))
	return hex.EncodeToString(sum[:])
}
func main() {
	// alice and erin both chose the SAME password:
	pw := "dragon"
	aSalt, eSalt := make([]byte, 16), make([]byte, 16)
	rand.Read(aSalt)
	rand.Read(eSalt)
	fmt.Println("alice:", saltedHash(aSalt, pw))
	fmt.Println("erin :", saltedHash(eSalt, pw))
	fmt.Println("same password, different hashes -> rainbow tables are dead")

	// but if the DB leaks, the salt leaks with it. Attack erin, per user:
	target := saltedHash(eSalt, pw)
	f, _ := os.Open("words.txt")
	defer f.Close()
	for sc := bufio.NewScanner(f); sc.Scan(); {
		if saltedHash(eSalt, sc.Text()) == target {
			fmt.Printf("erin's password is still %q\n", sc.Text())
			break
		}
	}
}
go run salt.go       # run it a second time: the salts, and so the hashes, change

Checkpoint 3

alice and erin have the same password (dragon) but two different hashes, and both change every run as the salt changes — so rainbow tables and dedup are dead. And yet the last line still prints erin's password is still "dragon": a per-user dictionary attack, using the salt that leaked alongside the hash, cracks her anyway.

Talk about it: the salt is not a secret and does not need to be — it is stored in the clear next to the hash. So what did salting actually buy us? (It stops one precomputed table from cracking the whole file at once; the attacker must now redo the work per user.) What did it not buy us? (Any slowdown of a single targeted guess.) That is the next step's job.

Step 4

Slow it down with PBKDF2

15 min

The reason step 2 was instant is that SHA-256 is fast. A password hash should be deliberately slow. PBKDF2 does this by running HMAC-SHA256 many times over — you pick how many. The current OWASP recommendation is 600,000 iterations for PBKDF2-HMAC-SHA256. Create slow.go and type the body: one hash, timed, and the arithmetic for what the step-2 attack would now cost.

slow.go

package main

import (
	"crypto/pbkdf2"
	"crypto/rand"
	"crypto/sha256"
	"fmt"
	"time"
)

const iterations = 600_000 // OWASP-recommended work factor for PBKDF2-HMAC-SHA256
func main() {
	salt := make([]byte, 16)
	rand.Read(salt)
	start := time.Now()
	pbkdf2.Key(sha256.New, "dragon", salt, iterations, 32)
	per := time.Since(start)
	fmt.Printf("one hash: %v  (%.0f hashes/second)\n", per, 1/per.Seconds())

	words := 300.0
	fmt.Printf("step-2 wordlist (300 words): %v\n", time.Duration(words*float64(per)))
	space := 26.0 * 26 * 26 * 26 * 26 * 26 * 26 * 26 // 8 lowercase letters
	secs := space * per.Seconds()
	fmt.Printf("all 8-char lowercase (%.2e): %.0f years\n", space, secs/(3600*24*365))
}
go run slow.go

Checkpoint 4

One hash now takes a fraction of a second (roughly 0.1–0.5 s depending on your laptop) instead of the microseconds of step 2. The program prints how long the 300-word attack would now take — over a minute, not the fraction of a millisecond of step 2 — and that brute-forcing all 8-character lowercase passwords would take thousands of years. Same laptop, same code, one constant changed.

Talk about it: a single login now costs you a fraction of a second — imperceptible. The attacker pays that cost on every one of billions of guesses. Open the widget at the top of the page, keep the hardware on "gaming GPU", and drag storage from "SHA-256 once" to "600,000 · OWASP": watch ten seconds for the whole 8-letter lowercase space become months. Then drag hardware to the top of the scale and see what only a longer password can fix. Why is a hash you can tune better than a hash that is merely "strong"? (Because you can raise the cost as hardware gets faster — which step 6 does automatically.)

Step 5

Constant-time compare

10 min

One leak is left, and it is in the comparison. Go's == on byte strings stops the instant it finds a difference, so a comparison that fails on the first byte returns sooner than one that fails on the last. Response time then spells out how many leading bytes were right, one guess at a time. Measure it. Create timing.go; paste the harness, then type the six comparisons.

timing.go

package main

import (
	"crypto/subtle"
	"fmt"
	"strings"
	"time"
)

func avg(compare func() bool, reps int) time.Duration {
	hits := 0
	start := time.Now()
	for i := 0; i < reps; i++ {
		if compare() {
			hits++
		}
	}
	_ = hits
	return time.Since(start) / time.Duration(reps)
}

func main() {
	const n, reps = 65536, 50000
	secret := strings.Repeat("a", n)
	first := "b" + secret[1:]  // differs at the FIRST byte
	last := secret[:n-1] + "b" // differs at the LAST byte
	sec, fb, lb := []byte(secret), []byte(first), []byte(last)
	fmt.Println("plain ==")
	fmt.Println("  differs at first byte:", avg(func() bool { return secret == first }, reps))
	fmt.Println("  differs at last byte :", avg(func() bool { return secret == last }, reps))
	fmt.Println("subtle.ConstantTimeCompare")
	fmt.Println("  differs at first byte:", avg(func() bool { return subtle.ConstantTimeCompare(sec, fb) == 1 }, reps))
	fmt.Println("  differs at last byte :", avg(func() bool { return subtle.ConstantTimeCompare(sec, lb) == 1 }, reps))
}
go run timing.go

Checkpoint 5

For plain ==, "differs at first byte" is a few nanoseconds while "differs at last byte" is hundreds of times slower (roughly 3 ns versus 1.3 µs) — the short-circuit is visible. For subtle.ConstantTimeCompare, the two are close to equal (both tens of microseconds, varying run to run): it always reads every byte, so its timing tells an attacker nothing about which byte was wrong. Note that it is slower in absolute terms than even the worst == — the secret here is 64 KiB to make the effect large enough to see, and ConstantTimeCompare cannot use the wide SIMD shortcut that == uses. On a real 32-byte hash the leak is a handful of nanoseconds rather than a microsecond, but it is the same leak, and the rule is the same.

Talk about it: this is the same rule you met comparing TOTP codes in workshop 2 — any comparison of secret material is constant-time, always. Why does the length check that a real verifier puts in front of ConstantTimeCompare not itself leak? (It only reveals the length, which for a fixed-size hash the attacker already knows.) Over a network the nanoseconds are buried in noise; why build the habit anyway? (Because the leak is real on a shared machine, and the correct call is no harder to write.)

Step 6

Verify, and upgrade on login

10 min

Put it together into what a server actually stores: one self-describing string, $pbkdf2-sha256$iterations$salt$hash, with the salt and hash in Base64. The recipe travels with the hash, so a verifier reads the parameters straight out of it — and can notice when they are out of date. Create verify.go; paste the imports and the hashPassword helper, then type the verify function, the parser and the constant-time check.

verify.go

package main

import (
	"crypto/pbkdf2"
	"crypto/rand"
	"crypto/sha256"

Checkpoint 6

An account stored at the old cost of 100,000 iterations verifies with the correct password and is reported stale; the program re-hashes it at today's 600,000 and prints the upgraded string; a second verify reports it no longer stale; and a wrong password is rejected. The stored string carries its own algorithm, cost and salt, so nothing external has to remember them.

Talk about it: you never stored anyone's password, so how can you raise the iteration count on old accounts? (Only on a successful login, when the plaintext is briefly in hand — the store heals one login at a time.) Why is the algorithm name inside the string, not assumed? (So you can migrate to Argon2id later without a flag day: the same verify dispatches on what each record says.)

Step 7

Wrap-up and stretch goals

5 min

Bring the room back together for a few minutes, then let the fast typists pick a stretch goal.

Wrap-up points

  • You never store the password. You store a salted, slow, self-describing hash, and you compare it in constant time. Everything today was one of those four words.
  • Salt defeats bulk precomputation; it does not slow a single guess. The work factor is what does that, and it is the only knob that matters against a serious attacker.
  • "Slow enough" is not a fixed number — it is OWASP's number today (600,000 for PBKDF2-HMAC-SHA256) and a bigger one next year, which is why the hash describes itself and upgrades on login.
  • A fast, "strong" hash like SHA-256 is the wrong tool for passwords precisely because it is fast. Use a password hash: PBKDF2 at minimum, Argon2id by preference.

Stretch goals (pick one)

  • Argon2id — the production choice. Swap PBKDF2 for golang.org/x/crypto/argon2's IDKey with the OWASP parameters (m=19456 KiB, t=2, p=1) and a $argon2id$v=19$m=19456,t=2,p=1$salt$hash string. It costs the attacker memory as well as time, which is what beats GPUs. (This needs one module download — go get golang.org/x/crypto/argon2 — so it could not be run in this workshop's sealed environment; the code and parameters are in the instructor notes' sources.)
  • bcrypt. Do the same with golang.org/x/crypto/bcrypt, whose output is already self-describing. Discover its 72-byte input limit by hashing a 100-character password and a variant that differs only after byte 72.
  • Add a pepper. Mix a single secret value — kept out of the database, in an environment variable — into every hash. Why does a pepper help when the database leaks but the config does not, and why is it no substitute for a slow hash?
  • Breach check with k-anonymity. Using the wordlist, reproduce how Have I Been Pwned lets you check a password without sending it: SHA-1 the password, send only the first 5 hex characters to the range API, and match the suffix locally. (Needs network, so it is a home exercise.)
  • Rate limit and lock out. Wrap verify in a per-account failed-attempt counter that locks after five tries. Slow hashing and rate limiting are the two halves of a safe login; you built one, add the other.

	sum := sha256.Sum256(append(salt, []byte(password)...))
	return hex.EncodeToString(sum[:])
}

	pw := "dragon"

	rand.Read(eSalt)

import (
	"crypto/subtle"

	"time"

func avg(compare func() bool, reps int) time.Duration {
	hits := 0
	start := time.Now()
	for i := 0; i < reps; i++ {
		if compare() {
			hits++
		}
	}
	_ = hits
	return time.Since(start) / time.Duration(reps)
}

func main() {
	const n, reps = 65536, 50000
	secret := strings.Repeat("a", n)
	first := "b" + secret[1:]  // differs at the FIRST byte
	last := secret[:n-1] + "b" // differs at the LAST byte
	sec, fb, lb := []byte(secret), []byte(first), []byte(last)

	fmt.Println("plain ==")
	fmt.Println("  differs at first byte:", avg(func() bool { return secret == first }, reps))
	fmt.Println("  differs at last byte :", avg(func() bool { return secret == last }, reps))
	fmt.Println("subtle.ConstantTimeCompare")
	fmt.Println("  differs at first byte:", avg(func() bool { return subtle.ConstantTimeCompare(sec, fb) == 1 }, reps))
	fmt.Println("  differs at last byte :", avg(func() bool { return subtle.ConstantTimeCompare(sec, lb) == 1 }, reps))
}

Instructor notes

Timing reality

The two moments to protect are step 2 and step 4, because they are where the point lands. Step 2 is the longest step (20 minutes) on purpose: students are writing code, not pasting it, and the ~15-line loop is the one piece of real programming in the afternoon. Step 4's one number — how long your laptop takes for a single 600,000-iteration hash — is worth saying out loud; it ranges from about a tenth of a second on a fast machine to half a second on a modest one, and either way the contrast with step 2's microseconds is the whole lesson. If you are behind after step 4, cut the "talk about it" discussions in steps 3 and 5 and keep the code; steps 5 and 6 are short and must not be rushed.

Things students ask

  • "Isn't SHA-256 secure? Why is it wrong here?" It is secure and it is wrong here for the same reason: it is fast and collision-resistant. Password hashing wants a function that is deliberately, tunably slow. "Strong hash" and "password hash" are different jobs.
  • "Why not just encrypt the passwords?" Encryption is reversible by design; whoever holds the key can get every password back, and in a breach they often get the key too. Hashing is one-way on purpose — you never need the password back, only to check one.
  • "Is the salt secret?" No. It is stored in the clear next to the hash and leaks with it. Its only job is to make each hash unique so one precomputed table cannot crack the whole file. Secrecy is the pepper's job (stretch goal).
  • "Should I write this in real life?" Use a vetted library and a password hash — Argon2id via golang.org/x/crypto/argon2, or bcrypt — plus rate limiting. The point of writing PBKDF2 by hand is to be able to read those libraries and judge a stored-hash format, not to ship your own.
  • "How do I pick the iteration count?" Take OWASP's current number as the floor, then raise it until one hash takes as long as your login endpoint can tolerate (a common target is around a quarter-second), and store it in the hash so you can raise it again later.
