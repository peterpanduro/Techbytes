Containers From the Ground Up

Run other people's software in containers, then put your own web server in one: a Dockerfile, a build without any toolchain on your laptop, and a multi-stage build that shrinks the result from close to a gigabyte to about ten megabytes.

  • 15 min talk
  • 90 min guided lab
  • ~20 min student prep, one week before
  • No prior Docker knowledge
  • Go, built inside Docker
  • Any OS
Interactive · the layer cache

Each Dockerfile line is a layer. A layer is rebuilt when its input changed, or when any layer above it was rebuilt. Change a file and see what each ordering costs.

      Workshop 1

      At a glance

      OutcomeEvery student leaves with a working mental model of image vs container, the full container lifecycle in their fingers, and a repository containing a small Go web server plus a multi-stage Dockerfile that produces an image under 15 MB, built without Go installed on their laptop.
      Why this topicEvery later workshop, and most jobs, assume it. Courses rarely teach it, and self-taught Docker tends to be cargo-culted: people copy a Dockerfile without knowing what a layer is or why their image is a gigabyte. This afternoon fixes that once.
      ConceptsImages and containers, registries and tags, the run / ps / logs / exec / stop / rm lifecycle, port publishing, environment variables, bind mounts and what survives a restart, Dockerfile instructions, layers and the build cache, the build context and .dockerignore, multi-stage builds, and what containers are not (not VMs, not a security boundary by default, not CPU-architecture independent).
      Assumed knowledgeCan open a terminal and run a command. Can read a short program in any language. No Go knowledge is needed: the server is pasted and read aloud, never edited beyond one string.
      LanguageGo, but only inside containers. The point of the lab is that the Go toolchain lives in an image, so nobody installs Go. Go was chosen over Deno for this one because a Go binary is a single static file, which makes the multi-stage build land: the final image contains one file and nothing else.
      Students needLaptop with Docker Desktop (macOS, Windows) or Docker Engine (Linux), a browser, a text editor. The three images from the prep pack already pulled.
      Room needsProjector. Wi-Fi only for students who skipped the prep; the instructor carries the images on a USB stick.
      Timing15 min talk · 5 min break · 90 min lab (seven steps, each with a checkpoint that must pass before moving on).

      Preparation

      For students (about 20 minutes, plus a download)

      This is written to be pasted into an email or course page as-is.

      1. Install Docker

      On macOS or Windows install Docker Desktop from docs.docker.com/get-started/get-docker and accept the defaults (on Windows it will set up WSL 2, which may need a restart). On Linux install Docker Engine for your distribution from the same page, then let your user run it without sudo:

      sudo usermod -aG docker $USER
newgrp docker      # or log out and in again

      Start Docker Desktop once so it finishes its setup. It must be running whenever you use the docker command.

      2. Confirm it works

      docker run --rm hello-world

      You should see a message beginning "Hello from Docker!". If you see "Cannot connect to the Docker daemon", Docker Desktop is not running.

      3. Download the three images we will use

      About 400 MB in total. Do this at home; it is the only part that needs a good connection.

      docker pull alpine
docker pull nginx
docker pull golang:1.27

      4. The readiness check

      Make a folder called docker-lab and open a terminal in it (Terminal on macOS, PowerShell on Windows). Run:

      docker run --rm -v "$PWD":/work -w /work alpine sh -c "echo ready > proof.txt && cat proof.txt"

      Windows users: in PowerShell replace "$PWD" with "${PWD}"; if you use Git Bash, paths get rewritten and this will fail, so use PowerShell for the workshop.

      Expected output

      ready, and a file proof.txt has appeared in your folder. If both happened, Docker can run containers and share files with your folder, which is everything the lab needs. If not, bring the error message to the workshop and arrive ten minutes early.

      If Docker will not install

      The two common blockers are virtualisation disabled in the BIOS (Windows laptops from some vendors) and a university-managed laptop without admin rights. Neither is fixable in the room. Pair that student with a neighbour for the afternoon; everything in the lab works for two people at one keyboard.

      For the instructor

      • Run the whole lab yourself on each OS you expect in the room, with the exact commands on this page. Note the sizes and timings you get for step 3 and step 5 so you can say them out loud.
      • Save the three images to a USB stick for anyone whose pull failed: docker save alpine nginx golang:1.27 -o images.tar (about 1 GB), restored with docker load -i images.tar.
      • On Apple silicon, everything on this page works unchanged: the images are multi-architecture and the Go build produces an arm64 binary. Mention it only if someone asks why their image "would not run on the server": that is stretch goal 2.
      • The demo widget at the top of this page is your slide 7. Press the three buttons while talking about cache invalidation.
      • Have the full solution ready. The Dockerfiles are short enough that a stuck student can retype them from the projector, but main.go should be pasted.
      • Ask the room to close other applications that listen on port 8080 (a previous container, a dev server). "address already in use" (older Docker: "port is already allocated") is the second most common error of the day, after a forgotten -p.

      The talk: a process with its own view of the world

      The single idea to land: a container is an ordinary process that has been given its own filesystem, network and process list; an image is the frozen filesystem it starts from. Not a virtual machine, not magic. Everything in the lab is a consequence.

      1. 1"It works on my machine"1 min Title slide. Ask who has lost an afternoon to a dependency that was installed on one laptop and not another, or to two projects wanting different versions of the same runtime. That afternoon is the problem containers solve.
      2. 2What a container is2 min A process. The kernel is asked to give it a private view: its own root filesystem, its own network interfaces, its own process IDs, and a limit on memory and CPU. It shares the host's kernel with every other container, which is why it starts in milliseconds and why a VM is a different thing entirely: a VM boots a whole operating system. On macOS and Windows, Docker Desktop runs one small Linux VM and all your containers run inside it; that is why the clock and the disk sometimes behave oddly there.
      3. 3Image versus container2 min An image is a read-only filesystem, stored as a stack of layers, plus a note saying which program to start. A container is one image plus a thin writable layer plus a running process. Class and instance. You can run ten containers from one image; each has its own writable layer; delete the container and that layer is gone. Write this on the board and leave it there all afternoon.
      4. 4Where images come from1 min Registries. Docker Hub is the default; nginx means docker.io/library/nginx:latest. The tag after the colon is a label, not a promise: latest moves. Pin versions. Show the three images from the prep and their sizes with docker images.
      5. 5The lifecycle1 min run creates and starts. ps lists what is running, ps -a what exists. logs shows what the process printed. exec runs a second process inside the same container, which is how you look around. stop sends the process a signal; rm deletes the container and its writable layer. Draw it as a line. The lab does this loop by hand in step 1 and never stops doing it.
      6. 6Getting in and out: ports, files, environment2 min The container's network is private, so -p 8080:80 publishes a host port onto a container port; host first, container second, everyone gets it backwards once. Files: -v mounts a host folder into the container, and it is the only way data survives rm. Configuration goes in with -e environment variables; the app reads them at start. That is the whole interface between a container and the world.
      7. 7Dockerfiles are layered, and the cache is why order matters2 min FROM picks the starting filesystem, COPY adds files, RUN executes a command and keeps the result, CMD says what to start. Each instruction makes a layer, and a layer is rebuilt when its input changed or when anything above it changed. Use the widget on this page: copy everything first and one edit to main.go re-downloads dependencies; copy go.mod first and the edit only recompiles. Same image, different afternoon.
      8. 8Multi-stage: build in a big image, ship a small one1 min The Go toolchain image is close to a gigabyte; the compiled program is eight megabytes. A second FROM starts a new image, and COPY --from takes only the binary across. The result has no shell, no package manager, no toolchain, so there is nothing for an attacker to use and nothing to update. This is also why nobody in the room needs Go installed.
      9. 9More than one container: Compose1 min Real applications are several containers, each wanting ports, volumes and settings. A compose.yaml writes those docker run flags down per service, and docker compose up starts them all on a private network where they find each other by name. Not for today; the point is that a run command you keep retyping wants to be a file. Workshop 6 is built on it.
      10. 10What containers are not1 min Not a VM: same kernel. Not a sandbox by default: root inside is root on the host, and a mounted folder is the host's folder. Not portable across CPU architectures: an image built on an Apple-silicon laptop is arm64 and will not run on an amd64 server unless you ask for --platform. All three come back in later workshops.
      11. 11What we build in the next 90 minutes1 min Seven steps: run other people's images, borrow a Go toolchain from an image to run our server, write a Dockerfile, watch the cache, shrink the image with a second stage, then wire up ports, settings and a volume and prove what survives a restart. Five-minute break, then step 0.

      5 min

      Step 1

      Someone else's image: the lifecycle by hand

      10 min

      First a container you can look around in. -it gives you a terminal inside it; alpine is a five-megabyte Linux.

      docker run --rm -it alpine sh
# you are now inside the container:
cat /etc/os-release
ps
exit

      ps shows two processes: your shell and ps itself. That is the whole world as this container sees it. Now a real server, detached, with a port published and a name so you can refer to it:

      docker run -d --name web -p 8080:80 nginx
docker ps
docker logs web
docker exec -it web sh -c "ls /usr/share/nginx/html"
docker stop web
docker ps -a
docker rm web

      Open http://localhost:8080 in the browser after the first command and reload it a couple of times before docker logs, so there is something in the log. -p 8080:80 reads "host port 8080 to container port 80".

      Checkpoint 1

      The nginx welcome page in the browser; the reloads visible in docker logs web; after stop the container still shows in ps -a with status Exited; after rm it is gone.

      Talk about it: what does stop do to the writable layer? (Nothing; start web would bring it back with its files, and plain docker ps would show it again.) What does rm do? (Deletes it.) Why did ps inside alpine show only two processes when the laptop is running hundreds?

      Step 2

      Borrow a toolchain to run the server

      8 min

      The app for the rest of the afternoon is a 40-line Go web server. Create these two files in docker-lab. Read main.go once, top to bottom: it greets you, says which machine it is running on, and counts visits in a file called visits.txt. Three things it does will matter later: it reads GREETING from the environment, it prints its hostname, and it writes a file in the current directory.

      main.go

      // A tiny web server: says hello, tells you which machine it runs on,
// and counts visits in a file so we can see what survives a restart.
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
	"strconv"
	"strings"
)

func main() {
	greeting := os.Getenv("GREETING") // configuration comes from the environment
	if greeting == "" {
		greeting = "Hello"
	}
	host, _ := os.Hostname() // inside a container this is the container id

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path != "/" { // browsers also ask for /favicon.ico; do not count that
			http.NotFound(w, r)
			return
		}
		n := bump("visits.txt")
		log.Printf("%s %s -> visit %d", r.Method, r.URL.Path, n)
		fmt.Fprintf(w, "%s from %s! You are visit number %d.\n", greeting, host, n)
	})

	log.Println("listening on http://localhost:8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}

// bump reads a number from the file, adds one, writes it back.
func bump(path string) int {
	b, _ := os.ReadFile(path)
	n, _ := strconv.Atoi(strings.TrimSpace(string(b)))
	n++
	if err := os.WriteFile(path, []byte(strconv.Itoa(n)), 0o644); err != nil {
		log.Println("could not save the counter:", err)
	}
	return n
}

      Nobody has Go installed. The golang image does. Mount the folder in, publish the port, and run it there:

      docker run --rm -it -v "$PWD":/app -w /app -p 8080:8080 golang:1.27 go run .

      Checkpoint 2

      The browser at localhost:8080 says "Hello from some-hex-id! You are visit number 1." and the number goes up on reload. visits.txt has appeared in your folder, because the folder is mounted. Ctrl-C stops it.

      Talk about it: the hostname it prints is the container ID. Where did the compiler run? Where is the compiled program now? (Inside a container that no longer exists.) What does the -v do that makes visits.txt appear on the laptop?

      Step 3

      First Dockerfile

      12 min

      Step 2 works but the recipe lives in a shell command. A Dockerfile writes it down, and the result is an image anyone can run. Create a file named exactly Dockerfile:

      FROM golang:1.27
WORKDIR /app
COPY . .
RUN go mod download
RUN go build -o server .
CMD ["./server"]

      Six lines, four kinds of instruction: FROM picks the starting image, WORKDIR chooses a folder, COPY brings the project in, RUN executes a command at build time (fetch dependencies, then compile), and CMD says what to start. Build it, then run it like nginx in step 1:

      docker build -t hello:1 .
docker images hello
docker run --rm -p 8080:8080 hello:1

      The . at the end of build is the build context: the folder whose files COPY may see. -t hello:1 is the name and tag.

      Checkpoint 3

      The build finishes, docker images hello shows hello:1 at several hundred megabytes (close to a gigabyte, since the whole toolchain is in it), and the browser shows the greeting. Note the visit counter starts at 1 again: this container's filesystem is fresh.

      Common mistakes: the file is called Dockerfile.txt (Windows hides extensions); the . is missing from the build command; the build fails with "go.mod not found" because the command was run from the wrong folder.

      Step 4

      Layers, cache, and the build context

      15 min

      Change the word Hello in main.go to anything else and rebuild:

      docker build -t hello:1 .
docker history hello:1

      Watch the output: FROM and WORKDIR say CACHED; from COPY . . downwards everything ran again, including go mod download, which on a real project is the slow, network-bound step. docker history lists the layers with their sizes, newest first. Now reorder so that the part that rarely changes (dependencies) comes before the part that changes constantly (code):

      FROM golang:1.27
WORKDIR /app
COPY go.mod ./
RUN go mod download
COPY . .
RUN go build -o server .
CMD ["./server"]

      Same six lines plus one: COPY go.mod before the download. Build once, change the greeting again, build again. The go mod download layer is now cached; only COPY . . and go build rerun. Our program has no dependencies so the saving is small here; on a real project this is the difference between a five-second and a five-minute rebuild. The same layout appears in every language's Dockerfiles: package manifest first, install, then the code.

      One more thing: COPY . . copies everything in the folder, including visits.txt from step 2 and, from step 6 on, the whole data folder. A .dockerignore keeps them out of the build context. Create it next to the Dockerfile; on Windows make sure the editor does not save it as .dockerignore.txt.

      .dockerignore

      visits.txt
data/

      Checkpoint 4

      After changing the greeting, the rebuild shows CACHED for COPY go.mod and go mod download, and only the last two layers run. docker history hello:1 shows a layer per instruction.

      Talk about it: use the widget at the top of the page. Why is a change to go.mod expensive in both layouts? What would happen if RUN go build came before COPY . .?

      Step 5

      Multi-stage build

      15 min

      hello:1 ships a compiler, a shell, a package manager and Debian, to run an eight-megabyte program. A multi-stage Dockerfile builds in the big image and copies only the result into an empty one. Replace the whole Dockerfile:

      # Stage 1: build, in an image that has the Go toolchain (about 800 MB)
FROM golang:1.27 AS build
WORKDIR /app
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# Stage 2: run, in an image that has nothing at all
FROM scratch
WORKDIR /data
COPY --from=build /app/server /server
EXPOSE 8080
CMD ["/server"]

      scratch is the empty image: no files at all. CGO_ENABLED=0 makes Go produce a binary that needs no system libraries, which is why it can run on nothing. WORKDIR /data creates the one directory the program needs for its counter file.

      docker build -t hello:2 .
docker images hello
docker run -d --name app -p 8080:8080 hello:2
docker exec -it app sh
docker rm -f app

      Checkpoint 5

      hello:2 is under 15 MB (the DISK USAGE column) next to hello:1's several hundred, the browser still shows the greeting, and docker exec -it app sh fails with "sh: executable file not found": there is no shell in this image, or anything else, only /server.

      Talk about it: what can an attacker who gets into this container do? (Very little; there is no shell to run, no package manager to install one.) What is the cost? (No exec for debugging; the stretch goals mention distroless as the middle ground.) Why did nobody need Go on their laptop at any point today?

      Step 6

      Ports, environment, volumes: what survives

      15 min

      Three experiments, each a question the program was written to answer. First, configuration through the environment:

      docker run -d --name app -p 8080:8080 -e GREETING=Hej hello:2
docker logs -f app

      Reload the browser a few times; the greeting changed without a rebuild, and logs -f follows the log live. Ctrl-C leaves the container running. Second, what a restart keeps and what rm destroys:

      docker restart app
docker rm -f app
docker run -d --name app -p 8080:8080 hello:2

      Reload after each command. After restart the counter continues (the writable layer survived). After rm and a new run it is back to 1 (new container, new layer). Third, a volume:

      docker rm -f app
docker run -d --name app -p 8080:8080 -v "$PWD/data":/data hello:2
docker rm -f app
docker run -d --name app -p 8080:8080 -v "$PWD/data":/data hello:2
docker rm -f app

      Reload between the runs. The counter now continues across rm, because visits.txt lives in the data folder on your laptop, mounted over the container's /data.

      Checkpoint 6

      -e GREETING=Hej changes the text; restart keeps the count; rm resets it; with -v the count survives rm and data/visits.txt exists on the laptop.

      Talk about it: which of the three (env, writable layer, volume) would you use for a database's files? For an API key? For a cache? Why is "the container's filesystem" the wrong place for anything you want to keep?

      Step 7

      Wrap-up and stretch goals

      10 min

      Bring the room back together for five minutes, then let the fast students pick a stretch goal.

      Wrap-up points

      • Back to the board: image = read-only layers + a start command; container = image + writable layer + process. Everything today was one of: making an image (build), making a container from it (run), or getting things in and out (-p, -e, -v).
      • Order the Dockerfile by how often things change. Copy manifests, install, then copy code.
      • Ship what runs, not what builds. Multi-stage is the default for compiled languages and increasingly for the others.
      • Nothing in a container is kept unless you mounted it somewhere. Say it twice.

      Stretch goals (pick one)

      • Publish it. Tag the image with your GitHub username (docker tag hello:2 ghcr.io/<you>/hello:2), log in to GHCR with a token, push, and have a neighbour docker run it. That is the whole distribution story.
      • Architecture. Run docker image inspect hello:2 --format '{{.Architecture}}'. On Apple silicon it says arm64. Rebuild with docker build --platform linux/amd64 -t hello:amd64 . and inspect again. Which one runs on a typical cloud server?
      • A shell when you need one. Replace FROM scratch with FROM gcr.io/distroless/static-debian12 (still no shell, but proper certificates, time zones and a non-root user) and then with FROM alpine (a shell, five megabytes). Compare sizes and docker exec behaviour.
      • Run as nobody. Add USER 65534:65534 before CMD. What breaks with the volume, and why? Fix it.
      • Cheap health. Add HEALTHCHECK CMD ["/server", "-check"] and make the program exit 0 when started with -check. Watch docker ps show "(healthy)". This becomes a liveness probe in the Kubernetes workshop.
      • Write it down. Put the step 6 docker run into a compose.yaml (one service, its port, environment and volume) and start it with docker compose up. Then add redis:7 as a second service and confirm the app container can reach it by name with docker compose exec. This is the seed of workshop 6.
      • Where did the disk go? docker system df, then docker system prune. Read the prompt before answering it.

      Instructor notes

      Timing reality

      Step 3's first build is the slow moment: every build recompiles Go's standard library inside the container (the Go build cache does not survive between builds), so expect 30–60 seconds per build under Docker Desktop, and on a laptop that skipped the prep the golang pull is minutes on top; that student needs the USB stick immediately. Step 4 has three builds in it, which is why it got fifteen minutes. Step 5 and step 6 are the ones to protect; if you are behind after step 4, cut the "talk about it" questions in steps 2 and 3. Step 7's stretch goals absorb any time left over.

      Things students ask

      • "Is this how production works?" Yes for building the image. Running it in production is what workshops 6 and 7 are about; nobody types docker run on a server.
      • "Why is my image huge even with multi-stage?" Almost always a COPY . . that brought in node_modules, a data folder or a virtual environment. .dockerignore, then docker history to find the layer.
      • "Docker Desktop is slow / asks for a licence." Docker Desktop is free for education and small companies; Docker Engine on Linux is always free. Alternatives with the same command line exist (Podman, OrbStack, Colima); the lab is compatible with all of them but has only been tested on Docker.
      • "I cannot delete the data folder." On Linux the files a container writes into a bind mount are owned by root, because the process in the container ran as root. sudo rm -rf data, and see stretch goal 4 for the real fix.
      • "Can I use this for Python / Node?" Same shape: python:3.13-slim or node:22-slim as the base, manifest first, install, copy code. Multi-stage helps less because the runtime is needed at run time, but the manifest-first ordering matters even more.
