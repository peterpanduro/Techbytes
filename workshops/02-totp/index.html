Workshop 2

At a glance

OutcomeEvery student leaves with a totp.ts they wrote themselves that produces the same code as their phone, a deno test suite that pins it to the RFC numbers, and a verifier with a time window, replay protection and a constant-time compare.
Why this topic2FA is on every real system students will work on, yet it is almost never taught. It is also the ideal size: one RFC, one afternoon, no infrastructure, and a very satisfying moment of proof at the end.
ConceptsShared secrets, HMAC, HOTP (RFC 4226), TOTP (RFC 6238), Base32, big-endian packing, dynamic truncation, time windows, replay, constant-time comparison, brute-force arithmetic, and the limits of TOTP (phishing, relay attacks) that motivate passkeys. On the side: WebCrypto, typed arrays, Deno's permission flags and test runner.

Preparation

For students (about 15 minutes)

This is written to be pasted into an email or course page as-is.

1. Install Deno

Deno is a single program that runs TypeScript directly, no build step. Pick the line for your system, run it in a terminal (Terminal on macOS, PowerShell on Windows), then open a new terminal window so it is on your path.

# macOS / Linux
curl -fsSL https://deno.land/install.sh | sh

# Windows (PowerShell)
irm https://deno.land/install.ps1 | iex

# or, if you already use a package manager
brew install deno            # macOS
winget install DenoLand.Deno # Windows

Check it, in the new terminal window. Any version starting with 2 is fine.

deno --version

2. Install an authenticator app on your phone

Any of these work: Google Authenticator, Microsoft Authenticator, Aegis (Android), 2FAS, Ente Auth. If you already use one for a real account, that is fine; we will add a throwaway entry and delete it afterwards. Check that the app can add an account by scanning a QR code and by entering a key manually (every one of the above can).

3. Make sure both clocks are automatic

TOTP is built on both devices agreeing what time it is. Phone: Settings → Date & Time → set automatically. Laptop: same, in your OS settings. You will see why in the talk.

4. The readiness check

Make a folder called totp-lab and open a terminal in it. First, this downloads the one package we use (about 1 MB, so you do not need the venue Wi-Fi for it) and prints a QR code. Scan it with your phone's camera: it should say hello.

deno run --allow-env npm:qrcode@1.5.4 hello

Second, create a file check.ts in the folder with exactly this content, and run it:

const key = await crypto.subtle.importKey("raw", new TextEncoder().encode("workshop"), { name: "HMAC", hash: "SHA-1" }, false, ["sign"]);
const mac = new Uint8Array(await crypto.subtle.sign("HMAC", key, new TextEncoder().encode("ready")));
console.log([...mac].map((b) => b.toString(16).padStart(2, "0")).join(""));

deno run check.ts

Expected output

caad48f0073dc46b2174e2384dfa2e4378f8c823

If you see exactly that, you are ready. If not, bring the error message to the workshop and arrive ten minutes early; we will sort it out before the talk.

5. Optional: editor support

Any editor works. If you use VS Code, the official "Deno" extension gives you type errors as you type, which helps in the lab. Enable it for the totp-lab folder (Command Palette → "Deno: Initialize Workspace Configuration").

If Deno will not install

The fallback is Docker Desktop from workshop 1: in the totp-lab folder run docker run --rm -it -v "$PWD":/work -w /work denoland/deno bash (PowerShell: "${PWD}:/work") and work inside it. Note that the Docker VM's clock on macOS and Windows can drift after the laptop sleeps, which makes codes disagree with the phone; restart Docker Desktop if that happens. Native Deno has no such problem, which is one reason the lab does not use Docker.

The talk: a phone and a server that share a secret

The single idea to land: the code is not sent to the phone; the phone and the server compute it independently from a shared secret and the current time. Everything else in the lab is the mechanics of that sentence. Keep slides sparse; the speaker notes below carry the content.

  1. 1Your phone and the server share a secret1 min Title slide with a six-digit code on it. Ask the room how many have used an authenticator app this week. Ask how the app knows the code when the phone is in airplane mode. Let the question hang.
  2. 2Why passwords alone are not enough2 min Reuse, database leaks, phishing. "Something you know" plus "something you have". SMS codes are the weak version (SIM swap, interception); app codes are what this workshop builds. Mention that every serious system they will work on has this, and very few of them will ever have looked inside it.
  3. 3What it looks like from the outside1 min Show the live widget on this page next to your phone. Same code, no network, changes together every 30 seconds. State the thesis sentence out loud.
  4. 4Ingredient one: a shared secret1 min 20 random bytes generated by the server, shown to the phone exactly once as a QR code, then stored by both sides. That QR code is the secret, which is why "screenshot your 2FA setup" is bad advice. Base32 is just a way to write bytes as capital letters and digits so it survives being typed.
  5. 5Ingredient two: HMAC, a hash with a key2 min A hash turns any input into a fixed-size fingerprint. HMAC is a hash where you also need the key to produce the right fingerprint; without the key you cannot forge one, and from the fingerprint you cannot recover the key. That is all the crypto in this workshop. Browsers and Deno have it built in as WebCrypto: crypto.subtle.sign("HMAC", key, message). It returns a Promise, which is the only reason await shows up in the lab.
  6. 6HOTP: a counter, a MAC, six digits (RFC 4226, 2005)2 min Walk the widget's rows top to bottom: counter packed as 8 bytes, HMAC-SHA1 gives 20 bytes, the low four bits of the last byte pick an offset, take four bytes from there, clear the top bit, take the number mod a million, pad with zeros. Each of those is one line of code in the lab. Point at the yellow and blue bytes in the widget.
  7. 7TOTP: let the clock be the counter (RFC 6238, 2011)2 min counter = floor(unix_time / 30). Both sides can compute it without talking. That is the whole difference between HOTP and TOTP. Consequences: time zones do not matter (unix time is UTC); a phone with a wrong clock produces wrong codes; the server must accept a neighbouring step or two to allow for drift and typing time.
  8. 8The server's job is harder than the phone's2 min Accept a window (RFC 6238 recommends at most one step either side). Never accept the same code twice, or an attacker who sees you type it has 30 seconds. Compare in constant time. Do the brute-force arithmetic on the slide: a million possible codes, three accepted at any moment, so one guess succeeds with probability 3 in a million. Without rate limiting an attacker trying 10 codes per second expects a hit in about nine hours. With a lockout after five attempts, never. The code is only as good as the throttling around it.
  9. 9What TOTP does not protect against1 min A phishing site that asks for your code and forwards it to the real site within 30 seconds wins. The server stores the secret in plaintext by necessity, so a server breach leaks everyone's second factor. Passkeys / WebAuthn fix both by binding the login to the site's origin and using public-key signatures; that is a later workshop. TOTP is still everywhere and still far better than nothing.
  10. 10What we build in the next 90 minutes1 min Show the seven steps. Point out that steps 2 to 4 are checked by deno test against numbers printed in the RFCs, so students know they are right before the phone gets involved. Five-minute break, then step 0.

The lab

Students work in two files, totp.ts (the code) and totp_test.ts (the RFC checks), and run deno test after every step. Every step ends in a checkpoint. Nobody moves to the next step until their checkpoint passes; anyone stuck for more than five minutes pastes the reference code for that step from the full solution and continues. The time budget is deliberately loose in the middle steps and tight at the end.

Type or paste

Every code block is labelled. Type this is the algorithm, 45 lines over the afternoon, written by hand at a pace the whole room can follow. The Bytes alias is there because current TypeScript distinguishes a Uint8Array over a plain ArrayBuffer from one over shared memory, and WebCrypto only accepts the former. One alias saves six annotations later.

Step 1

Generate a secret and write it in Base32

10 min

A TOTP secret is just random bytes. RFC 4226 says at least 16, recommends 20. crypto.getRandomValues fills a typed array from the operating system's cryptographic randomness.

export function newSecret(nbytes = 20): Bytes {
  return crypto.getRandomValues(new Uint8Array(nbytes));
}

Authenticator apps want the secret as Base32 text: the 32 characters A–Z and 2–7, five bits each, no lower case and nothing that looks like anything else, so it survives being read aloud or typed on a phone. Deno's standard library has an encoder, but to keep the lab dependency-free here is one in twelve lines. Paste it under newSecret and read it once: it pushes eight bits in and pulls five bits out until the bytes run out.

const B32 = "ABCDEFGHIJKLMNOPQRSTUVWXYZ234567";

export function toBase32(bytes: Bytes): string {
  let bits = 0, acc = 0, out = "";
  for (const b of bytes) {
    acc = (acc << 8) | b; // push 8 bits in
    bits += 8;
    while (bits >= 5) { // pull 5 bits out at a time
      out += B32[(acc >>> (bits - 5)) & 31];
      bits -= 5;
      acc &= (1 << bits) - 1;
    }
  }
  if (bits > 0) out += B32[(acc << (5 - bits)) & 31]; // pad the last group
  return out;
}

Add the first test to totp_test.ts. The RFC's test secret is the ASCII string 12345678901234567890; its Base32 form is the key printed under the live widget at the top of this page.

import { newSecret, toBase32 } from "./totp.ts";

Deno.test("step 1: secrets are 20 bytes, base32 matches the RFC key", () => {
  assertEquals(newSecret().length, 20);
  assertEquals(toBase32(k), "GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ");
});

Checkpoint 1

deno test prints ok | 1 passed | 0 failed. Then deno run totp.ts twice with a temporary console.log(toBase32(newSecret())) at the bottom: two different 32-character secrets.

Talk about it: why crypto.getRandomValues and not Math.random? (Math.random is predictable from its internal state; the crypto one reads the OS's entropy pool.) Why 32 characters for 20 bytes? (160 bits / 5 bits per character.)

Step 2

HMAC over a counter

15 min

HOTP feeds a counter into HMAC-SHA1. The counter must be exactly 8 bytes, most significant byte first ("big-endian"). A DataView over an 8-byte buffer writes it that way with setBigUint64. WebCrypto wants the secret wrapped as a key first, then signs.

export async function hmacCounter(secret: Bytes, counter: number, hash = "SHA-1") {
  const key = await crypto.subtle.importKey(
    "raw", secret, { name: "HMAC", hash }, false, ["sign"],
  );
  const msg = new Uint8Array(8);
  new DataView(msg.buffer).setBigUint64(0, BigInt(counter)); // 8 bytes, big-endian
  return new Uint8Array(await crypto.subtle.sign("HMAC", key, msg));
}

Now the first number from the RFC. Appendix D of RFC 4226 prints the full HMAC for counter 0:

import { hmacCounter } from "./totp.ts";

Deno.test("step 2: HMAC-SHA1 of counter 0 (RFC 4226 Appendix D)", async () => {
  const mac = await hmacCounter(k, 0);
  const hex = [...mac].map((b) => b.toString(16).padStart(2, "0")).join("");
  assertEquals(mac.length, 20);
  assertEquals(hex, "cc93cf18508d94934c64b65d8ba7667fb7cde4b0");
});

Checkpoint 2

deno test: step 2 passes, so the MAC is 20 bytes and starts cc93cf18…, exactly the first row of the RFC's table.

Common mistakes: setUint32 instead of setBigUint64 (4 bytes, not 8); forgetting BigInt(counter); passing true as the little-endian argument. Each gives a perfectly valid-looking 20-byte MAC that is simply wrong, which is why the RFC vector matters.

Talk about it: change one character of the test secret and rerun. Every byte of the MAC changes. That is the property the whole scheme rests on. Also: this is the exact call the widget at the top of the page makes in the browser; WebCrypto is the same API in both places.

Step 3

Dynamic truncation: 20 bytes to 6 digits

10 min

Twenty bytes is not something a human types. RFC 4226 §5.3 turns it into a number: take the low four bits of the last byte as an offset (0–15), read the four bytes starting there as a big-endian integer, clear the top bit so it is never negative, then take it modulo 106.

export function truncate(mac: Bytes, digits = 6): string {
  const offset = mac[mac.length - 1] & 0x0f; // low 4 bits of the last byte
  const num = new DataView(mac.buffer).getUint32(offset) & 0x7fffffff;
  return String(num % 10 ** digits).padStart(digits, "0");
}

export async function hotp(secret: Bytes, counter: number, digits = 6, hash = "SHA-1") {
  return truncate(await hmacCounter(secret, counter, hash), digits);
}

Checkpoint 3

deno test: step 3 passes, all ten counters. The zero-padding matters: a student whose code prints 7081804 instead of 07081804 in the next step has forgotten padStart.

Talk about it: why & 0x7fffffff? (RFC 4226 says so to avoid signed/unsigned confusion across languages; the top bit is discarded so every implementation agrees. Notice the 31-bit integer column: the last six digits are the code. That is all "mod a million" does.

Step 4

Let the clock be the counter

10 min

This is the entire difference between HOTP and TOTP: counter = floor(unix_time / 30). Unix time is seconds since 1970-01-01 00:00 UTC, so time zones never enter into it. Date.now() is milliseconds, hence the division by 1000 in the default.

export function totp(secret: Bytes, at = Date.now() / 1000, step = 30, digits = 6, hash = "SHA-1") {
  return hotp(secret, Math.floor(at / step), digits, hash);
}

RFC 6238 Appendix B gives 8-digit vectors for the same test secret at fixed times:

import { totp } from "./totp.ts";

Deno.test("step 4: TOTP vectors (RFC 6238 Appendix B, 8 digits)", async () => {
  const vectors: [number, string][] = [[59, "94287082"], [1111111109, "07081804"],
    [1234567890, "89005924"], [2000000000, "69279037"]];
  for (const [t, e] of vectors) assertEquals(await totp(k, t, 30, 8), e, `t=${t}:`);
});

Step 5

Put it on your phone

15 min

Authenticator apps read a URI in the otpauth:// format, usually from a QR code. The label is issuer:account, and the secret is the Base32 string from step 1.

export function otpauthUri(secret: Bytes, account: string, issuer: string) {
  const label = `${encodeURIComponent(issuer)}:${encodeURIComponent(account)}`;
  return `otpauth://totp/${label}?secret=${toBase32(secret)}` +
    `&issuer=${encodeURIComponent(issuer)}&algorithm=SHA1&digits=6&period=30`;
}

Now a separate script, qr.ts, that makes a fresh secret, draws the QR code in the terminal with the package fetched during the prep, also saves it as qr.png in case the terminal version does not scan, and then prints the current code every five seconds:

import QRCode from "npm:qrcode@1.5.4";
import { newSecret, otpauthUri, toBase32, totp } from "./totp.ts";

const s = newSecret();
const uri = otpauthUri(s, "you@example.edu", "TOTP Workshop");
console.log(uri);
console.log(await QRCode.toString(uri, { type: "terminal", small: true }));
await QRCode.toFile("qr.png", uri); // in case the terminal version will not scan
console.log("secret, if you would rather type it in:", toBase32(s));

while (true) {
  console.log(await totp(s), "  valid for", 30 - Math.floor(Date.now() / 1000) % 30, "s");
  await new Promise((r) => setTimeout(r, 5000));
}

Run it. Deno will stop and ask whether the script may write qr.png, because nothing is allowed by default; answer y, or grant exactly that up front:

deno run --allow-write=qr.png qr.ts

Scan the QR code with your phone's authenticator app (or add an account manually and type the Base32 secret). Watch the two codes change together.

Checkpoint 5

Your phone and your terminal show the same six digits, and they roll over to the same new digits at the same moment. Stop the loop with Ctrl-C.

If the codes differ

Nine times out of ten it is a clock. Compare the laptop's clock with the phone's to the second. If the phone is the one that is wrong, turn automatic time off and on again. Anyone on the Docker fallback: the VM's clock drifts after sleep; restart Docker Desktop. Only after both clocks agree is it worth looking at the code.

Talk about it: the QR code is the secret. Anyone who photographs it has your second factor forever. That is why the real setup screens show it once and offer "backup codes" instead of "show QR again". And the permission prompt: a script from npm just asked to write a file, and the runtime made it ask. What would -A have skipped?

Step 6

A verifier a server could use

15 min

Generating codes is the easy half. A server that checks them must handle three things: the user's clock may be a little off and typing takes time, so accept the previous and next step (RFC 6238 §5.2 allows at most one step of delay; accepting one step early as well, for a phone whose clock runs fast, is the common extension); a code must never be accepted twice; and the comparison must not leak information through timing. timingSafeEqual comes from Deno's built-in Node compatibility layer, so it is still not a download.

export class Verifier {
  lastCounter = -1; // highest counter already used

  constructor(private secret: Bytes, private window = 1, private step = 30) {}

  async verify(code: string, at = Date.now() / 1000): Promise<boolean> {
    const now = Math.floor(at / this.step);
    const enc = new TextEncoder();
    for (let c = now - this.window; c <= now + this.window; c++) {
      if (c <= this.lastCounter) continue; // used already, or older than one used
      const expected = await hotp(this.secret, c);
      if (code.length === expected.length &&
          timingSafeEqual(enc.encode(expected), enc.encode(code))) {
        this.lastCounter = c;
        return true;
      }
    }
    return false;
  }
}

Test it with fixed times so the result is deterministic. Google Authenticator shows the code as "151 534"; the login script strips the space, but a copied code with other characters is rejected without a hint:

import { Verifier } from "./totp.ts";

Deno.test("step 6: verifier accepts each step once, rejects replay", async () => {
  const s = newSecret();
  const v = new Verifier(s);
  const t0 = 1_700_000_000;
  assertEquals(await v.verify(await totp(s, t0 - 30), t0), true);  // previous step
  assertEquals(await v.verify(await totp(s, t0 - 30), t0), false); // same code again
  assertEquals(await v.verify(await totp(s, t0), t0), true);       // current step
  assertEquals(await v.verify(await totp(s, t0 + 30), t0), true);  // next step
  assertEquals(await v.verify(await totp(s, t0 + 90), t0), false); // too far ahead
  assertEquals(await v.verify("12345", t0 + 300), false);          // wrong length
});

Checkpoint 6

deno test: all five tests pass. Then the live test, with a third small script, login.ts, that acts as the server: it prints the key both as a URI and as the bare Base32 text, so add it to the phone by typing (or reuse the QR trick from qr.ts), then type codes at it. It should accept a code once and refuse it the second time.

import { newSecret, otpauthUri, toBase32, Verifier } from "./totp.ts";

const s = newSecret();
console.log("add this key to your phone:", otpauthUri(s, "you@example.edu", "TOTP Workshop"));
console.log("or type it in:", toBase32(s));
const v = new Verifier(s);
while (true) {
  const code = prompt("code from your phone (empty to quit):");
  if (!code) break;
  console.log(await v.verify(code.replace(/\s/g, "")) ? "accepted" : "rejected");
}

deno run login.ts

Talk about it: replace timingSafeEqual(...) with expected === code. It still passes every test. Why is it wrong anyway? (=== stops at the first differing character, so response time leaks how many leading digits were right. Against a network it is hard to exploit for six digits, but the habit matters: any comparison of a secret uses constant-time compare, always.) Why the length check in front of it? (timingSafeEqual throws on inputs of different length rather than returning false, and a user who types five digits should get "rejected", not a crash.) Why keep lastCounter rather than a set of used codes? (One integer per user, and it also rejects a code from an older step after a newer one was used.)

Step 7

Wrap-up and stretch goals

10 min

Bring the room back together for five minutes, then let the fast students pick a stretch goal.

Wrap-up points

  • Everything they built runs on APIs that ship with the runtime; the "crypto" was one call to crypto.subtle.sign. The design work is all in what surrounds it: randomness, encoding, windows, replay, timing, throttling.
  • Redo the slide-8 arithmetic with their own verifier: window 1 accepts 3 codes out of 106. Ask what a login endpoint needs around the verifier before it is safe (rate limit per account, lockout, logging).
  • Ask them to delete the throwaway account from their phone and to never reuse a secret printed on a projector.

Stretch goals (pick one)

  • The decoder. Write fromBase32, the mirror image of the pasted encoder (push five bits in, pull eight out), and add a round-trip test. A server that stores secrets as Base32 text needs it.
  • Other hashes and sizes. Make it produce the RFC 6238 SHA-256 vector (secret is the ASCII digits repeated to 32 bytes, t=59 → 46119246, hash name "SHA-256") and SHA-512 (64 bytes, t=59 → 90693936). Then put algorithm=SHA256 in the URI and see whether their phone app honours it. (Google Authenticator has historically ignored algorithm and period, which is why nearly every site sticks to SHA-1, 6 digits, 30 seconds.)
  • Drift experiment. Feed totp(s, Date.now() / 1000 + 40) to the verifier. Then + 70. Where does the window stop helping? What would a server do if a user's codes are consistently one step ahead? (RFC 6238 §6 suggests recording the drift after a successful login and applying it next time.)
  • Brute force it. Write a loop that guesses every code from 000000 to 999999 against a Verifier at a fixed time. How many guesses until success, on average? Then add a counter of failed attempts and lock after five. This is the whole argument for rate limiting in one experiment.
  • Serve it. Wrap the verifier in Deno.serve with a POST /login that takes a code, and note that the first flag you need is --allow-net. This is the seed of workshop 9, the OAuth workshop.

// TOTP from scratch — complete lab file. Deno, no dependencies.
import { timingSafeEqual } from "node:crypto";

type Bytes = Uint8Array<ArrayBuffer>; // a Uint8Array that WebCrypto accepts

// ---------- Step 1: a shared secret ----------
export function newSecret(nbytes = 20): Bytes {
  return crypto.getRandomValues(new Uint8Array(nbytes));
}

const B32 = "ABCDEFGHIJKLMNOPQRSTUVWXYZ234567";

export function toBase32(bytes: Bytes): string {
  let bits = 0, acc = 0, out = "";
  for (const b of bytes) {
    acc = (acc << 8) | b; // push 8 bits in
    bits += 8;
    while (bits >= 5) { // pull 5 bits out at a time
      out += B32[(acc >>> (bits - 5)) & 31];
      bits -= 5;
      acc &= (1 << bits) - 1;
    }
  }
  if (bits > 0) out += B32[(acc << (5 - bits)) & 31]; // pad the last group
  return out;
}

// ---------- Step 2: HMAC over a counter ----------
export async function hmacCounter(secret: Bytes, counter: number, hash = "SHA-1") {
  const key = await crypto.subtle.importKey(
    "raw", secret, { name: "HMAC", hash }, false, ["sign"],
  );
  const msg = new Uint8Array(8);
  new DataView(msg.buffer).setBigUint64(0, BigInt(counter)); // 8 bytes, big-endian
  return new Uint8Array(await crypto.subtle.sign("HMAC", key, msg));
}

// ---------- Step 3: dynamic truncation ----------
export function truncate(mac: Bytes, digits = 6): string {
  const offset = mac[mac.length - 1] & 0x0f; // low 4 bits of the last byte
  const num = new DataView(mac.buffer).getUint32(offset) & 0x7fffffff;
  return String(num % 10 ** digits).padStart(digits, "0");
}

export async function hotp(secret: Bytes, counter: number, digits = 6, hash = "SHA-1") {
  return truncate(await hmacCounter(secret, counter, hash), digits);
}

// ---------- Step 4: the clock is the counter ----------
export function totp(secret: Bytes, at = Date.now() / 1000, step = 30, digits = 6, hash = "SHA-1") {
  return hotp(secret, Math.floor(at / step), digits, hash);
}

// ---------- Step 5: the URI a phone can scan ----------
export function otpauthUri(secret: Bytes, account: string, issuer: string) {
  const label = `${encodeURIComponent(issuer)}:${encodeURIComponent(account)}`;
  return `otpauth://totp/${label}?secret=${toBase32(secret)}` +
    `&issuer=${encodeURIComponent(issuer)}&algorithm=SHA1&digits=6&period=30`;
}

// ---------- Step 6: a verifier a server could use ----------
export class Verifier {
  lastCounter = -1; // highest counter already used

  constructor(private secret: Bytes, private window = 1, private step = 30) {}

  async verify(code: string, at = Date.now() / 1000): Promise<boolean> {
    const now = Math.floor(at / this.step);
    const enc = new TextEncoder();
    for (let c = now - this.window; c <= now + this.window; c++) {
      if (c <= this.lastCounter) continue; // used already, or older than one used
      const expected = await hotp(this.secret, c);
      if (code.length === expected.length &&
          timingSafeEqual(enc.encode(expected), enc.encode(code))) {
        this.lastCounter = c;
        return true;
      }
    }
    return false;
  }
}

Deno.test("step 4: TOTP vectors (RFC 6238 Appendix B, 8 digits)", async () => {
  const vectors: [number, string][] = [[59, "94287082"], [1111111109, "07081804"],
    [1234567890, "89005924"], [2000000000, "69279037"]];
  for (const [t, e] of vectors) assertEquals(await totp(k, t, 30, 8), e, `t=${t}:`);
});

import { Verifier } from "./totp.ts";

Deno.test("step 6: verifier accepts each step once, rejects replay", async () => {
  const s = newSecret();
  const v = new Verifier(s);
  const t0 = 1_700_000_000;
  assertEquals(await v.verify(await totp(s, t0 - 30), t0), true);  // previous step
  assertEquals(await v.verify(await totp(s, t0 - 30), t0), false); // same code again
  assertEquals(await v.verify(await totp(s, t0), t0), true);       // current step
  assertEquals(await v.verify(await totp(s, t0 + 30), t0), true);  // next step
  assertEquals(await v.verify(await totp(s, t0 + 90), t0), false); // too far ahead
  assertEquals(await v.verify("12345", t0 + 300), false);          // wrong length
});

Running the room

Instructor notes

Timing reality

Steps 2 and 3 are where the room spreads out; that is why they have the most slack. If you are more than ten minutes behind at the end of step 3, cut the "talk about it" discussions in steps 4 and 6 and keep the code. Step 5 is the payoff and must not be rushed: budget for at least one student whose phone clock is wrong. Step 7's stretch goals absorb any time left over.

Things students ask

  • "Why SHA-1? Isn't it broken?" SHA-1 collisions are practical, but HMAC-SHA1 does not depend on collision resistance and has no known practical attack. The RFCs allow SHA-256 and SHA-512 too; apps' patchy support is why SHA-1 is still the default.
  • "Why is everything async?" WebCrypto returns Promises so that browsers can do the work off the main thread. Deno keeps the same API, so the same code runs in both. The cost is one await per call; the benefit is that the lab's HMAC is literally the browser's HMAC.
  • "Where does the server keep the secret?" Encrypted at rest at best, but it has to be decryptable to verify, so a full server compromise leaks it. That limitation is one motivation for passkeys, which store only a public key on the server.
  • "Can I use this in a real project?" Use a maintained library (otpauth on npm/JSR for TypeScript, pquerna/otp in Go) plus rate limiting; the point of writing it by hand is to be able to read those libraries and their bug reports.
  • "What about the codes banks send by SMS?" Usually not TOTP at all: a random code stored server-side and sent over a channel that can be intercepted or SIM-swapped. Same user experience, much weaker security.
