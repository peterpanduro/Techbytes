Git for the Things That Go Wrong

A prepared repository with planted problems: a commit that broke the tests, four WIP commits that need squashing, a hard reset and a deleted branch to undo, a merge conflict to resolve by hand, and a pre-commit hook that says no. No code to write; thirty-eight commands, and after each one the repository is still whole.

  • 15 min talk
  • 90 min guided lab
  • ~15 min student prep, one week before
  • Basic git only: add, commit, push
  • No code; ~40 commands
  • Any OS (Git Bash on Windows)
Interactive · pointers, not deletions

The last six commits on main, with the real hashes from the lab. A branch is a label on a commit; HEAD is a label on a branch. Press the commands and watch what moves. Nothing is ever removed.

  Workshop 5
  
At a glance

  

    
OutcomeEvery student leaves having repaired six git "disasters" with their own hands, and with the model that makes them unfrightening: a commit is a snapshot with a parent, a branch is a label on a commit, HEAD is a label on a branch, and nothing committed is deleted by reset, rebase or branch deletion. They can find a breaking commit with bisect, tidy a branch with rebase -i, recover from the reflog, resolve a conflict, and install a hook.

    
Why this topicEveryone in the room uses git daily and most have only ever used add, commit, push and pull. The first time something goes wrong they delete the folder and clone again, and the second time they lose a day's work. One afternoon of breaking a repository on purpose, in a safe copy, replaces that fear with a handful of habits. It is also the breather of the year: no runtime to install, no code to type, placed between the security block and the infrastructure block.

    
ConceptsCommits as content-addressed snapshots, the parent chain, why hashes are the same on every laptop today; branches and HEAD as pointers; reachable versus unreachable, and the reflog; bisect as binary search and bisect run; interactive rebase (pick, squash, reword, fixup) and the rule about rewriting shared history; revert versus reset; merge conflicts and the three markers; hooks and --no-verify; stash, worktrees, log -S, blame -L.

    
Assumed knowledgeHas used git before: knows what a commit and a branch are for, has run git add, git commit and git push. Can open a terminal. No knowledge of git internals, rebase, bisect or hooks is assumed.

    
LanguageNone. The practice project is a five-line shell script with a shell test script, both pasted by the setup script and never edited beyond one appended line. Every command is a git command.

    
Students needLaptop with git 2.23 or newer (any git from the last five years), a terminal (Terminal on macOS, Git Bash on Windows, any shell on Linux), a text editor git can open: VS Code or nano, configured in the prep. Wi-Fi is not needed at any point.

    
Room needsProjector. Nothing else.

    
Timing15 min talk · 5 min break · 90 min lab (seven steps, each with a checkpoint that must pass before moving on).

Preparation


  
For students (about 15 minutes)

  
This is written to be pasted into an email or course page as-is.


  
1. Install git, and use the right terminal

  
Windows: install Git for Windows from git-scm.com/install/windows (or winget install --id Git.Git -e --source winget). It includes Git Bash; use Git Bash, not PowerShell, for everything in this workshop, because the setup script and the test script are bash scripts. The git commands themselves are identical everywhere. macOS: xcode-select --install gives you Apple's git, or brew install git for the current one. Linux: sudo apt install git or sudo dnf install git. Then:


git --version

  
Anything from 2.23 onwards is fine; the current release is 2.55. Older than 2.23 and git switch does not exist: upgrade.


  
2. Tell git who you are, if you never have


git config --global user.name "Your Name"
git config --global user.email "you@example.com"

  
You will make a few commits in the lab and git refuses to commit without these.


  
3. Give git an editor it can open

  
Twice in the lab git opens a file for you to edit and waits until you close it. Pick one of these and run it once:


git config --global core.editor "code --wait"      # VS Code; needs the "code" command on your PATH
git config --global core.editor nano               # or nano, which Git Bash and macOS include

  
To check: run git config --global --edit. Your config file must open in the editor you chose, and the terminal must wait until you close it. If VS Code says code: command not found, open VS Code, press F1, run "Shell Command: Install 'code' command in PATH", and try again; or use nano.


  
4. The readiness check

  
In Git Bash or Terminal:


echo ready | git hash-object --stdin

  
Expected output
395527df662d5fdf4b00c5f1cd9b8d7ac048e127, exactly. That is the name git gives to a file containing the word "ready", and it is the same on every computer in the world, which is the idea the whole afternoon is built on. If you get b81bd720fc3e7f4662c75969e274e5500e06f5a4 you are in PowerShell, which sends the word with Windows line endings: switch to Git Bash. If you get "command not found", git is not on your PATH.


  
5. Optional: build the practice repository once

  
Save make-repo.sh into an empty folder and run bash make-repo.sh there. It prints Top of main: f063a35 CHANGELOG: prepare 1.1. If it does, you are ready. Delete the git-lab folder it made before the workshop (rm -rf git-lab); we build it again together so everyone starts from the same place.


  
If git will not install
A university-managed Windows laptop without admin rights can still install Git for Windows with the portable ("thumbdrive edition") build from the same download page, which needs no administrator. Everything else on this page works from it.

The talk: everything is a pointer

  
The single idea to land: a commit is a snapshot that names its parent, a branch is a label on a commit, HEAD is a label on a branch, and none of the frightening commands deletes a commit; they move labels. Once that is believed, every step of the lab is "find the hash, put the label back".

  
    
    
  1. 1Nothing committed is ever lost1 min
      Title slide. Ask who has typed reset --hard and felt their stomach drop, deleted a branch that was the only copy, or spent an afternoon reading diffs to find which commit broke the build. The sentence the afternoon hangs on: nothing you have committed is ever lost. Every git disaster is a label pointing at the wrong place, and labels move.
    2. 
    
  2. 2A commit is a snapshot that names its parent2 min
      Not a diff: a snapshot of every file, plus author, date, message and the hash of the parent. The hash is computed from all of it, so it names the snapshot and the whole history behind it. Consequence one: everyone in the room runs the same script with fixed names and dates and gets the same hashes; the top commit is f063a35 on every laptop. Consequence two: commits live in a database in .git, and nothing in today's lab removes one. Reset, rebase and branch deletion move labels; unlabelled commits sit there for 30 days at the very least.
    3. 
    
  3. 3Branches are sticky notes; HEAD is a note on a note2 min
      .git/refs/heads/main is a 41-byte file: a hash and a newline. Commit makes a new commit whose parent is that hash, then rewrites the file. HEAD is a file saying ref: refs/heads/main. Read every scary command through this: switch rewrites HEAD; reset moves the branch HEAD points at (--hard also rewrites the working files); branch -D deletes the note; rebase makes new commits and moves the note. Unreachable means no note leads there. Unreachable is not deleted.
    4. 
    
  4. 4The reflog2 min
      Use the widget on this page. Every move HEAD makes appends a line: hash and reason. Press reset: main jumps back two to 95d7f26, the two newest commits go hollow but stay. Press reflog: HEAD@{1} is where you were, with its hash. Press branch: a new label and everything is reachable again. Three caveats: the reflog is local, not pushed; entries for unreachable commits, which is what a rescue needs, expire after 30 days (90 for the rest); it only records moves, so uncommitted work is the one thing git can lose. Commit early, commit ugly, tidy later.
    5. 
    
  5. 5Bisect: binary search over history1 min
      One good commit, one bad commit, git checks out the middle one; you say good or bad, it halves again. Ten commits take three runs, a thousand take ten. With a script that exits 0 on pass and non-zero on fail, git bisect run does the saying for you and names the culprit. Step 1 is exactly this with our test script.
    6. 
    
  6. 6Rewriting history: interactive rebase and the one rule2 min
      The to-do list: one line per commit, oldest first, verbs pick, reword, squash, fixup, drop; reorder lines to reorder commits. Rebase cannot edit commits (the hash is the content); it makes new ones and moves the label, so the four WIP commits squashed in step 2 are still there, unreachable, showable by hash. The rule: rewrite anything nobody else has; never rewrite a pushed commit that someone may have built on. Rebase your own branch before the pull request; never rebase main.
    7. 
    
  7. 7A conflict is a question, not an error2 min
      Both branches changed the same line and git will not guess. Between <<<<<<< HEAD and ======= is your side; between ======= and >>>>>>> is theirs; everything outside merged already. Edit the region into the line you want, often both sides combined, delete the markers, git add to say "resolved", git commit to finish. git merge --abort puts everything back. The lab's conflict is a README tagline: one branch fixed a typo, the other made it longer; the right answer uses both. Stretch: rerere remembers resolutions.
    8. 
    
  8. 8Hooks: a script that says no1 min
      A script in .git/hooks with the right name and the executable bit; pre-commit runs before the commit exists and a non-zero exit means no commit. Hooks are not committed or shared, so teams install them with a tool. --no-verify skips them: a seatbelt, not a lock. The day you type it, be able to say why.
    9. 
    
  9. 9The small tools: stash, worktree, -S, blame -L1 min
      Stash shelves uncommitted changes so you can switch; worktree checks out a second branch into a second folder sharing the same repository; log -S finds the commits that added or removed an exact string, which is how you find where a line came from when blame points at a refactor; blame -L shows who last touched a line range. Not disaster tools: the tools that keep you out of one.
    10. 
    
  10. 10The next 90 minutes1 min
      Seven steps: build the same repository for everyone; bisect and revert; squash four WIP commits; a hard reset and a deleted branch, both repaired from the reflog; a merge conflict by hand; a pre-commit hook; stash, worktree and pickaxe. Every step ends in a checkpoint. Five-minute break, then step 0.
    11.

The lab

  
Students work in one terminal (Git Bash on Windows) with their editor beside it. Every step ends in a checkpoint. Nobody moves to the next step until their checkpoint passes; anyone stuck for more than five minutes waves, and every step can be restarted from a known commit hash, because the hashes are the same on every laptop.

Step 1
Bisect: which commit broke the test?
15 min

    
The tests fail on main and, the changelog says, passed at v1.0. Ten commits in between. Tell git one bad commit (where you are) and one good one, and it checks out the middle:


git bisect start
git bisect bad
git bisect good v1.0


Bisecting: 4 revisions left to test after this (roughly 2 steps)
[4c42b15625786affdee895a959f04caa4bdedf71] README: contributing section

    
You could now run ./test.sh and type git bisect good or git bisect bad, and repeat. Or, since the test script exits 0 when it passes and 1 when it fails, let git do the repeating:


git bisect run ./test.sh


running './test.sh'
ok    100 -> 212
ok    0 -> 32
ok    -40 -> -40
FAIL  212 f -> 195 (wanted 100)
FAIL  32 f -> 15 (wanted 0)
Bisecting: 2 revisions left to test after this (roughly 1 step)
[08e14b18418e2643c52e5745cac2af59b5f3a741] Simplify f_to_c arithmetic
running './test.sh'
  ... FAIL again ...
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[4708ac82c07ad96fb9bb936cb96999c00aafe06d] Refactor: one function per conversion
running './test.sh'
  ... all five ok ...
08e14b18418e2643c52e5745cac2af59b5f3a741 is the first bad commit
commit 08e14b18418e2643c52e5745cac2af59b5f3a741
Author: Maja Lindqvist <maja@example.com>
Date:   Tue Mar 3 04:00:00 2026 +0000

    Simplify f_to_c arithmetic

 temp.sh | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit

    
Three test runs, and it names the commit: 08e14b1 Simplify f_to_c arithmetic. Look at what it changed with git show 08e14b1 if you like (a dropped pair of parentheses: $1 - 32 * 5 / 9). Now leave bisect mode, which puts you back on main, and undo that commit with a new commit rather than by editing history:


git bisect reset
git revert --no-edit 08e14b1
./test.sh

    
Checkpoint 1
bisect run ended with 08e14b18418e2643c52e5745cac2af59b5f3a741 is the first bad commit. After the revert, git log --oneline -1 shows Revert "Simplify f_to_c arithmetic" on top (your hash, not ours: you are the author) and ./test.sh prints all tests passed.

    
Talk about it: why revert and not reset? (The bad commit was pushed, in the story; revert adds history, reset rewrites it.) How many runs would bisect need for a thousand commits? (Ten.) What would you do if some commit in the middle did not build at all? (Exit 125 from the script tells bisect to skip it; stretch goal.)

  


  

    
Step 2
Interactive rebase: four WIP commits into one
15 min

    
Ola added Kelvin support on a branch, in four commits called WIP, wip kelvin, fix, and WIP tests and help. The feature is fine; the history is not something you would open a pull request with. Squash the four into one commit with a message that says what it does.


git switch feature/kelvin
git log --oneline main..
git rebase -i HEAD~4

    
main.. means "commits on this branch that main does not have": the four. rebase -i HEAD~4 opens your editor with a to-do list, oldest commit first:


pick cb1d805 WIP
pick 1096f61 wip kelvin
pick c0ecc06 fix
pick 037ffcf WIP tests and help

# Rebase 4708ac8..037ffcf onto 4708ac8 (4 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# ...
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's log message ...
# d, drop <commit> = remove commit
# ...
# If you remove a line here THAT COMMIT WILL BE LOST.

    
Change the verb on lines 2, 3 and 4 from pick to squash (leave line 1 alone: squash melds a commit into the one above it, so the first must stay). Do not touch the hashes. Save and close (nano: Ctrl-O, Enter, Ctrl-X; VS Code: Ctrl-S or Cmd-S, then close the tab):


pick cb1d805 WIP
squash 1096f61 wip kelvin
squash c0ecc06 fix
squash 037ffcf WIP tests and help

    
Git replays the four commits and opens the editor again, now with all four messages pasted together. Delete everything that is not a comment and write one message: first line Add Kelvin conversion, a blank line, then a sentence such as ./temp.sh 300 k prints 27, and test.sh checks it. Save and close the same way. Then look:


git log --oneline -3


33c9f80 (HEAD -> feature/kelvin) Add Kelvin conversion
4708ac8 Refactor: one function per conversion
707e21a (tag: v1.0) Release 1.0

    
Checkpoint 2
The branch has one commit above 4708ac8, titled Add Kelvin conversion (your hash differs from 33c9f80). git show --stat HEAD lists temp.sh and test.sh, and the author is still Ola Berg: squash keeps the first commit's author. ./test.sh prints six ok lines including 300 k -> 27.

    
If the editor fights you
The whole edit can be done without an editor. Paste this and the rebase happens with lines 2–4 as fixup (like squash, but the message is discarded), then the message is set afterwards:


GIT_SEQUENCE_EDITOR="sed -i.bak '2,4s/^pick/fixup/'" GIT_EDITOR=true git rebase -i HEAD~4
git commit --amend -m "Add Kelvin conversion"

    
Use it to get a stuck student to the checkpoint, then have them run git reflog and git show cb1d805 to see that the WIP commits are still there. If a rebase goes wrong halfway, git rebase --abort returns to exactly where the branch was.

    
Common mistakes: squashing line 1 ("cannot squash without a previous commit"; abort and retry); deleting a line, which drops that commit (the to-do list warns you in capitals); the editor opened, the student closed the terminal instead, and git is now waiting: git rebase --abort. And the question that always comes: the old commits cb1d805 to 037ffcf are not in the log any more, but git show 037ffcf still works. Rebase made new commits and moved the label.

  


  

    
Step 3
Two accidents and the reflog
10 min

    
Back on main, go and look at the colour experiment, come back, and delete the branch, as someone tidying up on a Friday would:


git switch main
git switch experiment/color
git switch main
git branch -D experiment/color


Deleted branch experiment/color (was 54ad38b).

    
(-d, lower case, would have refused: "not fully merged". -D is the "I know what I am doing" spelling, and you did not.) Now the second accident. You meant to undo one local change and typed this:


git reset --hard HEAD~3


HEAD is now at 95d7f26 Fix typo in README

    
Three commits, including your revert from step 1, are gone from git log, and ./test.sh fails again. Nothing was deleted. The label main moved three commits down, and git wrote down where it was:


git reflog


95d7f26 HEAD@{0}: reset: moving to HEAD~3
f108af5 HEAD@{1}: checkout: moving from experiment/color to main
54ad38b HEAD@{2}: checkout: moving from main to experiment/color
f108af5 HEAD@{3}: checkout: moving from feature/kelvin to main
33c9f80 HEAD@{4}: rebase (finish): returning to refs/heads/feature/kelvin
33c9f80 HEAD@{5}: rebase (squash): Add Kelvin conversion
  ...
f108af5 HEAD@{10}: revert: Revert "Simplify f_to_c arithmetic"
f063a35 HEAD@{11}: checkout: moving from 4708ac82c07ad96fb9bb936cb96999c00aafe06d to main
  ... one line per bisect step ...
f063a35 HEAD@{15}: commit: CHANGELOG: prepare 1.1
  ... every commit the script made ...
2d9e498 HEAD@{51}: commit (initial): Initial commit

    
Newest first (git says checkout even when you typed switch; they are the same move). HEAD@{0} is the reset. HEAD@{1} is where HEAD was before it: the revert commit, on main. And HEAD@{2} is the moment you looked at experiment/color, with the hash of its tip, 54ad38b. Both rescues are one command each:


git reset --hard HEAD@{1}
git branch experiment/color 54ad38b

    
Checkpoint 3
git log --oneline --graph --all looks exactly as it did at the end of step 2: the revert on top of main, and experiment/color back on 54ad38b. ./test.sh passes again.

    
Talk about it: why did HEAD@{2} know about the experiment branch? (Because you had switched to it; had you deleted it without ever checking it out, the reflog would not help, but the "was 54ad38b" in the delete message would.) What is the one thing the reflog cannot bring back? (Changes you never committed. reset --hard throws those away for real.) How long do you have? (30 days: both rescues here are unreachable commits, and gc.reflogExpireUnreachable defaults to 30 days; entries for commits still on a branch last 90.)

  


  

    
Step 4
A merge conflict, by hand
15 min

    
feature/tagline rewrote the README's first sentence. On main, meanwhile, somebody fixed a typo in that same sentence. Merge it:


git merge feature/tagline
git status


Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

    
git status says both modified: README.md under "Unmerged paths", and tells you the two ways out: fix and commit, or git merge --abort. Open README.md in your editor (nano README.md, or code README.md; VS Code offers "Accept Current / Incoming / Both Changes" buttons above the markers, and "Both" would keep two lines, so edit by hand this once):


# tempconv

<<<<<<< HEAD
A tiny temperature converter.
=======
A tiny temperture converter for the shell.
>>>>>>> feature/tagline

## Usage

    
Three marker lines. Between <<<<<<< HEAD and ======= is your side, main: the typo is fixed. Between ======= and >>>>>>> feature/tagline is theirs: longer, typo intact. Everything else in the file merged on its own; the second usage example from the branch is already there. The right answer is both: replace the five lines with the single line A tiny temperature converter for the shell. and save. Then tell git you have resolved it, and finish the merge:


git add README.md
git commit --no-edit
git log --oneline --graph -6


*   e5db6cf (HEAD -> main) Merge branch 'feature/tagline'
|\
| * 5fed98d (feature/tagline) README: second usage example
| * eb748f7 README: longer tagline
* | f108af5 Revert "Simplify f_to_c arithmetic"
* | f063a35 CHANGELOG: prepare 1.1
* | 4128a3a Bump version to 1.1 in --help

    
Checkpoint 4
A merge commit on top of main with two parents, drawn as a fork in the graph. grep -c '<<<<' README.md prints 0: no markers survived. The first sentence of the README reads "A tiny temperature converter for the shell."

    
Common mistakes: committing with the markers still in the file (git lets you; the hook in step 5 would not); resolving by keeping one side when both were needed; running git commit -a and sweeping in an unrelated change. Stretch, five minutes: git config rerere.enabled true, then git reset --hard HEAD~1, merge again and resolve again: git prints Recorded resolution for 'README.md'. Reset and merge a third time: Resolved 'README.md' using previous resolution, and the file is already fixed; you only git add and commit. Step 5
A pre-commit hook that says no
10 min

    
A hook is a script git runs at a fixed moment. pre-commit runs before the commit exists; if it exits non-zero, there is no commit. Ours runs the tests and refuses any commit that adds a line containing TODO. Paste it into a new file at exactly .git/hooks/pre-commit (no extension; the folder already exists and contains .sample files, which are ignored):

    
.git/hooks/pre-commit


#!/usr/bin/env bash
# pre-commit: refuse the commit if the tests fail or if it adds a TODO.
# Git runs this before every commit. Exit 0 = go ahead, anything else = refuse.
bad=0
if ! ./test.sh >/dev/null; then
  echo "pre-commit: ./test.sh fails. Fix it, or --no-verify if you really must." >&2
  bad=1
fi
if git diff --cached | grep -E '^\+.*TODO' >/dev/null; then
  echo "pre-commit: this commit adds a TODO. Do it or drop it:" >&2
  git diff --cached | grep -E '^\+.*TODO' >&2
  bad=1
fi
exit $bad

    
Make it executable, then make a change that breaks both rules at once and try to commit it:


chmod +x .git/hooks/pre-commit
echo 'echo done # TODO: remove this' >> temp.sh
git commit -am "Debug output"


pre-commit: ./test.sh fails. Fix it, or --no-verify if you really must.
pre-commit: this commit adds a TODO. Do it or drop it:
+echo done # TODO: remove this

    
No commit was made; git log --oneline -1 still shows the merge. Throw the change away and confirm the tree is clean:


git restore temp.sh

The commit was refused with both messages, git log --oneline -1 still shows Merge branch 'feature/tagline', and after git restore, git status says nothing to commit, working tree clean. On Windows, chmod prints nothing and changes nothing, and the hook runs anyway.

    
Talk about it: git commit --no-verify would have gone through. When is that right? (A work-in-progress commit on your own branch that you will squash, when the tests take twenty minutes.) When is it wrong? (Any time the answer to "why?" is "the hook was annoying".) Why is the hook not in the repository? (It lives in .git, which is never pushed, so every clone needs it installed: teams do that with a tool such as pre-commit or a one-line core.hooksPath setting pointing at a committed folder.) The hook greps the staged diff, not the files: an old TODO already in the project does not block you, only a new one.

#   f = from Fahrenheit to Celsius
c_to_f() { echo $(( $1 * 9 / 5 + 32 )); }
f_to_c() { echo $(( $1 - 32 * 5 / 9 )); }

if [ "${1:-}" = "--help" ]; then
  echo "tempconv 1.1"
  echo "usage: temp.sh DEGREES [c|f]"
  exit 0
fi
n=$1
unit=${2:-c}
case $unit in
  c) c_to_f "$n" ;;
  f) f_to_c "$n" ;;
  *) echo "unknown unit: $unit" >&2; exit 2 ;;
esac

#!/usr/bin/env bash
# pre-commit: refuse the commit if the tests fail or if it adds a TODO.
# Git runs this before every commit. Exit 0 = go ahead, anything else = refuse.
bad=0
if ! ./test.sh >/dev/null; then
  echo "pre-commit: ./test.sh fails. Fix it, or --no-verify if you really must." >&2
  bad=1
fi
if git diff --cached | grep -E '^\+.*TODO' >/dev/null; then
  echo "pre-commit: this commit adds a TODO. Do it or drop it:" >&2
  git diff --cached | grep -E '^\+.*TODO' >&2
  bad=1
fi
exit $bad

Instructor notes

  
Timing reality

  
Step 2 is the one that can run away: the editor. Anyone whose editor does not open, or opens without waiting, loses ten minutes, which is why the prep insists on core.editor and why the non-interactive GIT_SEQUENCE_EDITOR line is on the page. Use it without hesitation to get a student to the checkpoint. Steps 1 and 3 are quick and reliable; step 4 takes longer than it looks because people read the markers twice. If you are behind after step 4, cut the rerere stretch and the "talk about it" in step 5. Step 7's stretch goals absorb whatever is left. The lab has no network dependency and no long-running command, so the timings on this page are close to real.

  
Things students ask

  
    
    
  • "My hash is different." For a commit the script made: the script was edited after download; nothing in a global git config changes them (tested with core.autocrlf, commit.gpgsign, another identity and no config at all), and a CRLF-mangled script does not run at all. A git older than 2.23 fails at the first git switch rather than producing other hashes. Re-download and rebuild. For a commit they made themselves: correct, they are the author and it is now.
    • 
    
  • "Does this work on GitHub?" Everything here is local. GitHub sees commits when you push; a rewritten branch needs git push --force-with-lease, and that is exactly the case the "never rewrite shared history" rule is about. Reflog and bisect never leave your laptop.
    • 
    
  • "Why revert instead of just fixing the line?" Fixing the line by hand is fine too and yields the same file. Revert records why ("this reverts commit 08e14b1") and is mechanical, which matters when the bad commit touched twelve files.
    • 
    
  • "Can I squash after pushing?" Yes, and then you force-push, and anyone who pulled the old commits has a mess. On a branch only you work on, before the review, it is normal; on main, never.
    • 
    
  • "Is the reflog backed up?" No. It is in .git/logs, on this laptop, and a fresh clone has an empty one. It is a safety net for your own moves, not a backup.
    • 
    
  • "Why Git Bash and not PowerShell?" Only because the setup script, the test script and the hook are bash. Every git command on this page is the same in PowerShell; students can switch back after today.
    •
