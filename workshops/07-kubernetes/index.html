Kubernetes on a Laptop

Take workshop 6's three containers (an API, a worker, Redis) and run them on a real Kubernetes cluster that lives inside Docker on your laptop. Type one Deployment, scale it to three, kill a pod and watch it come back, roll out a new image and roll it back.

  • 15 min talk
  • 90 min guided lab
  • ~30 min student prep, one week before
  • Builds on workshop 6
  • YAML + kubectl, no code
  • Any OS
Interactive · desired vs actual

A Deployment says how many pods should exist. A controller loop compares that with what does exist and fixes the difference, forever. Change the number. Kill a pod. Watch.

    Workshop 7

    At a glance

    OutcomeEvery student leaves having run a three-service application on a Kubernetes cluster they created on their own laptop, with the four objects that matter (Pod, Deployment, ReplicaSet, Service) in their fingers, and having seen with their own eyes that a deleted pod comes back and a bad rollout can be undone with one command. They keep three YAML files that would work unchanged on a cloud cluster.
    Why this topicKubernetes is where most containers end up, and it is taught badly: either as a wall of YAML or as a vendor console. The one idea underneath it (you declare what should be true, a controller keeps making it true) is small, and once it lands, every command and every field on this page is a consequence. Doing it on a laptop, on last week's images, keeps it concrete.
    ConceptsCluster, node, control plane and API server; desired state and controllers; Pods as the unit; Deployments and ReplicaSets; labels and selectors; Services and in-cluster DNS; kubectl get / describe / logs / apply / expose / scale / rollout; image pull policy and why :latest bites; rolling updates, revisions and rollback; what a laptop cluster does not have (load balancers, persistent storage, more than one node).
    Assumed knowledgeWorkshop 6: what an image is, what compose.yaml did, and that the API finds Redis by the name redis. Nothing about Kubernetes.
    LanguageNone. YAML and kubectl only. The images from workshop 6 are used as they are; step 6 changes one string in the API and rebuilds it to have something to roll out.
    Students needLaptop with Docker Desktop (or Docker Engine on Linux), kind and kubectl installed per the prep, the kindest/node image already downloaded, workshop 6's folder with its images rebuilt as api:1 and worker:1.
    Room needsProjector. No Wi-Fi is needed if the prep was done: every image the cluster uses is loaded from the laptop's Docker.
    Timing15 min talk · 5 min break · 90 min lab (seven steps, each with a checkpoint that must pass before moving on).

    Preparation

    For students (about 30 minutes, plus a download)

    This is written to be pasted into an email or course page as-is. It assumes you still have your workshop 6 folder and that Docker works.

    1. Give Docker enough memory

    The cluster runs inside Docker. On macOS and Windows open Docker Desktop → Settings → Resources and check the memory limit: kind's documentation asks for 6 GB minimum and recommends 8 GB for the Docker virtual machine. On Linux there is no limit to set.

    2. Install kind (a Kubernetes cluster inside Docker)

    macOS:

    brew install kind

    Windows (PowerShell):

    winget install Kubernetes.kind

    Linux (x86-64; for ARM replace amd64 with arm64):

    curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.33.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

    No Homebrew or winget? The same page has a curl line for every platform: kind.sigs.k8s.io/docs/user/quick-start.

    3. Install kubectl (the command-line client)

    Docker Desktop already ships a kubectl on macOS and Windows; run kubectl version --client and if it prints a version you can skip this step. Otherwise:

    macOS:

    brew install kubectl

    Windows (PowerShell):

    winget install -e --id Kubernetes.kubectl

    Linux (x86-64; for ARM replace amd64 with arm64):

    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

    Other ways (Chocolatey, apt, dnf, snap) are at kubernetes.io/docs/tasks/tools.

    4. Download the cluster image by creating and deleting a cluster

    This pulls the node image (about 370 MB) once, so the workshop needs no Wi-Fi. It takes a minute or two.

    kind create cluster
kubectl get nodes
kind delete cluster

    kubectl get nodes should list one node called kind-control-plane with status Ready (if it says NotReady, wait twenty seconds and run it again). Deleting the cluster keeps the image in Docker.

    5. Rebuild workshop 6's images with explicit tags

    In your workshop 6 folder (the one with compose.yaml, api/ and worker/):

    docker build -t api:1 api
docker build -t worker:1 worker
docker images

    You should see api with tag 1, worker with tag 1, and redis with tag 7 (from workshop 6; if it is missing, docker pull redis:7). The tags matter: the lab explains why in step 2.

    6. The readiness check

    kind version
kubectl version --client
docker images kindest/node

    Expected output

    A line beginning kind v0.33.0, a line Client Version: v1.37.0 (a newer patch number is fine; the line after it, Kustomize Version, can be ignored), and a table with one row for kindest/node. If all three are there, the lab will run without the network. If not, bring the error message to the workshop and arrive ten minutes early.

    If kind will not start

    The usual causes: Docker Desktop not running, Docker Desktop with too little memory, or on Linux a cgroup v1 system (kind warns about it and still works today). A student who cannot get a cluster can pair with a neighbour; every step works with two people at one keyboard. As a last resort, Docker Desktop has its own built-in Kubernetes (Settings → Kubernetes → Create cluster, context docker-desktop); the lab was written for kind and kind load does not apply there, but every kubectl line does.

    For the instructor

    • Run the whole lab yourself on each OS you expect in the room, with the exact commands on this page, one week before. Note how long kind create cluster takes on the slowest laptop you can find; that is the length of step 0.
    • Bring workshop 6's images on a USB stick for anyone who lost their folder: docker save api:1 worker:1 redis:7 -o w6-images.tar, restored with docker load -i w6-images.tar. Bring the node image too if the venue has no Wi-Fi: docker save kindest/node:v1.37.0 -o node.tar.
    • The demo widget at the top of this page is slide 3. Set replicas to 3, press "Kill a pod" while talking, then set replicas to 1 and watch it terminate two.
    • Have the full solution ready. The three Deployments differ by a handful of lines; a stuck student pastes redis.yaml and carries on.
    • Ask the room to close anything listening on port 8080 (a workshop 6 docker compose up still running is the usual one): docker compose down in the workshop 6 folder, or docker ps and docker rm -f.
    • Decide in advance whether you will explain the :latest trap on the projector or let everyone type the three lines in step 2. The page has them as typed; they cost two minutes and buy a lesson people otherwise learn at work, the hard way.

    The talk: say what should be true

    The single idea to land: you never tell Kubernetes what to do; you tell it what should be true, and it keeps making it true. Every command in the lab either states a desired state or asks what the actual state is. Nothing else.

    1. 1Who restarts it at three in the morning?1 min Title slide. Workshop 6 ended with docker compose up on one laptop. Ask: the worker crashes at 3 a.m. on a server, who restarts it? The server dies, who moves the containers? You ship a broken image, who rolls it back? Today the answer to all three is "a control loop", and by the end of the afternoon they will have watched it happen.
    2. 2What a cluster is2 min Nodes are machines that run containers. The control plane is a small set of programs: an API server that stores the desired state, a scheduler that picks a node for each pod, and controllers. kubectl is just an HTTP client for the API server. On the laptop the whole thing is one Docker container; on a cloud it is hundreds of machines; the commands are identical, which is the point of doing it here first.
    3. 3Desired versus actual: the control loop2 min The widget on this page. A Deployment says "three replicas". A controller reads that, counts the pods that exist, and creates or deletes to close the gap; then it does it again, forever. Kill a pod on the widget: the count drops to two, the loop notices, a new one appears. Set replicas to one: two are terminated. Nobody typed "restart" or "stop"; they changed a number. That is the whole model. The thermostat analogy from the Kubernetes docs.
    4. 4The Pod is the unit1 min Kubernetes never runs a container on its own; it runs a Pod, one or more containers that share a network address and can share storage. Almost always one container. A pod is disposable: it has a name and an IP until it dies, and it is not restarted, it is replaced. Step 1 runs a single pod by hand so the lifecycle is familiar before anything manages it.
    5. 5Deployment, ReplicaSet, Pods2 min The Deployment YAML on the slide is the one they type in step 3. Four top-level keys every object has: apiVersion, kind, metadata, spec. Inside spec: replicas (how many), selector (which pods are mine, by label), template (what a pod looks like). A Deployment makes a ReplicaSet, which makes the pods; the Deployment exists so that changing the template makes a new ReplicaSet next to the old one, which is what a rolling update is. Labels are the glue: every "which pods" question in Kubernetes is answered with labels.
    6. 6A Service is a stable name for moving pods2 min Pods die and come back with new IPs, so nothing may talk to a pod by IP. A Service is a name plus a virtual IP plus a selector; the cluster's DNS makes the name resolve, and traffic to it is spread over whatever pods match the selector right now. In compose the API reached Redis as redis; here it is the same word, and the Service is why. kubectl expose writes that YAML for you; not every object is typed by hand.
    7. 7Rolling update and rollback2 min Change the image in the template and the Deployment creates a second ReplicaSet and shifts pods across, a few at a time, by default at most 25% extra and at most 25% missing. The old ReplicaSet is kept at zero replicas, which is why rollout undo is instant: scale the old one up, the new one down. Nothing is rebuilt; the history is a list of templates. Step 6 does this with a one-string change to the API.
    8. 8kind, and the :latest trap1 min kind runs a Kubernetes node as a Docker container, with its own image store, so images built on the laptop must be copied in with kind load docker-image. And a tag of :latest, or no tag, sets the pull policy to Always, so the node asks Docker Hub and fails with ImagePullBackOff even though the image is right there. Tag everything. Step 2 shows the failure on purpose.
    9. 9What the laptop cluster is not1 min One node, so "reschedule to another machine" cannot be shown. No load balancer, so port-forward stands in for a real external IP. No persistent storage, so Redis loses its queue when its pod dies. A cloud cluster adds exactly those three things and charges for them. Everything else on this page transfers unchanged.
    10. 10What we build in the next 90 minutes1 min Seven steps: create the cluster, run one pod by hand, load the images and see the trap, type one Deployment and expose it, paste the other two and send the workshop 6 request through port-forward, scale to three and kill a pod, roll out api:2 and roll it back. Five-minute break, then step 0.

    Step 0

    A cluster in a container

    5 min
    kind create cluster
kubectl get nodes

    The first command prints a checklist (Ensuring node image, Preparing nodes, Starting control-plane, and so on) and ends with Set kubectl context to "kind-kind". It also wrote the cluster's address and credentials into ~/.kube/config, which is how kubectl knows where to send requests. Run docker ps if you like: the whole cluster is one container named kind-control-plane.

    Checkpoint 0

    kubectl get nodes prints one row: kind-control-plane, STATUS Ready, ROLES control-plane, VERSION v1.37.0. If STATUS is NotReady, wait twenty seconds and run it again.

    Instructor

    Walk the room. Anyone whose cluster is not up in three minutes gets the USB stick (docker load -i node.tar) or a neighbour. Do not start step 1 until every screen shows Ready.

    Step 1

    One pod, by hand

    12 min

    Before anything is managed, run one pod the way you ran one container in workshop 1. The node has its own image store, separate from your laptop's Docker, so first copy the Redis image in (step 2 explains this properly):

    kind load docker-image redis:7
kubectl run redis --image=redis:7
kubectl get pods

    kubectl run prints pod/redis created. get pods shows the columns you will read all afternoon: NAME, READY (1/1 means one container of one is ready), STATUS, RESTARTS, AGE. If STATUS says ContainerCreating, run it again in a few seconds. Now the two commands that answer "what is going on":

    kubectl describe pod redis
kubectl logs redis

    describe is long; read the bottom, the Events table: Scheduled, Pulled, Created, Started. That is the pod's life story and the first place to look when something is stuck. logs is docker logs; the last line is Redis saying Ready to accept connections. Now delete it and check it is gone:

    kubectl delete pod redis
kubectl get pods

    Checkpoint 1

    The pod reached STATUS Running and READY 1/1; logs ended with Ready to accept connections; after delete (which prints pod "redis" deleted from default namespace) get pods says No resources found in default namespace.

    Talk about it: the pod is gone and nothing brought it back. That is correct: nobody said it should exist, only that it should be created once. Compare with docker run + docker rm. What would have to be true for something to recreate it? (Something must hold the desired state. Step 3.)

    Step 2

    Your images, and the :latest trap

    8 min

    The kind node is a container with its own container runtime inside it, so the images you built on the laptop are invisible to it until you copy them across. Load both workshop 6 images:

    kind load docker-image api:1 worker:1

    Now the trap, on purpose. Ask for the API image without a tag:

    kubectl run bad --image=api
kubectl get pods
kubectl delete pod bad

    No tag means api:latest, and for :latest Kubernetes sets the pull policy to Always: the node asks the registry every time, ignoring the copy it already has, and Docker Hub has no api image. For any other tag the policy is IfNotPresent: use what is there, pull only if missing. That is why the prep said to tag the images :1 and why step 6 tags the next one :2. The habit for life: never ship :latest, in Kubernetes or anywhere.

    Checkpoint 2

    kind load prints one Image: "api:1" with ID "sha256:…" not yet present on node "kind-control-plane", loading... line per image (or found to be already present on all nodes if you ran it twice); the bad pod shows STATUS ErrImagePull or ImagePullBackOff and never Running; after delete the list is empty again.

    Common mistakes: kind load run before the cluster exists (step 0) or after it was deleted; images built under a different name in workshop 6 (check docker images; the prep asked for api:1 and worker:1 exactly).

    Step 3

    A Deployment and a Service

    17 min

    Now state a desired state. Create a file redis.yaml in k8s-lab and type it, indentation and all (two spaces per level, never tabs):

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7
          ports:
            - containerPort: 6379

    Read it top to bottom as you type. apiVersion and kind say what this object is. metadata.name names it. spec.replicas is how many pods should exist. spec.selector says which pods count as mine: those labelled app: redis. spec.template is the pod to make when one is missing, and its labels must match the selector or the API server rejects the file. Everything under template.spec is the pod from step 1, written down.

    kubectl apply -f redis.yaml
kubectl get deploy,rs,pods

    apply prints deployment.apps/redis created. The second command shows the chain: a Deployment (READY 1/1), a ReplicaSet named redis- plus a hash, and a pod named after the ReplicaSet plus five random characters. You wrote one object and got three. Now give it a stable name. This YAML is generated, not typed:

    kubectl expose deployment redis --port 6379
kubectl get svc

    expose prints service/redis exposed and creates a Service called redis: a virtual IP in the 10.96.x.x range and a DNS name, pointing at whichever pods carry the label app: redis at any moment. The first row in get svc, kubernetes, is the API server's own Service; ignore it. The Service is a real object like any other; kubectl get svc redis -o yaml shows the file you did not have to write (a trimmed version is in the full solution).

    Checkpoint 3

    kubectl get deploy,rs,pods shows deployment.apps/redis 1/1, one replicaset.apps/redis-… with DESIRED 1 CURRENT 1 READY 1, and one pod/redis-…-… Running. kubectl get svc shows redis of TYPE ClusterIP, PORT(S) 6379/TCP.

    Common mistakes: a tab character in the YAML ("found character that cannot start any token"); containers list item indented wrongly ("unknown field"); template labels that do not match the selector ("selector does not match template labels"). Every error names the line; read it before waving.

    Step 4

    The whole app, and the same request as last week

    15 min

    The API and the worker are the same shape as Redis. Paste these two files and read the diff instead of retyping: the names and labels change, the image changes, the API publishes port 8080 instead of 6379, and both get one environment variable: REDIS_ADDR=redis:6379 for the Go API and REDIS_URL=redis://redis:6379 for the Deno worker, the same two variables as in workshop 6's compose.yaml. redis is the Service name from step 3: in both systems the name of the service is its hostname.

    api.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: api:1
          ports:
            - containerPort: 8080
          env:
            - name: REDIS_ADDR
              value: redis:6379

    worker.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: worker
  template:
    metadata:
      labels:
        app: worker
    spec:
      containers:
        - name: worker
          image: worker:1
          env:
            - name: REDIS_URL
              value: redis://redis:6379
    kubectl apply -f api.yaml -f worker.yaml
kubectl get pods

    Three pods Running. Nothing outside the cluster can reach the API yet: a laptop cluster has no load balancer to hand out an external address. port-forward is the everyday substitute, a tunnel from a port on your laptop to the Service. It does not return, so run it in the second terminal:

    kubectl port-forward svc/api 8080:8080

    It prints Forwarding from 127.0.0.1:8080 -> 8080. Back in the first terminal, send the request from workshop 6 and look at what the worker did with it:

    curl -s -X POST localhost:8080/jobs -d '{"task":"hello"}'
kubectl logs deploy/worker

    Checkpoint 4

    kubectl get pods shows api-…, redis-… and worker-… all Running; the curl returns the same JSON reply the API gave in workshop 6; kubectl logs deploy/worker shows the job being picked up. Send two more and watch the log grow.

    Talk about it: the API found Redis with the same word as last week. What did the work: the Service, or the DNS server inside the cluster, or both? What would break if you renamed the Service to cache? Why is there no kubectl expose for the worker?

    Step 5

    Scale, kill, self-heal

    13 min

    Change one number, in the Deployment, from the command line:

    kubectl scale deployment worker --replicas=3
kubectl get pods -w

    -w watches: the list stays open and prints a line whenever a pod changes. Two new worker- pods appear as Pending, then ContainerCreating, then Running. Leave it running. In the other terminal (stop port-forward with Ctrl-C first, or open a third), pick any worker pod from the list and delete it by its full name:

    kubectl delete pod worker-REPLACE-WITH-A-NAME

    Watch the first terminal: the deleted pod goes Terminating, and within a second or two a pod with a new name goes Pending, ContainerCreating, Running. Nobody asked for a new pod. The ReplicaSet's desired count is still 3, the actual count fell to 2, and the controller closed the gap. That is the whole point of the afternoon, so do it twice. Then Ctrl-C the watch.

    Checkpoint 5

    kubectl get pods shows three worker- pods Running, and at least one of them has an AGE of seconds while the others are minutes old: the replacement.

    Talk about it: restart port-forward and send three requests. Run kubectl logs -l app=worker --prefix (all worker pods, each line prefixed with the pod name): which pod took which job? What happens to a job the worker was in the middle of when you deleted its pod? (Workshop 6's idempotency stretch goal is the answer.) What would happen if you deleted the Redis pod? (It comes back, empty: no volume.)

    Step 6

    Roll out, roll back

    12 min

    A new version is a new image with a new tag. Open workshop 6's API source, change one string in the text it replies with (anything you will recognise in the curl output), and rebuild it as api:2. The path is the api folder of your workshop 6 project; adjust it if yours is elsewhere:

    docker build -t api:2 ../compose-lab/api
kind load docker-image api:2
kubectl set image deployment/api api=api:2
kubectl rollout status deployment/api

    set image changes one field in the Deployment's template (api= is the container name, api:2 the new image) and prints deployment.apps/api image updated; you could equally edit api.yaml and apply it again. rollout status waits and ends with deployment "api" successfully rolled out. Restart port-forward (the old pod it pointed at is gone) and send the request: the reply has your new string. Now look at the history and undo it:

    kubectl rollout history deployment/api
kubectl rollout undo deployment/api
kubectl get rs

    Checkpoint 6

    rollout history lists REVISION 1 and 2 (CHANGE-CAUSE <none>); undo prints deployment.apps/api rolled back; get rs shows two ReplicaSets for api, the api:1 one back at DESIRED 1 and the api:2 one at 0; after restarting port-forward the reply is the old string again.

    Talk about it: nothing was rebuilt during undo; the old ReplicaSet was simply scaled up again. What did the cluster keep that made this instant? (The old template, as revision 1.) Run rollout history once more: the rollback is a new revision, 3, and revision 1 is gone, because a revision is a template and the same template cannot be two revisions. With three replicas instead of one, how many pods would exist in the middle of the rollout? (Up to four: 25% surge, rounded up.)

    Step 7

    Wrap-up and stretch goals

    8 min

    Bring the room back together for four minutes, then let the fast students pick a stretch goal. Leave the cluster running until the end; kind delete cluster is the last thing anyone types.

    Wrap-up points

    • Every command today either stated a desired state (apply, scale, set image, expose, delete) or asked about the actual state (get, describe, logs, rollout status). There was no "restart", "start" or "stop". Say it twice.
    • Pod: the disposable unit. ReplicaSet: keeps N of them. Deployment: keeps ReplicaSets, one per template, so updates and rollbacks are just scaling. Service: a name for whichever pods match a label right now.
    • Labels are the glue. Every "which pods" question was answered with app: something.
    • Tag every image. :latest means "ask the registry", and the registry does not have your laptop's build.
    • The three YAML files in k8s-lab would run unchanged on a cloud cluster. What the cloud adds is other machines, a real load balancer and real disks, not a different model.

    Stretch goals (pick one)

    • Tell it when you are ready. Add a readinessProbe (httpGet on /, port 8080) to the API's container. Then a livenessProbe. Break the probe path on purpose and watch describe and RESTARTS: a failing liveness probe restarts the container; a failing readiness probe removes the pod from the Service without restarting it. Workshop 1's HEALTHCHECK stretch goal is the same idea.
    • Ask for what you need. Add resources.requests and resources.limits (cpu: 100m, memory: 64Mi) to the worker. Set the memory limit to 8Mi and watch it get OOMKilled and restarted. This is what the scheduler uses to decide where a pod fits on a real cluster.
    • Config out of the image. Move REDIS_ADDR into a ConfigMap (kubectl create configmap app --from-literal=REDIS_ADDR=redis:6379) and reference it with envFrom. Then put a fake password in a Secret and look at how it is stored (kubectl get secret -o yaml: base64, not encryption).
    • A real front door. Install the ingress-nginx controller for kind (its docs have a one-line kubectl apply) and write an Ingress that routes /jobs to the api Service, then throw port-forward away. Needs Wi-Fi.
    • Three files became one. Put the three Deployments and two Services in a folder with a kustomization.yaml and kubectl apply -k it; or read the Helm quick start and think about which values you would let someone override. Both exist because nobody wants to maintain forty near-identical YAML files by hand.
    • Break it properly. docker exec kind-control-plane crictl images to see the node's image store. Then docker stop kind-control-plane, count to ten, docker start it, and watch kubectl get pods come back on its own. What did the cluster remember and where?

    Instructor notes

    Honesty note. This page was written in an environment without registry access: kind v0.33.0 was installed and kind create cluster was run, and it failed exactly where expected, pulling kindest/node:v1.37.0. Nothing after step 0's first line has been executed by the author. The YAML was machine-validated against the 1.37 API schema; the expected outputs are transcribed from the official documentation and the kubectl source. Before you teach it, run it end to end on each OS in the room and fix any wording that does not match what you see.

    Timing reality

    Step 0 is the fragile moment: kind create cluster takes 30 seconds on a good laptop and three minutes on a bad one, and a student who skipped the prep needs the node image from the USB stick immediately. Step 3 is where the time goes: typing 19 lines of YAML with correct indentation takes the slowest keyboard ten minutes, and the first apply error costs another two. Protect steps 5 and 6; if you are behind after step 3, cut the "talk about it" questions in steps 2 and 4 and the three :latest lines in step 2 (say it from the front instead). Step 7's stretch goals absorb whatever is left. port-forward being killed when its pod is replaced (steps 5 and 6) surprises people every time; say in advance that restarting it is normal.

    Things students ask

    • "Is this what production looks like?" The YAML, yes: these three files, with probes and resource requests added (stretch goals 1 and 2), are what a small service looks like on a cloud cluster. The kubectl apply from a laptop, no: in production a CI pipeline or a GitOps tool applies the files from a repository, and nobody types scale by hand.
    • "Why not Docker Desktop's built-in Kubernetes / minikube / k3s?" All fine, same kubectl. kind was chosen because it installs as one binary, creates and deletes clusters in seconds, and is what the Kubernetes project itself tests with. Docker Desktop's built-in cluster (Settings → Kubernetes) works for every kubectl line on this page; only kind load is different there.
    • "Why did the Redis queue disappear when I deleted its pod?" No volume. A pod's filesystem is the container's writable layer from workshop 1, and it dies with the pod. Real clusters attach a PersistentVolume; on a laptop the honest answer is "do not keep state in this cluster".
    • "Where is the YAML for the Service?" Inside the cluster: kubectl get svc redis -o yaml. Every object, typed or generated, is stored the same way and can be read back. That is also the answer to "what if I lose my files": kubectl get deploy api -o yaml.
    • "How do I get rid of all this?" kind delete cluster. It removes the container and the kubeconfig entry; the images stay in Docker.
