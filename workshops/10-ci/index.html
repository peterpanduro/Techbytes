A CI Pipeline That Builds Your Image

Workshop 1's Go server goes on GitHub, and a fifteen-line workflow tests it on every push. A second job builds its image and pushes it to ghcr.io with a token that lives for one job. govulncheck turns a vulnerable dependency into a red build, a ruleset turns the red build into a merge button that will not press, and the fixed image ends the afternoon running on your laptop. Five runs; every wait has a job to do.

  • 15 min talk
  • 90 min guided lab
  • ~25 min student prep, one week before
  • Needs workshops 1 and 3–5
  • 21 lines of YAML, 13 of Go and Dockerfile, 26 commands
  • Any OS (Git Bash on Windows)
Interactive · push and wait

The lab's workflow: a test job, then a build job that needs it. Pick a branch, the x/text version in go.mod and the Go the runner uses, then push. The findings are the real govulncheck output from the lab; the seconds are not.

Preparation

For students (about 25 minutes)

This is written to be pasted into an email or course page as-is. Windows users: use Git Bash for everything in this workshop, as in workshop 5.

1. A GitHub account, and a public repository

Use a personal account, not one owned by an organisation (organisation policies can stop you creating packages). If GitHub asks you to turn on two-factor authentication, do it now rather than in the workshop. Then, on github.com, create a new repository called ci-lab: Public, with Add a README ticked. Create it fresh; do not fork someone else's, because Actions are switched off on forks until you switch them on. It has to be public: on the free plan, rulesets (step 2 of the lab) only work on public repositories, and public repositories get Actions minutes and package storage free.

2. Clone it with SSH or Git Credential Manager

Clone it into the same folder that holds your docker-lab folder from workshop 1, so the two sit side by side:

git clone git@github.com:YOUR-USERNAME/ci-lab.git

That is the SSH address (needs an SSH key on your GitHub account). The HTTPS address works too if Git Credential Manager handles your login (Git for Windows and GitHub Desktop install it). What does not work is an HTTPS token without the workflow scope: the push in item 4 below fails with "refusing to allow an OAuth App to create or update workflow … without workflow scope". If you see that and use the GitHub CLI, run gh auth refresh -h github.com -s workflow; otherwise switch to SSH.

3. The newest Go 1.27

go version

It must print the newest 1.27 patch release on the day of the workshop. When this page was written that was go1.27.2 (released 2026-10-08, with security fixes in net/http and crypto/tls); check go.dev/dl again the day before. Not a formality: an older patch makes the vulnerability scan in item 5 below fail on the standard library, and that is the scanner being right.

4. The readiness run

In ci-lab, create the folders .github/workflows and save ci.prep.yml in it as ci.yml. It is seven lines:

name: ci
on: push
jobs:
  ready:
    runs-on: ubuntu-latest
    steps:
      - run: uname -sr
git add .github
git commit -m "Readiness run"
git push

Expected output

The push succeeds, and the repository's Actions tab shows a run called "Readiness run" that turns green within a minute or two; open it, then the ready job, and the Run uname -sr step prints a line starting with Linux. That one green tick proves your account, your login (including the workflow scope) and that Actions is switched on. A push refused with "workflow scope" is item 2. A red run titled with "Invalid workflow file" is a typo in the file: GitHub accepts the push and fails the run at once. (Not executed in the authoring environment; verified against docs.)

5. A local vulnerability scan

In your docker-lab folder from workshop 1:

go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...

After a few go: downloading lines it must print No vulnerabilities found. If instead it lists findings in the Standard library with "Found in: net/http@go1.27.1" or similar, your Go is out of date: go back to item 3. This is what go1.27.1 printed for workshop 1's server after go1.27.2 came out, shortened:

Vulnerability #1: GO-2026-6617
    HTTP/2 server crash due to HPACK encoder race in net/http
  More info: https://pkg.go.dev/vuln/GO-2026-6617
  Standard library
    Found in: net/http/internal/http2@go1.27.1
    Fixed in: net/http/internal/http2@go1.27.2
  ...
Your code is affected by 5 vulnerabilities from the Go standard library.

6. Download the one dependency in advance

From your home folder, outside any Go project, so that nothing is written into one:

cd ~
go mod download golang.org/x/text@v0.3.7 golang.org/x/text@v0.3.8

It prints nothing when it works. This saves the venue Wi-Fi a download per laptop.

7. Docker

Docker Desktop (or Docker Engine on Linux) from workshop 1, running. docker run --rm hello-world must print "Hello from Docker!".

If a student cannot use GitHub

Some employers block github.com or Actions. Such a student pairs with a neighbour for steps 1–5: they still type the YAML and the Go and run go test and govulncheck locally, which is half the lesson, and they watch the runs on the neighbour's screen.

The talk: the hook nobody can skip

The single idea to land: CI is a "no" that applies to everyone, and it is only worth what main requires. A workflow is a file that GitHub runs on a fresh machine for every push; the token it uses lives for one job; a vulnerable dependency is a failing test like any other; and none of it stops anything until a ruleset makes the check required.

  1. 1The same no, for the whole team1 min Title slide. Callback to workshop 5: the pre-commit hook lives in .git, is never pushed, and --no-verify skips it. CI is the hook nobody can skip, because it runs on a machine nobody's laptop controls. Today it builds workshop 1's image, the year's first workshop, on every push.
  2. 2A workflow is a file GitHub runs2 min Push event → workflow → jobs → steps. Walk through today's ci.yml on the slide: on: push, two jobs, runs-on, steps that either uses: an action (someone else's code, at a version) or run: a command. The file lives in the repository, so the pipeline is reviewed and versioned like the code.
  3. 3Every job is a fresh machine1 min A new VM per job, thrown away at the end. Nothing carries over except what you publish: that is why checkout appears in both jobs. needs: test orders them: the build never starts if the tests fail. Jobs without needs run in parallel.
  4. 4The wait is the design constraint2 min Use the widget: push with the defaults, then on main. The run is a queue, a VM, a Go download and a build, a minute or three. So: the fast job first and the expensive one after it; cancel-in-progress so a second push kills the first run; and never let CI be the first place a failure is seen: today's commands are the same on the laptop and the runner. Every wait in the lab has a task.
  5. 5Who is GITHUB_TOKEN?2 min A token GitHub mints for each job and revokes when the job ends. permissions: says what it may do: the build job gets packages: write, the test job only the read-only default. No personal access token is created or stored anywhere today. The package it pushes is linked to the repository, inherits its access, and starts private even in a public repository.
  6. 6Tags are names, digests are facts1 min Every push to main publishes two tags: main, which moves, and sha- plus the commit, which does not. Both name a sha256: digest, the hash of the image itself, content addressing as in workshop 5. Branches build but do not publish. Workshop 7's rollout would use the sha- tag.
  7. 7Your dependencies are your code2 min go.sum is the lock. The Go vulnerability database lists affected modules, packages and functions, so govulncheck can tell called from imported from merely required, and only fails on called. Use the widget again: v0.3.7 is red because greet calls ParseAcceptLanguage. The toolchain is a dependency too: Go 1.27.2 (2026-10-08) fixed five net/http issues this server reaches, so a runner on 1.27.1 goes red for a reason that has nothing to do with your change. check-latest fixes the runner; the image still builds with whatever golang:1.27 means that day.
  8. 8A check is only a no if main requires it2 min Without a rule, a red check is advice: anyone can merge, or push straight to main. A ruleset on the default branch requires a pull request and the test check, with an empty bypass list, so it applies to the repository owner too. Red means the merge button is blocked. This is the "no" from slide 1, made binding.
  9. 9Pin what you run1 min Every uses: line runs someone else's code with your token. Tags can move: in March 2025 the tj-actions/changed-files tags were repointed at a commit that dumped secrets into logs (CVE-2025-30066). Today we type major tags for first-party actions, because a 40-character SHA is not typeable; the stretch file pins full SHAs and lets Dependabot move them.
  10. 10The next 90 minutes1 min Six steps, five runs: workshop 1's server with a test; a workflow that runs it; a build job that publishes the image, and the ruleset during the wait; a feature on a branch that pins a vulnerable x/text and goes red; reproduce, fix and merge; run what main built. Every wait has a task. Five-minute break, then step 0.

The lab

Students work in the ci-lab folder from the prep, with a terminal (Git Bash on Windows), an editor, and the repository open in the browser. Every step ends in a checkpoint. Nobody moves to the next step until their checkpoint passes; anyone stuck for more than five minutes downloads the recovery file for that step from the full solution and continues.

Type or paste

Every code block is labelled. Type this is 60 lines over the afternoon: 21 lines of workflow YAML, 12 lines of Go, one Dockerfile line and 26 commands. Typing the workflow is how its indentation gets into your fingers. Paste this is the copy command in step 0, the two test files, and the body of the build job in step 2. Windows users run everything in Git Bash; in PowerShell, curl is a different program, so type curl.exe there.

Step 0

Workshop 1's server, with a test

10 min

The project for the afternoon is workshop 1's server, unchanged. Copy exactly four files from docker-lab into ci-lab: not visits.txt, not data/, not the Dockerfile.v1 and Dockerfile.v2 experiments, because in a minute git add . commits whatever is in the folder. (No docker-lab any more? Download main.go, go.mod, Dockerfile and .dockerignore from workshop 1 into ci-lab instead.)

cd ci-lab
cp ../docker-lab/main.go ../docker-lab/go.mod ../docker-lab/Dockerfile ../docker-lab/.dockerignore .

Workshop 1 had no tests, and a pipeline needs something to run. Save this next to main.go as main_test.go. It calls bump three times on a file in a fresh folder that Go deletes afterwards, so it never touches your real visits.txt:

main_test.go

package main

import (
	"path/filepath"
	"testing"
)

// TestBump counts three visits in a fresh, empty folder that Go deletes afterwards.
func TestBump(t *testing.T) {
	path := filepath.Join(t.TempDir(), "visits.txt")
	for want := 1; want <= 3; want++ {
		if got := bump(path); got != want {
			t.Fatalf("visit %d: bump returned %d", want, got)
		}
	}
}

Run the tests, then the same vulnerability scan as in the prep, here, then commit. Do not push yet: the next push should be the one that runs the tests.

go test ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...
git add .
git commit -m "Workshop 1's server, with a test"
ok  	hello	0.223s
No vulnerabilities found.

Checkpoint 0

go test prints ok and hello (the module name from workshop 1's go.mod), govulncheck prints No vulnerabilities found., and git status says nothing to commit, working tree clean. git log --oneline shows your commit above "Readiness run" and the README's "Initial commit".

Instructor

This is the door check for the toolchain. Anyone whose govulncheck lists Standard library findings has an old Go and will be red all afternoon for the wrong reason. The fastest fix in the room is export GOTOOLCHAIN=go1.27.2 (or the newest patch on the day) in that terminal: the go command downloads that toolchain once and uses it. A proper install from go.dev/dl can wait until home.

Step 1

A workflow that runs the tests

15 min

Open .github/workflows/ci.yml, the readiness file from the prep, delete its seven lines, and type this instead. Indent with spaces, two per level; YAML refuses tabs.

.github/workflows/ci.yml

name: ci
on: push
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-go@v7
        with:
          go-version: '1.27'
          check-latest: true
      - run: go test ./...

Read it top to bottom. on: push: run on every push, to any branch. concurrency: runs with the same group (this workflow, this branch) take turns, and a new one cancels the one in progress, so two quick pushes cost one run. One job, test, on a fresh Ubuntu VM. Its steps: actions/checkout puts your commit on the VM, which starts empty; actions/setup-go installs Go, and check-latest: true makes it fetch the newest 1.27 patch instead of whatever the runner image has cached; then your own command, the one you just ran on the laptop. '1.27' is quoted because YAML would otherwise read it as the number 1.27, which is fine here but turns 1.30 into 1.3 one day.

git add .
git commit -m "CI: run the tests"
git push

While it runs (about a minute): read the log. Open the repository's Actions tab, click the run "CI: run the tests", then the test job. Each step is a line you can expand. Set up job names the runner image and its version, and lists the permissions of the job's GITHUB_TOKEN: all read, which is the default for a new repository. Run actions/checkout@v7 is a git fetch of exactly your commit. Run actions/setup-go@v7 says which Go it found and that it downloaded the newest one. Run go test ./... is your command. The Post steps clean up, and then the VM is deleted.

Run go test ./...
ok  	hello	0.004s

Checkpoint 1

A green tick next to the run and next to the test job. The Run go test ./... step prints ok and hello, and the setup-go step mentions go 1.27.2 (or the newest patch on the day). A yellow warning from setup-go that it cannot find go.sum for its cache is harmless: the project has no dependencies yet. (Not executed in the authoring environment; verified against docs.)

Common mistakes: the file saved at .github/workflow/ci.yml (no s) or .github/workflows/ci.yml.txt, in which case nothing runs at all; a tab or a wrong indent, in which case the push succeeds and a red run appears at once, titled with "Invalid workflow file" and the line number; go-version: 1.27 unquoted, which works today. Stuck: download ci.v1.yml, save it over ci.yml, commit and push.

Talk about it: push twice within a few seconds (an empty commit will do: git commit --allow-empty -m again). The first run turns grey, "cancelled": that is concurrency. Why is the check that matters called test and not ci? (Checks are named after jobs. The ruleset in step 2 asks for test by name.)

Step 2

Build the image and push it to ghcr.io

20 min

A second job: the same docker build as workshop 1, on a runner, pushed to GitHub's container registry. Paste this at the end of ci.yml. build: must line up with test:, two spaces in:

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }} # minted for this job, dead when it ends
      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=ref,event=branch
            type=sha
      - uses: docker/build-push-action@v7
        with:
          context: .
          provenance: false # one plain image per tag, no attestation index
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

Three actions do what you did by hand in workshop 1. login-action is docker login ghcr.io, with the job's own token as the password. metadata-action works out the image name (ghcr.io/ plus your user and repository, lowercased) and two tags: the branch name, and sha- plus the first seven characters of the commit. build-push-action is docker build on the checked-out folder with those tags. provenance: false keeps it one plain amd64 image per tag, which a Mac can run with --platform; the default would wrap it in an index with an attestation entry.

Now the five lines that decide what this job may do and when. Type these four directly under build:, above runs-on:

    needs: test
    permissions:
      contents: read
      packages: write

and this one as the last line of the file, inside the build-push step's with:, lined up with labels::

          push: ${{ github.ref == 'refs/heads/main' }}

needs: test: the build starts only after test is green. permissions: this job's token may read the code and write packages, and nothing else; the test job keeps the read-only default. push: true only on main (if your default branch has another name, use it here). Every branch builds, so a broken Dockerfile shows up before the merge, but only main publishes. Commit and push:

git commit -am "CI: build and push the image"
git push

While it runs (two to three minutes): make test required. In the repository: Settings → Rules → Rulesets → New ruleset → New branch ruleset. Ruleset name main; Enforcement status Active; under Target branches, Add target → Include default branch. Leave the bypass list empty: the rules then apply to you too, which is the point. Under the rules, leave "Restrict deletions" and "Block force pushes" ticked; tick Require a pull request before merging and set required approvals to 0 (you are working alone); tick Require status checks to pass, press Add checks, type test and pick it (it is offered because run 1 reported it); leave "Require branches to be up to date before merging" unticked. Press Create. From now on, nobody pushes to main. If run 2 turns out red, fix it the new way: git switch -c fix, commit the fix, git push -u origin fix, open a pull request and merge it once test is green.

When the run is green, find the image: on the repository's front page, Packages in the right-hand column, then ci-lab. It is linked to the repository and private, even though the repository is public. To pull it you need one of these:

  • Make it public (cannot be undone): on the package page, Package settings → Danger Zone → Change visibility → Public, and type the package name to confirm. A public package can never be made private again.
  • Log Docker in with the GitHub CLI (reversible, needs gh): the token gh already holds, given one more scope. docker logout ghcr.io logs Docker out; the read:packages scope stays on gh's token until gh auth refresh -h github.com -r read:packages removes it. 
    gh auth refresh -h github.com -s read:packages
gh auth token | docker login ghcr.io -u YOUR-USERNAME --password-stdin
  • Neither: skip the two commands below. The package page is your checkpoint.

Then run what the pipeline built. Replace YOUR-USERNAME with yours, in lower case; image names cannot contain capitals. --platform linux/amd64 is workshop 1's flag: the runner built for amd64 only, and on an Apple Silicon Mac Docker runs it under emulation.

docker run --rm --platform linux/amd64 -p 8080:8080 ghcr.io/YOUR-USERNAME/ci-lab:main

The server stays in the foreground. In a second terminal:

curl localhost:8080
Hello from 3c1f0e7a9b2d! You are visit number 1.

Checkpoint 2

The run shows two green jobs, test then build, joined by an arrow. The package page lists the tags main and sha- plus seven characters of your commit, both on the same digest. curl answers with workshop 1's greeting and a container id as the host name (or, without Docker, the package page is enough). The ruleset is listed as Active. (Not executed in the authoring environment; verified against docs.)

Stop the container with Ctrl-C in the first terminal. If Ctrl-C does not stop it (Git Bash on Windows sometimes leaves it running), docker ps shows its id, and docker stop followed by that id stops it.

Instructor

"denied" from docker run means the package is still private, or the name has capitals. "unauthorized" or "permission_denied: write_package" in the build log means the permissions block is missing or mis-indented, or the student pushed an image of that name by hand once before. "no matching manifest for linux/arm64/v8" means --platform linux/amd64 was left off on a Mac. Stuck: ci.v2.yml is this step's file; since the ruleset now blocks direct pushes, put it on a branch and merge it (the step-3 recipe).

Step 3

A feature with a vulnerable dependency

20 min

main is protected now, so features start on a branch:

git switch -c greeting

The feature: greet visitors whose browser prefers Swedish with "Hej". Browsers say which languages they prefer in the Accept-Language header, for example sv-SE,sv;q=0.9,en;q=0.8, and parsing that properly is a job for the Go team's golang.org/x/text/language package. First the test; save it as greet_test.go:

greet_test.go

package main

import "testing"

// TestGreet checks that the first language in Accept-Language picks the greeting.
func TestGreet(t *testing.T) {
	cases := []struct{ header, want string }{
		{"sv-SE,sv;q=0.9,en;q=0.8", "Hej"},
		{"en-GB,en;q=0.9,sv;q=0.5", "Hello"},
		{"", "Hello"},
	}
	for _, c := range cases {
		if got := greet(c.header, "Hello"); got != c.want {
			t.Errorf("greet(%q) = %q, want %q", c.header, got, c.want)
		}
	}
}

Then the function, at the end of main.go:

func greet(acceptLanguage, fallback string) string {
	tags, _, err := language.ParseAcceptLanguage(acceptLanguage)
	if err != nil || len(tags) == 0 {
		return fallback
	}
	if base, _ := tags[0].Base(); base.String() == "sv" {
		return "Hej"
	}
	return fallback
}

Add the import at the end of the import block, after a blank line (gofmt keeps the standard library and everything else apart):

	"golang.org/x/text/language"

and in the handler, change the line that writes the greeting so it reads:

		fmt.Fprintf(w, "%s from %s! You are visit number %d.\n", greet(r.Header.Get("Accept-Language"), greeting), host, n)

Now the dependency, at a version a colleague found in an old project: v0.3.7. go mod tidy afterwards marks it as a direct dependency (go get leaves a misleading // indirect) and checks that go.sum is complete. Then the tests:

go get golang.org/x/text@v0.3.7
go mod tidy
go test ./...
go: added golang.org/x/text v0.3.7
ok  	hello	0.255s

go.mod now has require golang.org/x/text v0.3.7, and there is a new file, go.sum, with the module's hashes: the lock file. Two more one-line changes so the pipeline knows about it. In the Dockerfile, the build stage now has a lock file to copy, so change the line COPY go.mod ./ to:

COPY go.mod go.sum ./

go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...

// A tiny web server: says hello, tells you which machine it runs on,
// and counts visits in a file so we can see what survives a restart.
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
	"strconv"
	"strings"

	"golang.org/x/text/language"
)

func main() {
	greeting := os.Getenv("GREETING") // configuration comes from the environment
	if greeting == "" {
		greeting = "Hello"
	}
	host, _ := os.Hostname() // inside a container this is the container id

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path != "/" { // browsers also ask for /favicon.ico; do not count that
			http.NotFound(w, r)
			return
		}
		n := bump("visits.txt")
		log.Printf("%s %s -> visit %d", r.Method, r.URL.Path, n)
		fmt.Fprintf(w, "%s from %s! You are visit number %d.\n", greet(r.Header.Get("Accept-Language"), greeting), host, n)
	})

	log.Println("listening on http://localhost:8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}

// bump reads a number from the file, adds one, writes it back.
func bump(path string) int {
	b, _ := os.ReadFile(path)
	n, _ := strconv.Atoi(strings.TrimSpace(string(b)))
	n++
	if err := os.WriteFile(path, []byte(strconv.Itoa(n)), 0o644); err != nil {
		log.Println("could not save the counter:", err)
	}
	return n
}

// greet says Hej to visitors whose first choice of language is Swedish.
func greet(acceptLanguage, fallback string) string {
	tags, _, err := language.ParseAcceptLanguage(acceptLanguage)
	if err != nil || len(tags) == 0 {
		return fallback
	}
	if base, _ := tags[0].Base(); base.String() == "sv" {
		return "Hej"
	}
	return fallback
}

package main

import (
	"path/filepath"
	"testing"
)

// TestBump counts three visits in a fresh, empty folder that Go deletes afterwards.
func TestBump(t *testing.T) {
	path := filepath.Join(t.TempDir(), "visits.txt")
	for want := 1; want <= 3; want++ {
		if got := bump(path); got != want {
			t.Fatalf("visit %d: bump returned %d", want, got)
		}
	}
}

Running the room

Instructor notes

Timing reality

The lab has about ten minutes of runner time in five runs, and every one of them has a task, so the room should never be watching a spinner. Step 1 is where YAML indentation costs time: walk the room while people type, look at the left edge of the file, and send anyone stuck for five minutes to ci.v1.yml. Step 2's ruleset takes longer than its wait for people who have never seen the Settings page; do it once on the projector while run 2 is going. Step 3 has the most typing (21 lines); if the room is behind at 1:00, paste greet for those who need it and keep the go get line typed, because it is the lesson. In step 4 the merge has to wait for run 4's test, and step 5 waits for run 5: about four to five minutes of waiting in the last 25 minutes, which is why the wrap-up is spoken during run 5 rather than after it. If you are behind at 1:20, do the wrap-up and leave the Swedish curl for home.

Things students ask

  • "Why did my push to main get refused?" The ruleset from step 2, working as intended. Rescue the commit with workshop 5's tools: git switch -c fix, git branch -f main origin/main, push the branch and open a pull request.
  • "What are the grey cancelled runs?" concurrency: a newer push to the same branch cancelled the older run. Nothing failed.
  • "Is the token in the log a leak?" GitHub masks it in logs, and it expires when the job ends. A personal access token would be neither masked nor short-lived if it were ever printed some other way; that is why there is none today.
  • "Why not Trivy, or Dependabot alerts?" Image scanners also report standard-library CVEs found in the binary and anything in the image, which is useful and noisy; Dependabot alerts read go.mod, so they would have flagged GO-2026-6629 and GO-2026-5970 too. govulncheck is the Go team's own tool, needs no third-party action, and fails only on what the code calls. Use both kinds in real projects.
  • "Why go run …@v1.8.0 and not the govulncheck action?" The same command runs on the laptop and the runner, it is pinned, and the official golang/govulncheck-action describes itself as experimental. The price is compiling govulncheck in every run, about half a minute.
  • "Does the image get scanned?" No: the source was. The image's Go came from golang:1.27 on the day the runner pulled it. The stretch goal pins it.
  • "My username has capitals." metadata-action lowercases the image name for the push; docker run needs it typed in lower case.
  • "Can I make the package private again?" No. That is why making it public is optional and the gh login is offered first.

If the Wi-Fi fails

Pushes are kilobytes and x/text was downloaded in the prep, so a slow network is fine. With none, run the five runs from your own repository on a phone hotspot, on the projector. Students still type the YAML and the Go and run go test locally; govulncheck needs vuln.go.dev, so show its output from your screen. Students push at home; every checkpoint on this page can be checked later from the Actions tab. If even the hotspot fails, open your rehearsal repository's public run logs (kept 90 days by default) and the five screenshots from the instructor prep.

Risks, and what to say

  • The runner's cached Go is behind. check-latest: true handles it; it is why the line is there.
  • A new advisory for x/text/language before the workshop. Step 3 then shows two findings and step 4's fix is the newest "Fixed in". Re-run the three scans from the solution statement the day before.
  • "permission_denied" when pushing the image. A package of that name was once pushed by hand, or the account is an organisation's. Use a fresh personal ci-lab.
  • Docker Hub rate limits on golang:1.27. GitHub's documentation for Enterprise Server 3.14 says hosted runners pulling public images are exempt; not confirmed for github.com. Re-run the job if it happens.
  • Action majors released or retired before the workshop. Re-check the five tags on the day.
