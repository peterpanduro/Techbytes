1

The same no, for the whole team

0:00 → 1:00 · 1 min · 149 words

In workshop five you installed a pre-commit hook: a script that runs your tests and says no to a commit that breaks them. And I told you its weakness. It lives in the dot-git folder, so it is never pushed, every clone has to install it again, and anyone can skip it by typing dash dash no-verify. A seatbelt, not a lock.

Today is the lock. Continuous integration is the same no, but it runs on a machine that none of our laptops control, on every push, for everyone on the team. And because this is the last workshop of the year, what it builds is the first thing we made: workshop one's Go server and its image. By the end of the afternoon a machine will test it, scan it, build it and publish it every time you push, and refuse to let a broken change into main.

2

A workflow is a file GitHub runs

1:00 → 3:00 · 2 min · 242 words

Here is the whole idea in one picture. You push. GitHub looks in your repository for files in dot-github slash workflows, and every file whose on line matches the event starts a run. Ours says on push, so every push to any branch starts one.

A run is made of jobs, and a job is made of steps. On the right is the file you will have at the end of the afternoon, all of it. Two jobs, test and build. Each says runs-on ubuntu-latest, which means: give me a fresh Ubuntu virtual machine. Each has a list of steps, and a step is one of two things. Either uses, which runs an action, a small program somebody published, at the version you name after the at sign: checkout, setup-go, the Docker login, build and push. Or run, which is a shell command, exactly as you would type it: go test, govulncheck.

The thing I want you to notice is where this file lives. It is in the repository, next to the code. It goes through the same pull request, the same review, the same history. If someone weakens the pipeline, it is a diff with their name on it. That is the difference between a pipeline and a build server somebody configured by clicking, once, years ago. In step one you type the first fifteen lines of it yourself, and you will see that it is less magic than it looks.

3

Every job is a fresh machine

3:00 → 4:00 · 1 min · 125 words

One fact explains half of the confusing things about CI. Every job gets a brand-new virtual machine, and the machine is thrown away when the job ends. Nothing carries over: not the files, not the Go you installed, not the image you built, unless you publish it somewhere.

That is why checkout appears twice in our file. The test job's copy of your code died with the test job's machine, so the build job fetches it again. And it is why the build job says needs. Without it, test and build would start at the same moment on two machines. With needs test, the build waits, and if the tests fail it never starts at all. You will see that grey skipped in step three.

4

The wait is the design constraint

4:00 → 6:00 · 2 min · 233 words

This widget is the lab's pipeline. Let me push with the defaults: a branch called greeting, the fixed library, the current Go. Set up job: that is the queue and the machine. Checkout. Setup-go. Go test is quick. Govulncheck is the slow one, because go run compiles it first, on a machine that has never seen it. Then build, with its own setup, and the build itself is most of it. Nothing is pushed, because this is a branch. Now main, and push again: the same, and this time it publishes.

The seconds are made up, but the shape is real. A run is a minute or three, and you will wait for five of them today. So the wait is the thing you design around. Put the fast job first, so a broken test fails in seconds and the expensive build never starts. Turn on cancel-in-progress, so when you push twice in a row the first run is cancelled instead of wasting three minutes. And above all, never let CI be the first place a failure is seen. Every command in our pipeline is one you can run on your laptop, in the same form. When CI goes red today, you will reproduce it locally in seconds, instead of pushing guesses and waiting three minutes per guess.

And every wait in the lab has a task. You will not be watching spinners.

5

Who is GITHUB_TOKEN?

6:00 → 8:00 · 2 min · 226 words

To push an image, the build job has to log in to the registry. With what? The answer most tutorials used to give is: make a personal access token and paste it into the repository's secrets. Today we do not create a single token.

Instead, GitHub mints a fresh token for every job, called GITHUB_TOKEN. It exists from the moment the job starts until the moment it ends, and then it is revoked. If it ends up in a log, it is worthless by the time anyone reads the log, and GitHub masks it anyway.

What it may do is written in the file. The permissions block on the build job says: contents read, packages write. Read the code, push packages, nothing else. Not delete the repository, not change settings, not push commits. The test job says nothing, so it gets the default for a new repository, which is read only. That is least privilege, the idea from the security workshops, as four lines of YAML.

Two things about the package it creates. It is linked to the repository and inherits who may access it. But it starts private, even though your repository is public. To pull it on your laptop you either make it public, which cannot be undone, or log Docker in with the GitHub command-line tool, which can. Both are on the page.

6

Tags are names, digests are facts

8:00 → 9:00 · 1 min · 119 words

Every push to main publishes one image with two names. The tag main, which moves every time main changes. And sha-dash plus the first seven characters of the commit, which never moves, because that commit never changes. Both are labels. The fact underneath is the digest, the sha256 of the image itself: same bytes, same digest, on every machine. You have met this idea before; a git commit hash is content addressing too.

Branches build, but only main publishes, so the registry only ever holds code that passed. In workshop seven you rolled out api colon two. With this pipeline you would roll out a sha tag, because a rollback needs a name that still means the old image.

7

Your dependencies are your code

9:00 → 11:00 · 2 min · 224 words

Your program is mostly other people's code, and in Go the list of it is go dot sum: every module at an exact version, with a hash. That is the lock. The Go team keeps a vulnerability database that knows, for each advisory, the module, the package and the exact functions affected. That is what makes govulncheck different. It reads your code, follows the calls, and sorts findings into called, imported and required, and it only fails on called.

Watch the widget. x/text zero point three point seven: red. GO-2022-1059, and the trace says hello dot greet calls language dot ParseAcceptLanguage. That is your code, in step three. Zero point three point eight: green, and two newer advisories in the same module are reported but do not fail, because we never import those packages.

Now the third toggle. The toolchain is a dependency too. Go 1.27.2 came out on the eighth of October 2026 with fixes in net slash http, and this server reaches five of them. A runner with a cached 1.27.1 goes red for a reason that has nothing to do with your change. One line, check-latest true, fixes the runner, and the prep fixed your laptop. The image is another matter: it is compiled by whatever golang 1.27 means on the day it is pulled. That one is a stretch goal.

8

A check is only a no if main requires it

11:00 → 13:00 · 2 min · 213 words

Here is the uncomfortable part. Everything so far is advice. A red cross on a pull request does not stop anyone pressing merge, and nothing stops anyone pushing straight to main and skipping the pull request entirely. CI that nobody is required to pass is a dashboard.

The fix is a ruleset on the default branch, with two rules. Require a pull request before merging, so main only changes through one; we set required approvals to zero because you work alone today, but on a team that is where review lives. And require status checks to pass, naming the check: test, the name of our job. Now red means the merge button is blocked. We leave the bypass list empty, so it applies to the owner of the repository as well, which is you: after step two, your own git push to main is refused, by your own rule.

That is the no from slide one, made binding. The hook in workshop five could be skipped by anyone, alone. This one cannot be skipped by anyone, including the person who wrote it. You create it during the wait in step two. It needs the name test, and it learns that name from your first run, which is why it comes after step one.

9

Pin what you run

13:00 → 14:00 · 1 min · 114 words

Every uses line runs somebody else's code, with your token. And a tag like v7 is a pointer, like a branch in workshop five: whoever owns the repository can move it. In March 2025 that happened to a popular action, tj-actions changed-files. Its tags were moved to a commit that printed secrets into build logs, and thousands of repositories ran it without changing a line.

The defence is to pin the full forty-character commit hash, which cannot move, and let Dependabot open a pull request when there is a new version. Today we type major tags, for actions from GitHub and Docker, because nobody types forty hex characters. The stretch file shows the habit.

The next 90 minutes

14:00 → 15:00 · 1 min · 122 words

Here is the afternoon. Step zero, workshop one's server goes into your new repository, with a test. Step one, you type the first workflow and push, and the tests run on a machine in a data centre. Step two, a build job that publishes the image, and while it runs you create the ruleset. Step three, a feature on a branch, with a dependency pinned to a vulnerable version, and you watch it go red. Step four, reproduce the failure on your laptop, fix it, and merge. Step five, we wrap up while main builds, and then you run what the pipeline published.

Five runs, and every wait has a task. Every step ends in a checkpoint. Five-minute break, then step zero.
