Log in with GitHub (OAuth 2)

Word for word, in first person. 1662 words over 15 minutes: about 13 minutes at a comfortable 130 words per minute, which leaves room for the live widget and one or two questions. Slide numbers match the deck; the same text appears in the deck's speaker view (press S).

1

"Log in with GitHub": what actually happens?

0:00 → 1:00 · 1 min · 119 words

Hands up if you have ever clicked a "Log in with GitHub" button. Keep it up if you could draw what happened between the click and the page that said hello. That is the gap we close today.

It feels like one click. It is about six HTTP requests between three parties, two of them redirects, and one of them a request your browser never sees. Today you build the server behind that button, by hand, in about fifty lines of TypeScript. You develop it against a fake GitHub on your own laptop, then point the same code at the real one and log in with your own account. Fifteen minutes of talking first, then ninety minutes of building.

2

Let an app act as you, without your password

1:00 → 3:00 · 2 min · 244 words

Start with the problem OAuth was invented for. Some app wants to do something with your GitHub account: read your profile, list your repositories. The old answer was: give it your password. Think about what that means. The app can now do everything you can do, until you change your password, and when you do, every other app you gave it to breaks as well. You cannot give it less, and you cannot take it back from just that one.

OAuth's answer is delegation. You never give the app your password. You go to GitHub, you sign in there, and GitHub asks you: this app wants to read your profile, is that all right? If you say yes, GitHub gives the app a token. The token is scoped: it can read your profile and nothing else. And it can be revoked: there is a page in your GitHub settings that lists every app you have authorized, with a button next to each.

Notice what OAuth is about: authorization, permission to act. "Log in with GitHub" borrows it for something slightly different, which is finding out who you are. We come back to that gap on slide seven, because it is exactly where GitHub differs from Google.

And workshop four, in one line: a certificate proves that a server holds the key for a name, and trust is a list you choose. That question was "encrypted to whom?". Today's question is "logged in as whom?".

3

Three parties and a redirect

3:00 → 4:00 · 1 min · 122 words

Three parties. Your browser. Your app, the server you write today. And GitHub. Who holds what? The browser holds you: your GitHub session, and whatever cookie the app gives it. The app holds a client ID, which is public, and a client secret, which is not. GitHub holds your password and decides what to hand out.

The whole protocol is who redirects whom where, carrying what. Every hop that passes through the browser is visible: it is in the address bar, in the history, in server logs. That is the front channel. One request goes straight from your app to GitHub and never touches the browser: the back channel. Keep those two words. The secret only ever travels on the back channel.

4

Step one: send the user to GitHub

4:00 → 6:00 · 2 min · 193 words

Step one. The user clicks the button, and your app does not show a form. It answers with a redirect to github dot com, slash login, slash oauth, slash authorize, with four values in the query string.

Client ID: which app is asking. GitHub looks it up, and that is how its consent page knows to say "TechBytes OAuth lab". Redirect URI: where to send the user back afterwards. It must match, exactly, the callback URL you registered in the prep. Hold on to that; it is one of today's three checks. Scope: what you are asking for. We ask for read colon user, permission to read the profile, and nothing else. Ask for the least you need, because the consent page shows the user exactly what you asked for.

And state, a random string that your app makes up for this one login. That is the next slide.

Then the user is on GitHub. They sign in there, not on your page. A password manager, a passkey, the six-digit codes from workshop two: all of that happens on GitHub's page, and your app never sees any of it. That is the point.

5

state: the string that ties the trip together

6:00 → 7:00 · 1 min · 106 words

State. Before the redirect, your app makes a long random value, puts it in the URL, and also puts it in a cookie in the user's browser. GitHub hands it back unchanged on the return trip. Your app compares the two, and if they differ, or the cookie is missing, it stops. GitHub's documentation is blunt about it: if they don't match, abort.

What it proves: this callback belongs to a login that this browser started, here, a few minutes ago. We will compare it in constant time, out of habit from workshop three. But it is not a password. The exact match is what matters.

6

Step two: the code comes back; trade it for a token

7:00 → 9:00 · 2 min · 227 words

Step two. The user says yes. GitHub redirects the browser back to your callback with two values in the query string: state, which you check, and a code.

The code is not the token. It is a claim ticket. It travelled through the browser, so assume it has been seen: it is in the address bar, in the history, maybe in a log. So it is deliberately weak. GitHub says it expires after ten minutes, and on its own it buys nothing.

To turn it into a token, your server makes a request of its own, straight to GitHub: a POST to login, slash oauth, slash access token, carrying the code, your client ID, the same redirect URI again, and the client secret. That is the back channel. The browser is not involved, the user cannot see it, and the secret never leaves your server.

One detail that will bite you otherwise: ask for JSON. By default GitHub answers in form encoding. Send an Accept header of application slash json, and you get an access token, a token type of bearer, the scope, and, because Expire user access tokens is on by default, an expiry of eight hours and a refresh token. If anything is wrong, a bad secret or a spent code, you get an error field instead, and your code has to look for it.

7

Step three: who is this? There is no ID token

9:00 → 11:00 · 2 min · 209 words

Step three, and this is where GitHub surprises people. You have a token. Who is the user?

If you have built "Sign in with Google", you may expect an ID token: a signed statement, a JSON Web Token, that says "this is user so-and-so", signed by Google, which you verify with Google's public key. That is OpenID Connect, a layer on top of OAuth, and the signature is the same idea as workshop four's certificates.

GitHub does not do OpenID Connect for logging users in. There is no ID token. So we do the only thing we can: we use the token. We call api dot github dot com, slash user, with an Authorization header that says Bearer and the token, and GitHub answers with the profile of whoever the token belongs to. A login, a numeric id, a name.

So "logged in with GitHub" means: GitHub gave us a token in exchange for a code we asked for, the token works, and slash user says it is octocat. That is the whole proof of identity. It is good enough, because we checked every step that led to the token. Which is why the checks matter. And one habit: store the numeric id, not the login. People rename themselves.

8

PKCE: bind the code to the app that asked

11:00 → 12:00 · 1 min · 120 words

PKCE, pronounced pixie: Proof Key for Code Exchange. Before the redirect, the app makes a second random value, the verifier, and keeps it. It sends GitHub only a hash of it, the challenge. When the app redeems the code on the back channel, it sends the verifier itself, and GitHub checks that its hash matches the challenge.

So a code is now bound to whoever started the login. Someone who sees the code in a URL cannot redeem it, because they never had the verifier. GitHub supports it with SHA-256 only, recommends it, and still wants your client secret. PKCE does not replace the secret, and it does not replace state. It is a third lock, on a different door.

9

Three checks that make it safe

12:00 → 14:00 · 2 min · 210 words

Here is the whole flow, and where the three checks sit. Let me step through it.

Hop one: the browser asks for the app's front page. Hop two: the app answers with the redirect. State and the verifier go into a cookie; state and the challenge go into the URL. And GitHub runs check two right here: is this redirect URI exactly the registered one? If not, no code is issued.

Hop three is between you and GitHub only. Hop four: back to the callback with the code and state. Check one, the app's own: does state match the cookie? Then the app clears the cookie, and the browser drops it.

Hop five, the back channel: secret, code, the redirect URI again, and the verifier. GitHub runs check two again, and check three: does the verifier hash to the challenge? Only then is there a token. Hop six: slash user.

Two of the three checks are run by GitHub, but each one depends on something your app does: making state and comparing it, registering exactly one callback and sending it both times, keeping the verifier. Each check is one line of code you will be able to point at, and in step seven you prove each one with a test.

What we build in the next 90 minutes

14:00 → 15:00 · 1 min · 112 words

Here is the afternoon. Step zero: a project, and a fake GitHub that runs on your laptop. It is pasted, so that everything works offline and the tests run on their own. Then the authorize URL with state; the callback server; the token exchange; slash user, and you are signed in as octocat.
