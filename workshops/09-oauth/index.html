Log in with GitHub (OAuth 2)

Build the server behind a "Log in with GitHub" button with Deno.serve: send the browser to GitHub with a state value, trade the code that comes back for a token on a channel the browser never sees, and ask GitHub's API whose token it is. A pasted fake GitHub runs the whole lab offline; then the same code logs you in with your real account, PKCE binds the code to the app that asked for it, and a test proves each of the three checks.

  • 15 min talk
  • 90 min guided lab
  • ~20 min student prep, one week before
  • Builds on workshops 2–4
  • Deno · TypeScript
  • No dependencies
  • Any OS
Interactive · the redirect dance

Six hops between three parties. Dashed hops go through the browser: the front channel, visible in the address bar and the history. Solid hops go server to server: the back channel, where the secret travels. Step through and watch where each of the three checks runs.

    At a glance

    OutcomeEvery student leaves with a folder containing a "Log in with GitHub" server they wrote themselves (49 typed lines of TypeScript), a fake GitHub to develop against offline, thirteen tests that prove the flow and its three checks, and a working answer to "what does the app actually learn about me?": a token that works, and whatever /user says. Never the password.
    Why this topicEveryone has clicked "Log in with GitHub", and most developers have wired one up by copying a tutorial or adding a library that hides the redirects. The bugs that matter live in exactly the parts that get hidden: a state that is never compared, a callback URL registered too loosely, a secret that ends up in the browser. Building the flow once by hand, small enough to read in one sitting, makes every OAuth library, and every "redirect_uri mismatch" error, readable for the rest of a career.
    ConceptsDelegated authorization; the authorization-code flow as a dance between browser, app and GitHub; front channel and back channel; client ID, client secret, redirect URI and scope; state; the token exchange with Accept: application/json; bearer tokens; why GitHub login is OAuth 2 and not OpenID Connect, so identity comes from GET /user rather than a signed ID token; PKCE with S256; HttpOnly, SameSite=Lax cookies; single-use codes.
    Assumed knowledgeWorkshop 2: Deno, TypeScript, WebCrypto (crypto.getRandomValues, crypto.subtle), deno test and permission flags. Workshop 3: constant-time comparison, here as a habit. Workshop 4, in one line: a certificate proves a server holds the key for a name, and trust is a list you choose; today the question moves from "encrypted to whom?" to "logged in as whom?". Workshop 6's Deno worker is a useful refresher for anyone whose Deno is rusty, but nothing from it is needed. No OAuth knowledge.
    LanguageTypeScript on Deno 2, no dependencies: Deno.serve is the server, fetch is the client for the back channel, WebCrypto makes state and the PKCE hash, and node:crypto's timingSafeEqual (as in workshop 2) compares. Every command runs with narrow permissions: --allow-net for named hosts only and --allow-env, never -A.

    The talk: logged in as whom?

    The single idea to land: the app never sees your password. GitHub hands it a short-lived code on a redirect it registered, and the app trades that code, plus its own secret, for a token on a channel the browser never sees. Three checks tie the trip together, and there is no signed identity: only an API call that works.

    1. 1"Log in with GitHub": what actually happens?1 min Title slide. Everyone has clicked the button; almost nobody has watched the redirects. It is about six HTTP requests between three parties, and one of them never passes through the browser. Today everyone builds the server behind the button.
    2. 2Let an app act as you, without your password2 min Giving an app your password gives it everything, forever, and you cannot take it back from just that one app. OAuth is delegation: you sign in at GitHub, and the app gets a token that is scoped and revocable. "Log in with" borrows that for identity, which is slide 7. Recap workshop 4 in one line, then move the question from "encrypted to whom?" to "logged in as whom?".
    3. 3Three parties and a redirect1 min Browser, your app, GitHub, and who holds what: the browser holds your GitHub session and the app's cookie; the app holds a public client ID and a private client secret; GitHub holds the password. Everything through the browser is the front channel and is visible; the one request from app to GitHub is the back channel. The secret only travels on the back channel.
    4. 4Step one: send the user to GitHub2 min The button is a redirect to /login/oauth/authorize with four values: client_id (which app), redirect_uri (exactly the registered callback, one of the three checks), scope=read:user (the least you need), and state. The user signs in on GitHub's page, with whatever second factor they use; the app never sees any of it.
    5. 5state: the string that ties the trip together1 min Make a long random value, put it in the URL and in a cookie, compare the two when GitHub hands it back; missing or different, stop. It proves the callback belongs to a login this browser started. Compared in constant time out of habit from workshop 3, but it is not a password: the exact match is what matters.
    6. 6Step two: the code comes back; trade it for a token2 min GitHub redirects back with code and state. The code went through the browser, so treat it as seen: it expires after ten minutes and buys nothing alone. The app POSTs code, client ID, the same redirect URI and the secret to /login/oauth/access_token on the back channel, with Accept: application/json. Show the token shape, including expires_in and the refresh token, and say that errors come back as an error field.
    7. 7Step three: who is this? There is no ID token2 min Google and Microsoft add OpenID Connect: a signed ID token you verify, like workshop 4's certificates. GitHub does not, for user login. So the app calls GET https://api.github.com/user with Authorization: Bearer and the token, and the answer is the identity. It is good enough only because every step that led to the token was checked. Store the numeric id, not the login.
    8. 8PKCE: bind the code to the app that asked1 min A second random value, the verifier, stays with the app; only its SHA-256 hash, the challenge, goes to GitHub with the redirect. At redemption the app sends the verifier and GitHub compares. A code seen in a URL is useless without the verifier. GitHub supports S256 only, recommends PKCE, and still requires the secret: it replaces neither the secret nor state.
    9. 9Three checks that make it safe2 min Use the widget and press the six hops. Hop 2: GitHub checks the redirect_uri against the registered callback (check 2). Hop 4: the app checks state against the cookie and clears it (check 1). Hop 5, back channel: GitHub checks the redirect_uri again and hashes the verifier against the challenge (check 3). Two are run by GitHub, but each depends on something the app does, and each is one line the students will point at in step 7.
    10. 10What we build in the next 90 minutes1 min Show the nine steps. Steps 0 to 4 and 6 to 7 run entirely against the pasted fake GitHub, so they work offline and deno test checks them; step 5 is four lines of .env and a real login. Five-minute break, then step 0.

    Now the fake GitHub. fakehub.ts answers the same three URLs the lab uses on github.com and api.github.com, for one registered app and one user, octocat, and it skips the login page: it approves every request at once.     // fakehub: a stand-in for github.com's two OAuth endpoints and api.github.com/user.
// One registered app, one user, and no login screen: it approves every request at once.
// Run it in its own terminal:  deno run --allow-net=127.0.0.1 fakehub.ts
const APP = {
  id: "fakehub-client",
  secret: "fakehub-secret-not-a-real-secret",
  callback: "http://127.0.0.1:8000/callback",
};
const USER = { login: "octocat", id: 1, name: "The Octocat" };

type Grant = { redirect: string; scope: string; challenge: string; expires: number };
const codes = new Map<string, Grant>();
const tokens = new Set<string>();
const random = () => crypto.getRandomValues(new Uint8Array(20)).toHex();
const json = (body: unknown, status = 200) => Response.json(body, { status });
const b64url = (bytes: Uint8Array) => bytes.toBase64({ alphabet: "base64url", omitPadding: true });

// GitHub's rule: the redirect_uri must match the registered callback exactly,
// except that a loopback address (127.0.0.1 or [::1]) may use any port.
function registered(uri: string): boolean {
  const want = new URL(APP.callback);
  const got = URL.parse(uri);
  if (!got) return false;
  if (got.hostname === "127.0.0.1" || got.hostname === "[::1]") got.port = want.port;
  return got.href === want.href;
}

function authorize(q: URLSearchParams): Response {
  if (q.get("client_id") !== APP.id) return json({ message: "Not Found" }, 404);
  const redirect = q.get("redirect_uri") ?? APP.callback;
  const challenge = q.get("code_challenge") ?? "";
  // A mismatch goes back to the registered callback, never to the URI that was asked for.
  const back = new URL(registered(redirect) ? redirect : APP.callback);
  if (!registered(redirect)) back.searchParams.set("error", "redirect_uri_mismatch");
  else if (challenge && q.get("code_challenge_method") !== "S256") back.searchParams.set("error", "invalid_request");
  else {
    const code = random();
    codes.set(code, { redirect, scope: q.get("scope") ?? "", challenge, expires: Date.now() + 600_000 });
    back.searchParams.set("code", code);
  }
  if (q.has("state")) back.searchParams.set("state", q.get("state")!);
  return new Response(null, { status: 302, headers: { location: back.href } });
}

async function verifierMatches(challenge: string, verifier: string | null): Promise<boolean> {
  if (!challenge) return true; // no PKCE at authorize time, nothing to check
  if (!verifier) return false;
  const hash = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  return b64url(new Uint8Array(hash)) === challenge;
}

async function accessToken(form: URLSearchParams): Promise<Response> {
  if (form.get("client_id") !== APP.id || form.get("client_secret") !== APP.secret) {
    return json({
      error: "incorrect_client_credentials",
      error_description: "The client_id and/or client_secret passed are incorrect.",
    });
  }
  const code = form.get("code") ?? "";
  const grant = codes.get(code);
  codes.delete(code); // a code works once, right or wrong
  if (!grant || grant.expires < Date.now() || !(await verifierMatches(grant.challenge, form.get("code_verifier")))) {
    return json({ error: "bad_verification_code", error_description: "The code passed is incorrect or expired." });
  }
  if ((form.get("redirect_uri") ?? grant.redirect) !== grant.redirect) {
    return json({
      error: "redirect_uri_mismatch",
      error_description: "The redirect_uri MUST match the registered callback URL for this application.",
    });
  }
  const token = "gho_fake_" + random();
  tokens.add(token);
  return json({
    access_token: token,
    token_type: "bearer",
    scope: grant.scope,
    expires_in: 28800,
    refresh_token: "ghr_fake_" + random(),
    refresh_token_expires_in: 15811200,
  });
}

function user(authorization: string | null): Response {
  const token = authorization?.replace(/^(Bearer|token) /, "") ?? "";
  return tokens.has(token) ? json(USER) : json({ message: "Bad credentials" }, 401);
}

/** Routes one request the way github.com and api.github.com would. */
export async function fakehub(req: Request): Promise<Response> {
  const { pathname, searchParams } = new URL(req.url);
  const route = `${req.method} ${pathname}`;
  if (route === "GET /login/oauth/authorize") return authorize(searchParams);
  if (route === "POST /login/oauth/access_token") return await accessToken(new URLSearchParams(await req.text()));
  if (route === "GET /user") return user(req.headers.get("authorization"));
  return json({ message: "Not Found" }, 404);
}

}

    The callback server

    10 min

    Create server.ts. It starts with four pasted helpers. cookie writes the cookie that carries state between the two halves of the login; read its comment, because every flag is there for a reason, including the one that is missing. readCookie reads it back. same is the constant-time comparison from workshop 3, here out of habit: state is not a password, and what matters is that it matches exactly. page writes a one-line HTML page, escaped.

    // The app: "/" sends you to GitHub, "/callback" is where GitHub sends you back.
import { timingSafeEqual } from "node:crypto";
import * as oauth from "./oauth.ts";

// state (and from step 6 the PKCE verifier) waits in one cookie for ten minutes.
// HttpOnly: page scripts cannot read it. SameSite=Lax: it still arrives on the
// top-level redirect back from GitHub, where Strict would drop it. No Secure flag,
// because this is plain HTTP on 127.0.0.1; a real deployment on HTTPS adds it.
function cookie(value: string, maxAge = 600): string {
  return `oauth=${value}; HttpOnly; SameSite=Lax; Max-Age=${maxAge}; Path=/callback`;
}

function readCookie(req: Request): string[] {
  const m = req.headers.get("cookie")?.match(/(?:^|;\s*)oauth=([^;]+)/);
  return m ? m[1].split(".") : [];
}

// Constant time out of habit (workshop 3). state is not a password: what matters is the exact match.
function same(a: string | undefined, b: string | null): boolean {
  const x = new TextEncoder().encode(a ?? ""), y = new TextEncoder().encode(b ?? "");
  return x.length > 0 && x.length === y.length && timingSafeEqual(x, y);
}

function page(status: number, text: string): Response {
  const safe = text.replace(/[&<>"]/g, (c) => `&#${c.charCodeAt(0)};`);
  return new Response(`<!doctype html><meta charset="utf-8"><title>OAuth lab</title><p>${safe}</p>\n`, {
    status,
    headers: { "content-type": "text/html; charset=utf-8" },
  });
}

    Now the two routes, typed. start makes a fresh state, puts it in the cookie, and redirects the browser to GitHub with it. callback is where GitHub sends the browser back: it refuses unless the state in the query matches the one in the cookie, and for now it just shows the code it received.

    async function start(): Promise<Response> {
  const state = oauth.newState();
  const location = oauth.authorizeUrl(state);
  return new Response(null, { status: 302, headers: { location, "set-cookie": cookie(state) } });
}

async function callback(req: Request, url: URL): Promise<Response> {
  const [saved] = readCookie(req);
  if (!same(saved, url.searchParams.get("state"))) return page(400, "state does not match: login refused");
  const code = url.searchParams.get("code") ?? "";
  return page(200, `got a code: ${code}`);
}

    Last, paste the router. It sends / to start and /callback to callback, turns any error into a 502 page, and clears the cookie on every callback, whatever happened, so the browser drops it after one use. Deno.serve runs only when the file is started directly, so the tests can import handler and call it without opening a port.

    /** "/" starts a login, "/callback" finishes it; every callback clears the cookie. */
export async function handler(req: Request): Promise<Response> {
  const url = new URL(req.url);
  if (url.pathname === "/") return await start();
  if (url.pathname !== "/callback") return page(404, "not found");
  const res = await callback(req, url).catch((e: Error) => page(502, `login failed: ${e.message}`));
  res.headers.append("set-cookie", cookie("", 0)); // whatever happened, the browser drops this state
  return res;
}

const b64url = (bytes: Uint8Array) => bytes.toBase64({ alphabet: "base64url", omitPadding: true });

export type Token = { access_token: string; token_type: string; scope: string; expires_in?: number };
export type User = { login: string; name: string | null };

export function newState(): string {
  return b64url(crypto.getRandomValues(new Uint8Array(32)));
}

export function authorizeUrl(state: string, challenge?: string): string {
  const q = new URLSearchParams({ ...app(), scope: "read:user", state });
  if (challenge) q.set("code_challenge", challenge);
  if (challenge) q.set("code_challenge_method", "S256");
  return `${env("OAUTH_BASE")}/login/oauth/authorize?${q}`;

async function callback(req: Request, url: URL): Promise<Response> {

// GitHub's rule: the redirect_uri must match the registered callback exactly,
// except that a loopback address (127.0.0.1 or [::1]) may use any port.
function registered(uri: string): boolean {
  const want = new URL(APP.callback);
  const got = URL.parse(uri);
  if (!got) return false;
  if (got.hostname === "127.0.0.1" || got.hostname === "[::1]") got.port = want.port;
  return got.href === want.href;
}

function authorize(q: URLSearchParams): Response {
  if (q.get("client_id") !== APP.id) return json({ message: "Not Found" }, 404);
  const redirect = q.get("redirect_uri") ?? APP.callback;
  const challenge = q.get("code_challenge") ?? "";
  // A mismatch goes back to the registered callback, never to the URI that was asked for.
  const back = new URL(registered(redirect) ? redirect : APP.callback);
  if (!registered(redirect)) back.searchParams.set("error", "redirect_uri_mismatch");
  else if (challenge && q.get("code_challenge_method") !== "S256") back.searchParams.set("error", "invalid_request");
  else {
    const code = random();
    codes.set(code, { redirect, scope: q.get("scope") ?? "", challenge, expires: Date.now() + 600_000 });
    back.searchParams.set("code", code);
  }
  if (q.has("state")) back.searchParams.set("state", q.get("state")!);
  return new Response(null, { status: 302, headers: { location: back.href } });
}

async function verifierMatches(challenge: string, verifier: string | null): Promise<boolean> {
  if (!challenge) return true; // no PKCE at authorize time, nothing to check
  if (!verifier) return false;
  const hash = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
  return b64url(new Uint8Array(hash)) === challenge;
}

async function accessToken(form: URLSearchParams): Promise<Response> {
  if (form.get("client_id") !== APP.id || form.get("client_secret") !== APP.secret) {
    return json({
      error: "incorrect_client_credentials",
      error_description: "The client_id and/or client_secret passed are incorrect.",
    });
  }
  const code = form.get("code") ?? "";
  const grant = codes.get(code);
  codes.delete(code); // a code works once, right or wrong
  if (!grant || grant.expires < Date.now() || !(await verifierMatches(grant.challenge, form.get("code_verifier")))) {
    return json({ error: "bad_verification_code", error_description: "The code passed is incorrect or expired." });
  }
  if ((form.get("redirect_uri") ?? grant.redirect) !== grant.redirect) {
    return json({
      error: "redirect_uri_mismatch",
      error_description: "The redirect_uri MUST match the registered callback URL for this application.",
    });
  }
  const token = "gho_fake_" + random();
  tokens.add(token);
  return json({
    access_token: token,
    token_type: "bearer",
    scope: grant.scope,
    expires_in: 28800,
    refresh_token: "ghr_fake_" + random(),
    refresh_token_expires_in: 15811200,
  });
}

function user(authorization: string | null): Response {
  const token = authorization?.replace(/^(Bearer|token) /, "") ?? "";
  return tokens.has(token) ? json(USER) : json({ message: "Bad credentials" }, 401);
}

    Things students ask

    • "Is this how 'Sign in with Google' works?" The same code flow, plus OpenID Connect: Google also returns an ID token, a signed JWT naming the user, which the app verifies with Google's published keys, the workshop 4 idea of a signature you check against a key you trust. GitHub issues no ID token for user login, so the lab calls /user instead.
    • "Why does the app still need a secret if it does PKCE?" GitHub does not distinguish apps that can keep a secret from apps that cannot, and requires the secret for OAuth apps either way. PKCE protects the code; the secret identifies the app.
    • "Why keep the verifier in a cookie rather than on the server?" It keeps the lab's server stateless. An HttpOnly cookie with a ten-minute life, cleared after use, is a common pattern; a server-side map from state to verifier is equally good, and a fine stretch goal.
    • "What HTTP status does GitHub use for a bad secret?" Its documentation shows the JSON error and its wording, not the status; the fake GitHub answers 200 with the error in the body, which is why exchangeCode looks for error rather than checking res.ok.
    • "Is a code really single-use on GitHub?" GitHub's documentation says a code expires after ten minutes and that an incorrect or expired one gives bad_verification_code; it does not state single use. RFC 6749 requires authorization servers to refuse a second use, and the fake GitHub does.
    • "Why not localhost?" RFC 8252 recommends the loopback IP literal for apps on the user's own machine, and a cookie set for localhost is not sent to 127.0.0.1, as step 2's common mistake shows. GitHub accepts either if registered; consistency is what matters.
    • "Can I use this code in production?" Use a maintained OAuth client library for your framework, over HTTPS, with the Secure flag on the cookie and the secret in a secret store. The point of writing it by hand is to be able to read that library.
